### Added

- **The dispatch id (`spec/dispatch.md`, "The dispatch id", I1 to I4; [#2681](https://github.com/lushly-dev/afd/issues/2681)).** `CommandContext::dispatch_id()` names one call: 128 bits from the OS random source (never the context's `random`, so a journal's tape is unchanged) as 22 characters of unpadded base64url, set by `CommandRegistry::execute` before any check. Each call, batch item, pipeline step and command a handler runs through the registry gets its own, and the outer call keeps its own; a retry inside the chain runs under the same id. No caller or middleware can set it: the field is crate-private, every link of the chain restores it, and `extra` values under `dispatch_id` or `dispatchId` are removed before the call runs and before each link. Declaring a context field named `dispatch_id` or `dispatchId` now fails registration. The id is not stamped on the result, not written to journal entries and not among the context digest's `keys`, so results, `wire/journal.jsonl` and every digest are unchanged. It is `None` outside the registry (`CommandDefinition::execute`). A failure of the OS random source fails the call with `COMMAND_EXECUTION_ERROR` before any check.
- **The approval summary (`spec/command-metadata.md`, "The approval summary", rules 1 to 5; [#2681](https://github.com/lushly-dev/afd/issues/2681)).** `ApprovalMiddlewareOptions::with_on_approval_accepted(|summary, dispatch_id| ...)` is called, and awaited, each time the approval middleware admits a held call, before the next link: on an accepted token (`ApprovalVia::Token`, an approver client's carried token included), a `DirectClient` approval (`Direct`), an accepted answer over the form relay (`Elicitation`, once for each gated step of an `afd-batch` or `afd-pipe` approved up front) or relay evidence (`Relay`). It is given an `ApprovalSummary` (`via`, `command`, `input_digest`, `approval_id`, and `issued_at` and `expires_at` only when the evidence carries them: a token both, an elicitation hold its expiry, relay evidence neither), which serializes as the spec's object and holds no token, nonce, key or decision id, and the call's `dispatch_id` (`Option<String>`, `None` only outside the registry). The hook fails closed: an `Err` is the middleware's exception: it unwinds as a panicking middleware does, so a link outside the approval step sees an error rather than a result, and the registry answers `COMMAND_EXECUTION_ERROR` ("An internal error occurred") before the handler, with single-use evidence spent (where panics abort, the call fails with that error instead). `CommandDefinition::execute`, which is not a dispatch, clears the id from the context it is given. A call no policy held gets no summary. `afd::approval_id(single_use_key)` is the unpadded base64url SHA-256 of `approval\0<key>`, and the new `ApprovalRequest::approval_id` (the `with_on_approval_required` request) and `DirectApprovalRequest::approval_id` carry the id a held call's token will have. `tests/journal_seams_vectors.rs` runs every case of `spec/vectors/journal-seams.json` (the relay and elicitation cases with the `server` feature) and Rust leaves its `gaps`; `tests/approval_vectors.rs` checks each binding's `inputDigest` and `approvalId`.

- **`secret` commands in the journal (`spec/journal.md`; TypeScript #2576).** `CommandDefinition::as_secret()` sets the new `secret` field (default `false`; a `bool`, so a value of another type cannot be declared, and not reported in any tool, `afd-detail` or `afd-help` output). A `JournalRecorder` never records a call to such a command unless it has a redactor (`with_redact` or the new `with_redact_info`), whatever `with_filter` says; the default filter still skips `auth-*`. The registry reads the declaration from the command it runs, never from its name or the context, and passes it to the recorder. `with_redact_info(|record, info| ...)` is told `JournalRedactInfo { secret }` with each record; `with_redact` keeps its one-argument signature, so existing callers compile unchanged, and each replaces a redactor set before. The recorder runs inside the registry, so unlike TypeScript the answer is always known (`bool`, never unknown). **Caution:** a redactor set with `with_redact` now admits calls to secret commands without being told which they are, so a redactor that keeps records it does not recognise should move to `with_redact_info` and drop or sanitise those whose `info.secret` is `true` (Umbel's host and Loam mail's engine now do). A secret call never puts its clock readings or random values on a recording parent's tape (every recording ancestor, not only the nearest): given the parent's recording sources themselves, it runs on the sources under them and each such tape is marked `truncated`; given them inside a host's own wrapper, each tape refuses its readings and is marked `truncated` only once the call reads through it. A recorded secret call keeps its reads on its own entry. Two mechanisms hold this: the call runs on the sources under the recording ones (a hidden, defaulted `journal_taping` method on `Clock` and `RandomSource`, answered only by the journal's sources and forwarded by `Arc`), and its middleware steps, handler and its recorder's own timing run in a secret scope (taken again by every step, so a middleware that moves the rest of the chain to another task does not leave it) in which a tape accepts readings only from its own call's scope or a non-secret call inside it, so a host's own clock or random source wrapping a recording one leaks nothing either, not even to a sibling secret call's tape. `CommandDefinition::execute`, which calls a handler directly, does the same for a secret definition. A task the secret call spawns runs outside its scope, so its reads through a host's wrapper around a recording source can still reach a parent's tape. `JournalRecorder::records` still answers for the filter alone. Behaviour changes only for commands that declare `secret`.
- **MCP task post-completion retention and execution run budget ([#2500](https://github.com/lushly-dev/afd/issues/2500)).** `TaskOptions` now separates execution run budget (`with_max_run_ms`, getter `max_run_ms()`, default `DEFAULT_TASK_MAX_RUN_MS` = 1 hour) from post-completion retention (`with_ttl_ms`, default `DEFAULT_TASK_TTL_MS` = 1 hour). A new task's initial `ttlMs` (counted from `createdAt`) starts at `max_run_ms + ttl_ms` (2 hours by default) and tightens atomically on terminal transition to `(finished_at - created_at) + ttl_ms` (still capped at `expires_at + grace` when `with_ttl_capped_at_token_expiry` is set), so a task that finishes near the end of its run budget keeps its result readable for a full hour after finishing. A task still working when `max_run_ms` elapses is stopped and completes with `TIMEOUT` (`retryable: true` for reads or unstarted tasks, `false` for mutations that started), retained for `ttl_ms` after stopping.
- **`JwksKeySource`, `JwksKeySourceOptions` and `JwksLoader` (`server-auth`; `spec/authorization.md`, M3 rule 3).** The counterpart of TypeScript's `jwksKeySource(load, options)` and Python's `jwks_key_source`: a `KeySource` over the JWKS document a host's `JwksLoader` fetches (any `Fn(&str) -> impl Future<Output = Result<Value, E>>` with a `Display` error, or a type of the host's), so a host no longer writes its own cache. AFD still opens no socket. Per issuer, loaded keys are used for `with_max_age_ms` (default 5 minutes); an unknown `kid` loads again at most once per `with_min_refetch_interval_ms` (default 30 seconds), so a storm of made-up `kid`s costs one load per interval; concurrent callers that need a load share one call of the loader; a failed load (the loader's error or panic, or a document that `StaticKeys::from_jwks` would refuse) keeps the last good keys for up to `with_max_stale_ms` (default 1 hour, at least the maximum age: `JwksKeySource::new` refuses less), and with none, keys older than that, or a failed load for an unknown `kid` the answer is `KeyError::Unavailable`. Unlike TypeScript, the loader is given the issuer and the state is kept per issuer, so one source (clones share it) can serve several issuers; and a load runs while a caller awaits it, resuming with the next caller if every waiting one is dropped. `StaticKeys` now looks keys up by `kid` in a map. `tests/auth_jwks.rs` covers each rule on a manual clock, including concurrent loads and an unknown-`kid` storm.
- **`CommandDefinition::map_handler`.** Replaces a definition's handler with a wrapper of it and keeps every other field, so a host registering a definition built elsewhere can run code around its handler; Umbel puts its compiled-plugin turn and deadline around a plugin's finished definitions this way. TypeScript and Python reach `handler` as a field.
- **`McpServer::with_instances(ServerInstances::Single | Multiple)` and `McpServer::with_confirmation_key` ([#2242](https://github.com/lushly-dev/afd/issues/2242)).** `ServerInstances::Multiple` fails `McpServer::validate()` (and `try_streamable_http_service`, `streamable_http_service`, `authorized_http_service`, and `serve_stdio`) when active confirmations, `ApprovalRelay::McpElicitation`, or in-memory approval nonce stores (including inside `compose_middleware`, and beside `HumanRelay` even under `ApprovalReplay::WithinTtl`) rely on per-process defaults. When `with_instances` is omitted, starting an HTTP service logs one warning per process to stderr (`ServerInstances::Single` silences it; `serve_stdio` logs nothing). `McpServer::with_confirmations` now preserves an already-configured shared key.
- **`CommandError.recovery` ([`spec/recovery.md`](../../spec/recovery.md)).** A failed command can now carry the step its `suggestion` describes in a form a program can follow and a test can check, as `recovery: Option<Box<Recovery>>` (boxed, as `cause` is, so an error without one grows by one pointer), set with `CommandError::with_recovery`. `Recovery` has one variant per kind, each holding only its own fields, so a recovery that puts `command` on a `retry` cannot be built: `Call` (`command`, `input`, `needs`, `then_retry`), `FixInput` (`input`, `needs`), `Retry` (`after_ms`), `External {}` and `Stop {}`. Every variant is `#[non_exhaustive]`, so code outside the crate builds one only through its constructors, `Recovery::call`, `call_with`, `fix_input`, `retry`, `external` and `stop`, and a field added to a kind later breaks no caller; it reads the fields by pattern with `..` (`Recovery::Call { command, .. }`). `call`, `call_with` and `fix_input` return `Result<Recovery, InvalidRecovery>` and refuse what `$defs/recovery` refuses: an empty `command`, an empty `input` or one carrying `confirm`, an empty `needs` or one with an empty or repeated name, and a `fix-input` with neither `input` nor `needs`. A value changed through a `&mut` pattern after it was built is not checked again; `Recovery::validate` checks it. Neither checks rule 3 (`input` and `needs` naming the same field), which the schema does not check either. It serializes as the spec's object (`{"kind": "call", "command": "lane-resume", "thenRetry": true}`, unset fields omitted). Reading follows rule 7: a recovery that breaks `$defs/recovery` (an unknown kind or member, a `null` member, a member of the wrong JSON type or on the wrong kind, an empty `input` or one with `confirm`, an empty, repeated or empty-string `needs`, a `fix-input` that sets neither, a negative or fractional `afterMs`) reads as `recovery: None`, on the error and on its `cause`, and the rest of the error is kept, `suggestion` included. No member is coerced: `"30000"` is not a number and `"true"` not a boolean. `afterMs` reads as JSON Schema reads an integer, so `30000.0` reads as `30000`; an `afterMs` above 2^53 − 1, the schema's maximum and `MAX_AFTER_MS`, is refused however it is written, and `Recovery::retry` refuses one too. The error-level rules tying `retryable` to `retry` and `stop` are not enforced on read. `Recovery::kind` and `RECOVERY_KINDS` name the kinds, and `is_command_recovery(&Value)` says whether a JSON value is a recovery a reader keeps, as TypeScript's `isCommandRecovery` and Python's `is_command_recovery` do. `CommandError` is `#[non_exhaustive]`, so the new field breaks no code outside the crate; a `match` over `Recovery` needs a wildcard arm, since new kinds may be added. A context hook's refusal now passes `recovery` to the caller beside `code`, `message`, `suggestion` and `retryable`. `tests/recovery_vectors.rs` runs the `valid`, `normalizes` and `invalid` lists of `spec/vectors/recovery.json` against `spec/schema/error.json`: each valid error round-trips unchanged, and each normalizing and invalid error reads to exactly its `readsAs`, with every recovery on an error or its cause kept exactly when it passes `$defs/recovery`. The schema validator it shares with `tests/wire_fixtures.rs` now supports `anyOf`, `uniqueItems`, `minItems` and `minProperties` and refuses a schema keyword it does not implement.
- **The engine's own errors carry a recovery ([`spec/recovery.md`](../../spec/recovery.md), "Engine errors").** Each error the registry, the MCP server, the router, the middleware, the confirmation and approval steps, the context commands and `DirectClient` emit now sets the recovery the spec's table gives, and a batch item or pipeline step carries its call's. `COMMAND_NOT_FOUND` at lookup (a call, `afd-call`, a batch item or a pipeline step) is a `call` of `afd-discover` for an MCP caller, of `afd-help` for an in-process caller that can call it, and none otherwise; the suggestion and the recovery come from the one decision, so they always name the same command. A grouped tool's unknown action and `afd-detail`'s per-entry not-found set none. `COMMAND_NOT_EXPOSED`, `CALL_NOT_GRANTED`, `CONFIRMATION_REQUIRED` and `APPROVAL_UNAVAILABLE` (`no-approval-step`, `admission-mismatch`) are `external`; `input-not-canonical` sets none. `COMMAND_NOT_IN_CONTEXT` is a `call` of `afd-context-list` only when the caller can call it (registered, exposed to its interface, in its context, existing for it and in its listing), which now also decides whether the suggestion names it; its "or afd-context-enter to switch" clause appears only when the caller can call `afd-context-enter` by the same test. `afd-context-enter`'s `CONTEXT_NOT_FOUND` is a `call` of `afd-context-list`, and its `CONTEXT_DEPTH_EXCEEDED` a `call` of `afd-context-exit` with `thenRetry`, each only when the server's filters for the caller (which commands exist for it, and its listing) admit that command; otherwise the suggestion leaves the command out ("Available contexts: …", "Leave a context before entering another") and there is no recovery. `CONFIRMATION_DECLINED`, a declined `APPROVAL_REQUIRED` and a `DirectClient` whose `on_approval_needed` hook returns `Ok(false)` are `stop` (a hook that errors or panics keeps the hold's `external`). An `APPROVAL_REQUIRED` the caller reshapes (an `afd-batch` or `afd-pipe` refused up front, a gated step to call on its own, an approver's token sent the wrong way) sets none; every other one is `external`. The rate limiter's `RATE_LIMITED` is a `retry` with `afterMs` the suggestion's whole seconds × 1000, or with no wait when its client capacity is full, and the MCP task limit's is a `retry` with no wait. `rate_limit_error()` and `CommandError::rate_limited()` set `{kind: "retry"}`, with `afterMs` when given the wait; the other helpers set none. Every error keeps its `retryable`. The default server instructions' first sentence now reads "`<name>` is an AFD server. Every tool returns a CommandResult as JSON text: { success, data, error: { code, message, suggestion, recovery } }; follow error.suggestion to recover. When error.recovery is present, it is the same step in a form a program can follow." `tests/dispatch_vectors.rs` and `tests/tool_strategies_vectors.rs` compare each case's `recovery` (`null`: none), and the dispatch registry surface registers the context commands as plain commands (`setup.contextCommands: "plain"`); `tests/app_calls_vectors.rs` already compares the whole refusal.
- **`DirectClient` and pipeline deadlines fire the command's cancellation signal; pipelines stop at a cancelled call ([#1599](https://github.com/lushly-dev/afd/issues/1599)).** A `DirectClient` call with `timeout_ms` gives the command a child of the caller's signal and fires it when the call's deadline passes (both attempts and the approval wait); the caller's own signal is never fired. The caller's signal also ends the approval wait (`COMMAND_CANCELLED`), as in TypeScript. `execute_pipeline_with_cancellation` (`execute_pipeline` delegates to it) skips a step, and every later one, with `COMMAND_CANCELLED` once its signal has fired (`spec/execution-controls.md`), and fires that signal when the pipeline's deadline passes with steps still to run; the MCP server's `afd-pipe` passes a child of the call's signal when there is a deadline, else the call's own.
- **Stream executor, `afd::execute_stream` and `CommandRegistry::execute_stream` ([#1601](https://github.com/lushly-dev/afd/issues/1601)), as TypeScript's `executeStream` behaves:** the command runs once through `CommandRegistry::execute` (every check applies), then a lazy `Stream` yields one data chunk per array item (or one for any other data) and a complete chunk with the result's confidence, reasoning and metadata, or one error chunk for a failure (`recoverable` when retryable). The call's cancellation signal stops it with `STREAM_ABORTED` before execution, after it or before a data chunk (`resumeFrom` in the data phase); `StreamExecutorOptions::timeout_ms` gives the command a child of that signal, fires it at the deadline and ends the stream with `STREAM_TIMEOUT` even if the command ignores it (`0` is a deadline already passed, as in TypeScript; `native` feature, otherwise `UNSUPPORTED_OPTION`). Once the last data chunk is sent, the complete chunk follows. A streamed command's result is not checked against its output budget (`spec/output-budgets.md`, B7), as in TypeScript and C++; the ask is still validated and the handler still sees its budget. Nothing runs until the stream is polled, and dropping it stops the command.
- **`AsyncFileJournalSink` and `FileJournalSink::with_sync_data` ([#1764](https://github.com/lushly-dev/afd/issues/1764)).** `AsyncFileJournalSink` (the `native` and `journal-file` features) runs a `FileJournalSink`'s blocking calls on Tokio's blocking pool, so an append, a read of the whole file and a shared sink's wait for its lock never hold an async worker; a fair async lock keeps appends in the order calls arrived. `with_sync_data(true)` waits for each append to reach the device (`File::sync_data`); without it an append is handed to the OS before it returns, which survives a process crash but not a power loss. `FileJournalSink`'s docs now state this durability policy. `native` enables Tokio's `rt` and `sync` features for it.

### Changed

- **Pre-1.0 breaking:** `DirectApprovalRequest` gains the public field `approval_id`, so code that builds one with a struct literal must set it. `ApprovalRequest` is `#[non_exhaustive]`, so its new field breaks nothing.
- **`getrandom` is a dependency of every build but `wasm32-unknown-unknown`**, where the `wasm` feature now adds it (with its `wasm_js` backend) itself rather than only enabling it for `approval` and `server`. Every call's dispatch id draws from it, so a call on `wasm32-unknown-unknown` without `wasm`, which has no random source, carries no dispatch id. No lockfile changes.
- **Pre-1.0 breaking (behaviour):** `wrap_error` now returns a generic non-retryable `INTERNAL_ERROR` (`"An internal error occurred"`, `retryable: Some(false)`, operator-facing suggestion) instead of forwarding raw `Display` text into an agent-visible message marked retryable.
- **Pre-1.0 breaking (`server` feature, [#2500](https://github.com/lushly-dev/afd/issues/2500)):** `TaskChange::{Completed, Failed, Cancelled}` gain `ttl_ms: Option<u64>`, applied by `TaskRecord::apply` and custom `TaskStore::update` implementations to tighten `ttl_ms` on terminal transition. Custom `TaskStore` implementations and callers constructing `TaskChange` directly must handle or set `ttl_ms` (`None` keeps the existing `ttl_ms`).
- **One compiled input validator, built once at registration ([#1762](https://github.com/lushly-dev/afd/issues/1762)).** Replaced the separate legacy `parameters` validator and raw-`Value` whole-schema walker with a single arena-backed `CompiledSchema` compiled once at registration (`register`, `register_with_schema`, `register_with_schemas`, `set_context_fields`, and MCP meta-tools) and shared in an `Arc`. Legacy `parameters` are converted to whole JSON Schemas (including `JsonSchema::min_length`/`max_length` on arrays mapped to `minItems`/`maxItems`), `pattern` regexes are pre-compiled per node, `format` is treated as an annotation (unblocking `schemars`-generated schemas), and valid inputs move through validation without cloning. Legacy `parameters` now emit the same Zod-style `VALIDATION_ERROR` diagnostics as whole schemas. All 116 `spec/vectors/validation.json` executions (now including `pattern` and `format`, leaving 5 unsupported optional cases) pass. On `cargo bench --bench execute` (50-item payload), `0 middleware` drops from 559 allocations / 42,138 bytes / ~64 µs per call to 6 allocations / 2,125 bytes / ~44 µs per call.

### Fixed

- **Behaviour change: `create_retry_middleware` no longer repeats a mutation** ([#2673](https://github.com/lushly-dev/afd/issues/2673)). It used to retry any command whose failure code was `TRANSIENT_ERROR` or `TIMEOUT`, so a handler that returned `TIMEOUT` after a downstream write could have that write applied twice. A command declared with `as_mutation()` now runs once and its failure is returned. The middleware reads the declaration from the command `CommandRegistry::execute` runs for the call, never from its name; outside the registry it counts the call as a mutation. Set the new `RetryOptions::retry_mutations` (default `false`) to restore the old behaviour, and only when every mutation it wraps is safe to repeat. A `RetryOptions { .. }` literal without `..Default::default()` must add the field.

- **`ServerInstances::Multiple` runtime guard retryability:** the runtime per-process approval-state guard in `CommandRegistry::execute` now returns `retryable: Some(false)` with an operator-facing suggestion instead of `retryable: Some(true)` with `"Please try again."`.
- **`DirectClient` `timeout_ms`** ([#1599](https://github.com/lushly-dev/afd/issues/1599)): `0` is no deadline, as `CommandRegistry::execute` reads it (it timed out at once), and a caller's deadline replaces the registry's `default_timeout_ms` for the call (the default applied too).
- **Journal replay of streamed budgeted calls** ([#2361](https://github.com/lushly-dev/afd/issues/2361)): `replay_journal` now skips the B5 output-budget result check when replaying a successful budgeted entry that carries no B6 `dev.afd/outputBudget` report (buffered `execute_stream`, B7), matching TypeScript and C++ so over-budget streamed calls replay without falsely diverging while normal budgeted calls still run B5.
