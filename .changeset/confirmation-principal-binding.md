Bind the `requestState` of confirmation and approval elicitations to the call's principal ([#532](https://github.com/lushly-dev/afd/issues/532); `spec/command-metadata.md`, "Confirmations"; `spec/authorization.md`, M8). The state was bound to the method and the SDK's `authInfo.clientId`, and a confirmation's answer to its commands and input, so one caller's answered confirmation could confirm the same call for another caller of the same server. It is now also bound to the principal binding: the actor the commands run with (`createContext`'s `actor`, or the server's `actor` option) and, when `createContext` sets `credentials` (`{ issuer, subject, clientId }` of a token the host verified), their issuer, subject and client. The binding is HMAC input only, so the state names no one. A retry from another actor, or with another issuer, subject or client (a different client of the same person included), is "no answer" exactly as an altered state is, and the server asks again; a state minted before this change is asked again too. `credentials` without a non-empty `issuer`, `subject` and `clientId` are never bound: a call that would mint a state, or a retry that carries one, fails with an internal error that names no one, and the SDK's `authInfo` contributes only its `clientId`, so a host that authenticates people through the SDK must copy their identity into `credentials`. New exports: `principalBinding`, `credentialsBinding` and the `PrincipalCredentials` type, checked against the `principalBindings` cases of `spec/authorization.json`.
