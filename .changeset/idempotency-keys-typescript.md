**Idempotency keys: a mutation a caller can safely send twice** ([#2675](https://github.com/lushly-dev/afd/issues/2675), `spec/idempotency.md`). A command declares `idempotency: 'natural'` (a repeat leaves the same state; reported as the MCP annotation `idempotentHint: true`) or `'keyed'` (a repeat with the same key and input is safe), in `_meta.idempotency`, `afd-detail` and `afd-help` (`full`). A caller sends a key in `_meta["dev.afd/idempotencyKey"]`, a meta-tool's `meta` argument, `context.idempotencyKey` in process, DirectClient's and `McpClient`'s `idempotencyKey` call option, or `afd call --idempotency-key`. Every engine validates it (1 to 200 of `A-Z a-z 0-9 . _ ~ -`, else `VALIDATION_ERROR` before confirmation, middleware or handler) and delivers it to the handler; batch items and pipeline steps run under `<key>:<i>` and `<key>:step:<i>`; a command a handler runs through the registry does not inherit it; the journal records it in `idempotencyKey` and replay restores it. `createMcpServer({ idempotency: { store, ttlMs, leaseMs } })` adds the engine's step, between the approval admission check and the handler: a repeat of a `keyed` call with a key is answered from the store with `metadata.idempotentReplay: true`, or refused with the new `IDEMPOTENCY_KEY_REUSED` (another input), `IDEMPOTENCY_IN_PROGRESS` (still running) or `OUTCOME_UNKNOWN` (the first call returned `TIMEOUT`, threw, or outlived its lease), and a `TIMEOUT` on such a call carries `recovery: { kind: 'retry' }`. A server that cannot tell its HTTP callers apart refuses such a call with `UNAUTHORIZED`, anonymous stdio connections never share keys, and `instances: 'multiple'` needs a shared `store`. A direct registry takes a step built with `createIdempotencyStep(options, { clock })`, so a host without one does not bundle it. **Behaviour changes:** the retry middleware now follows the declaration: it repeats a `natural` command, a `keyed` one only when the call carries a key, and any other unless it declares `mutation: true`; `retryMutations: true` still restores retrying everything. `idempotencyKey` is a reserved context name, so declaring a context field of that name now fails at startup, and a `context.idempotencyKey` that host code or `createContext` sets is now validated like a caller's, so a malformed one fails every call with `VALIDATION_ERROR`. A journal entry whose call carried a key hashes it as a member of `contextDigest` instead of listing its name in `keys`, so its hash differs from a recording made before. `afd validate --surface` gains `missing-idempotency`, an info finding for a `mutation: true` command that declares neither value. The three codes join the shared catalog in an `idempotency` profile.
