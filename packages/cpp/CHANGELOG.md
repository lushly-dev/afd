# Changelog

All notable changes to afd-cpp are documented here. The package is versioned independently of the npm packages (proposal D11) and is released with tags of the form `cpp-vX.Y.Z`.

## Unreleased

### Added

- **`error_codes::APPROVAL_UNAVAILABLE`**, which joins the shared catalog (`spec/command-metadata.md`, "Approvals"): a server engine refuses a command whose declared approval policy is not `not-required` when no approval step admitted the call.
- **A declared approval policy holds without the approval middleware** ([#1886](https://github.com/lushly-dev/afd/issues/1886)). `CommandRegistry::execute` gives each call its own admission record (`CommandContext::approval_admission`, replacing any the caller passes) and runs a command whose policy is neither unset nor `not_required` only when an approval step admitted that call on that record, once, for that command and the same canonical validated input. Otherwise it answers `APPROVAL_UNAVAILABLE` (`retryable: false`, `details.reason` `no-approval-step` or `admission-mismatch`) before the handler, without evaluating a policy function. An input `canonical_json` cannot encode is compared by value: the admission keeps a copy, so a call a policy let through runs, and an in-place change after the approval middleware is refused. Taking an admission is one synchronized step, so overlapping `next()` calls run the handler once. Each batch item, pipeline step and nested call is checked on its own, so `DirectClient` and `afd::mcp_stdio` refuse such calls too. `create_approval_middleware` decides from the policy and `confirm_prompt` of the command each call runs, so commands registered after it are covered, and `ApprovalMiddlewareOptions::commands` is optional. `StdioServer::create` refuses an `afd-context-list` that declares an approval policy, since it reads that handler at startup. The C++ todo backend serves its commands without their approval policies when `APPROVALS=off`, as TypeScript's does. The host-visible changes are under "Changed".

- **`error_codes::CALL_NOT_GRANTED`**, which joins the shared catalog with app-to-app calls (`spec/command-metadata.md`, "App-to-app calls"; Loam phase 5 step 0b). C++ does not emit it yet: the `apps` exposure flag and the call check are [#1513](https://github.com/lushly-dev/afd/issues/1513), and `spec/vectors/app-calls.json` lists C++ as a documented gap. Meanwhile `replay_journal` refuses an entry recorded with the `apps` interface before any handler runs, where it would otherwise replay with no surface, as a trusted call.
- **The hybrid tool strategy on `afd::mcp_stdio`** (`spec/tool-strategies.md`, "Hybrid", H1 to H8; [#1202](https://github.com/lushly-dev/afd/issues/1202)). `ToolStrategy::hybrid` with `StdioServerOptions::first_class_tools` lists the five meta-tools, the context tools when contexts are configured, and then up to `max_first_class_tools` (8) command tools in configured order, each the individual strategy's tool. The list is the same in every context, so `ttlMs` keeps 300000 with contexts, and a first-class command outside the active context answers `COMMAND_NOT_IN_CONTEXT`. `create` refuses a set that is missing, empty or given with another strategy, and an entry that is unregistered, not exposed to MCP, a meta-tool or context tool, repeated or beyond the cap, naming it. `server/discover`'s default instructions say the listed command tools are the common ones. `CommandContext::first_class_tools` lets `afd-help` report `firstClassTools` and `firstClass: true`. The tests load `spec/vectors/tool-strategies.json`, which moved there from `spec/` now that all four languages load it.
- **One approval up front for `afd-batch` and `afd-pipe`** (`spec/command-metadata.md`, "One approval up front for `afd-batch` and `afd-pipe`", #459; closes [#1451](https://github.com/lushly-dev/afd/issues/1451)). With `ApprovalRelay::mcp_elicitation`, a batch or pipeline that can elicit is decided by the approval middleware before any step's handler runs: one form question lists every gated step with its summary, command and canonical validated input (a pipeline's `$input` resolved), as `input_required` on 2026-07-28 or in band on 2025. Each approval is bound to the whole request, the command, its input and the actor, every nonce is spent before anything runs, and each gated step runs once on its own approval. A gated pipeline step whose input reads an earlier step (`reads_step_data`, new in `afd/pipeline.hpp`), more than 20 gated steps, or a decline runs nothing, with `details.reason` `input-not-known`, `too-many-approvals` or `declined`. A batch's confirmation and approval share one `requestState`. The approval middleware removes the up-front approval from each step's context, so a command a step runs falls back.
- **Meta-tools and tool strategies on `afd::mcp_stdio`** (`spec/tool-strategies.md`, `spec/meta-tools.json`; part of [#1451](https://github.com/lushly-dev/afd/issues/1451)). `StdioServerOptions::tool_strategy` (`ToolStrategy::individual`, `grouped` or `lazy`) and `group_by` give TypeScript's tool lists, grouped tools with `_meta.actions` and inlined `params.anyOf` included, and `server/discover`'s strategy sentences. `afd-call`, `afd-batch`, `afd-pipe`, `afd-discover` and `afd-detail` are served on every strategy with TypeScript's definitions, and route through the same exposure, context, confirmation and validation checks as a command's own tool: `afd-call` and grouped tools take `confirm: true`, and `afd-batch` and `afd-pipe` take a `confirm` array and ask once, before any step runs, for every gated step, on 2026-07-28 and in band on 2025. A meta-tool's `meta` argument carries `dev.afd/context`. `CommandContext::remote`, which the server sets, makes the registry answer a command not exposed to the surface exactly as an unknown one (D4), with a suggestion naming `afd-discover`; `not_found_suggestion` is public. `CommandContext::tool_strategy` lets `afd-help` report `toolStrategy`. The C++ todo backend lists TypeScript's grouped tools.
- **Bootstrap commands** (`spec/tool-strategies.md`, "Terms"; part of [#1451](https://github.com/lushly-dev/afd/issues/1451)). `afd/bootstrap.hpp` adds `register_bootstrap_commands`, `bootstrap_commands` and `generate_input_types`. `afd-help`, `afd-docs` and `afd-schema` (category `bootstrap`, tagged `bootstrap`, `read` and `safe`, exposed to MCP) describe the commands exposed to MCP in the call's active context, themselves among them, as TypeScript's do: `afd-help` with `contractVersion`, `requires`, the full format's fields and the declared context fields; `afd-docs` as markdown by category with a parameter table from the input schema; and `afd-schema` as JSON Schema, or with `format: "typescript"` one module of input types, TypeScript's generator ported. Registering refuses a bootstrap name already taken. With all three registered, `afd::mcp_stdio`'s default `server/discover` instructions add "afd-help, afd-docs and afd-schema describe this server.", and the registry's unknown-command suggestion points to `afd-help`. The C++ todo backend registers them, as TypeScript's `bootstrap: true` does.
- **Contexts on `afd::mcp_stdio`** (`spec/tool-strategies.md`, "Contexts"; [#1425](https://github.com/lushly-dev/afd/issues/1425)). `afd/contexts.hpp` adds `ContextConfig`, `ContextStack`, `ContextScope`, `context_commands` and `register_context_commands`, which registers `afd-context-list`, `afd-context-enter` and `afd-context-exit` (category `bootstrap`, exposed to MCP) with Rust's results and errors (`CONTEXT_NOT_FOUND`, `CONTEXT_DEPTH_EXCEEDED`, `SESSION_REQUIRED` in process). `StdioServerOptions::contexts` serves them: a 2025 connection keeps one context stack, a 2026-07-28 request names its context in `_meta["dev.afd/context"]` (an unknown one is `-32602`), `tools/list` is filtered by the active context, and a confirm-gated command outside it is refused before anyone is asked. `StdioServerOptions::tools_list_ttl_ms` sets `ttlMs`, which defaults to 0 with contexts; `server/discover`'s default instructions add the contexts sentence. `create` refuses contexts that are blank, repeated or not those the context commands were registered with. `CommandContext::context_scope` carries the scope (only the server sets it); when it is set, the registry runs the call in its active context. `RequestInfo::active_context` shows the context hook the active context, which the hook cannot change. `server/discover`'s default first sentence now names the CommandResult fields, as the spec words it. `COMMAND_NOT_IN_CONTEXT` now names the context tools when the caller can call them. The C++ todo backend serves TypeScript's two contexts.

- **`structuredContent` and the top-level `outputSchema`** (`spec/command-metadata.md`, "Structured results"; [#465](https://github.com/lushly-dev/afd/issues/465)): every `afd::mcp_stdio` tool result carries the CommandResult as `structuredContent`, beside the same JSON as text, and a command with an `output_schema` advertises the CommandResult envelope as its top-level `outputSchema`. `StdioServerOptions::advertise_output_schema = false` switches the schema off. `afd/mcp.hpp` adds `command_result_output_schema`, which drops `$schema` and moves `$defs` and `definitions` to the envelope unless `data` has its own `$id`, in which case both stay with `data` so local references still resolve ([#1474](https://github.com/lushly-dev/afd/issues/1474)). The schema is on by default, so a handler whose `data` does not match its `output_schema` now fails on MCP clients that validate `structuredContent`.
- **The MCP stdio server: `afd::mcp_stdio` (#341).** An opt-in target, `AFD_BUILD_MCP_STDIO`, off by default, which needs `AFD_ENABLE_THREADS`; `afd::afd` stays transport-free. `afd/mcp_stdio.hpp` adds `afd::mcp::StdioServer`.
  - **Protocol.** Both MCP eras on one stdio connection: 2026-07-28 requests served from their `_meta` (`server/discover`, `resultType`, cache hints, `-32022`), and 2025 `initialize` and `ping`. It serves `tools/list` and `tools/call`, one tool per command exposed to MCP.
  - **Cancellation.** `notifications/cancelled` cancels a call through `CommandContext::cancellation`, including one still queued.
  - **Context.** `StdioServerOptions::context_hook` refines each call's context.
  - **Confirmations** (`StdioServerOptions::confirmations`: `off`, `enforce` or `require_human`; `spec/command-metadata.md`, "Confirmations"). The person is asked with a form elicitation: in band on a 2025 connection, as `input_required` on 2026-07-28. That request's `requestState` is HMAC-signed, expires after 10 minutes, and is bound to the command, its input and the actor. Under `enforce`, `confirm: true` or `_meta["dev.afd/confirm"]` also acknowledges.
  - **Approval relay.** `ApprovalMiddlewareOptions::relay = ApprovalRelay::mcp_elicitation` asks the person behind the client in the same way, with no token for the agent (`spec/command-metadata.md`, "Asking the human over MCP"). One state carries a confirmation's answer and then an approval's. Only the command the tool call routes to can ask, once. A declined approval fails with `APPROVAL_REQUIRED` and `details.reason: "declined"`.
  - **Tests and packaging.** `examples/mcp_stdio_server.cpp` is a complete server, built and self-tested with the examples and by the package consumers. The C++ todo backend now runs on this target, and its own loop is gone. It reads `CONFIRMATIONS` and passes the confirmation suite in both eras.
- **Commands as MCP tools (#341).** `afd/mcp.hpp` adds `command_to_mcp_tool`, `commands_to_mcp_tools`, `is_mcp_exposed`, `command_tool_meta`, `command_tool_annotations`, `execution_time_name` and `to_json` for `CommandDefinition` (afd-detail's shape). Tools carry the per-command `_meta`: `category`, `requires`, `mutation`, `destructive`, `undoable`, `approval`, `examples`, `outputSchema` and `contexts`, each only when set.

- `afd::error_codes::TASK_TOKEN_EXPIRED`, the shared catalog's 48th code (`spec/error-codes.md`, `spec/vectors/error-codes.json`), specified by `spec/command-metadata.md` ("Tasks") and emitted by the Rust server's task runner first (Umbel phase 5 step 0e). `afd::mcp_stdio` has no tasks, so C++ never emits it; the constant keeps the catalog whole.
- `afd::error_codes::INSUFFICIENT_SCOPE`, the shared catalog's 47th code (`spec/error-codes.md`, `spec/vectors/error-codes.json`), specified by `spec/authorization.md` (M6) and emitted by the Rust server first (Umbel phase 5 step 0b). C++ has no HTTP server, so it never emits it; the constant keeps the catalog whole.
- `afd::error_codes::OUTPUT_BUDGET_EXCEEDED`, the shared catalog's 46th code (`spec/error-codes.md`, `spec/vectors/error-codes.json`), specified by `spec/output-budgets.md` and emitted by the Rust engine first. C++ does not implement output budgets yet; the parity matrix tracks it.

- An optional `CommandDefinition::title`, a short display label, matching TypeScript (#466; `spec/command-metadata.md`, "Tool titles"). Declared after `description`, so existing designated initializers still compile. The todo backend's `tools/list` sends it as the tool's top-level `title` only when set; nothing is derived from the name, and it is never put in `annotations` or `_meta`. afd-cpp has no MCP server or afd-detail/afd-help describers, so nothing else reports it.
- Declared context fields and their journal support, matching TypeScript (`spec/context-fields.md`, `spec/journal.md` "Declared context fields"). `afd/context_fields.hpp` adds `ContextField` (`name`, `meta`, `schema`, `journal`, `required`), declared in `CommandRegistryOptions::context_fields`. `CommandRegistry::create` returns an `Expected` that names the field with an empty, reserved or repeated name, a `meta` key without a reverse-DNS prefix, with a reserved prefix or repeated, or an unsupported schema; a registry constructed directly with such a declaration fails every call with INTERNAL_ERROR. Each call's value in `context.extra[name]` is validated after the input and before middleware, and replaced with the schema's output; an invalid or missing required value fails with VALIDATION_ERROR naming the field and its `meta` key. A JSON `null` counts as no value (not validated or journaled), and `required` is not enforced for commands named `afd-*`, so a client can discover the fields first. `JournalRecord` gains `context` and `context_omitted` (written after `contextDigest`); the journal middleware keeps each journaled value up to 4096 bytes of canonical JSON, learning the journaled names from the registry through the internal `CommandContext::journaled_fields`. `create_context_digest` takes the kept values and omitted names, which then enter the hash and leave the key list; an entry with neither hashes as before. `replay_journal` restores the values and notes a field the target no longer declares (`ReplayJournalOptions::context_fields`, filled from the registry) and each omitted one. `CommandRegistry::context_fields()` returns the declarations. The tests record, round-trip and replay the six-line `spec/wire/journal.jsonl`.
- Add `DirectClientOptions::on_approval_needed` with a private per-call exchange (#460). Public call/pipe evidence is ignored and held results stay token-free; one approved retry still verifies binding, expiry and nonce. Synchronous hooks cooperate with cancellation and cannot retry after a deadline. Trusted registry execution retains its token API.

### Changed

- **Approval policies are enforced by the registry** ([#1886](https://github.com/lushly-dev/afd/issues/1886)); hosts that relied on the old behaviour need to change:
  - A registry without the approval middleware refuses a command whose policy is not `not_required` (`APPROVAL_UNAVAILABLE`): add the middleware, or register the command without its policy.
  - A command missing from `ApprovalMiddlewareOptions::commands` is now held by its own policy.
  - A retry placed after the approval middleware is refused (`admission-mismatch`): middleware that retries or changes the input goes before it. This holds for a command gated only by the middleware's `commands` list too: the middleware marks the call, also when middleware before it calls it under another name, and the registry takes its admission at dispatch.
  - The approval middleware admits only a call one of its own policies (the command's, or its `commands` entry's) may gate, and every approval middleware that ever admitted a call must admit it afresh and match at dispatch, so a second approval middleware that does not gate a command neither re-admits a retry nor replaces the first one's binding. One approval middleware per registry is the supported setup.
  - With form elicitation available, `afd::mcp_stdio` plans every `afd-batch` and `afd-pipe` up front, so a step gated only by the `commands` list is approved before any step runs; a call with no step any policy may gate runs as before.
  - The approval summary prefers the `confirm_prompt` of the command the registry runs over the `commands` entry's.
  - Replaying a journal of gated commands needs the approval middleware on the replay registry, or the policies removed there.
  - Passing the registry's own definitions in `commands` is now redundant, and a function policy given both ways may be evaluated twice.
  - A call the approval middleware would hold whose input `canonical_json` cannot encode, such as an integer beyond 2^53 − 1, is answered `APPROVAL_UNAVAILABLE` (`retryable: false`, `details.reason` `input-not-canonical`, nobody asked) instead of `COMMAND_EXECUTION_ERROR`, for a single call and for an up-front `afd-batch` or `afd-pipe` step. A call whose policy lets it through still runs.
  - `StdioServer::create` refuses contexts whose `afd-context-list` declares an approval policy.
  - `CommandContext` gained a field (`approval_admission`), so binary consumers rebuild against matching headers and library.
- **Tool lists (`spec/tool-strategies.md`, #533):** every `afd::mcp_stdio` strategy lists the five meta-tools first, in the hybrid order `afd-discover`, `afd-detail`, `afd-call`, `afd-batch`, `afd-pipe`; `lazy` adds only the context tools when contexts are configured, the same in every context, and keeps the default `ttlMs` with contexts.
- **`afd::mcp_stdio` lists grouped tools by default**, as TypeScript and Rust do: set `tool_strategy = ToolStrategy::individual` for one tool per command (after the five meta-tools). Calls by command name work in every strategy. Over MCP, a command not exposed to it now answers `COMMAND_NOT_FOUND` instead of `COMMAND_NOT_EXPOSED`, and the unknown-command suggestion ends "Use afd-discover to list all commands."
- `ApprovalMiddlewareOptions::include_token` is now a `std::optional<bool>`. Left unset, it includes `details.approvalToken` except on calls whose `context.surface` is MCP, as TypeScript does (`spec/command-metadata.md`, "Approvals", rule 6). An MCP agent therefore never holds the token, and the host gets it through `on_approval_required`. Over MCP, a held call's suggestion now says how the client can be asked: call the command on its own, or from a client that supports form elicitation. Set `include_token = true` to keep the old behaviour.

### Fixed

- **A `$ref` inside a subschema with its own `$id` resolves against that subschema** ([#1700](https://github.com/lushly-dev/afd/issues/1700); `spec/validation.md`, "Annotations"): `CompiledSchema` read `$id` as an annotation only and resolved every local `$ref` against the root, so a schema whose nested `$id` subschema holds its own `$defs`, such as a structured-result envelope's `data` schema, was refused at compile time. A string `$id` now starts a schema resource, as in Draft 2020-12. A bare fragment such as `"#node"`, which draft-07 used as an anchor, starts no resource. Compile checks a referenced definition once per target rather than once per reference text, so each resource's definition is checked. The `$id` value is never resolved as a URI.
- **Safe `RandomSource::next()` scaling and journal tape bounds** ([#1716](https://github.com/lushly-dev/afd/issues/1716)): `SystemRandom::next()` now scales 53-bit integers directly into `[0.0, 1.0)` (avoiding LWG 2524), `RecordingRandom::next()` and `TapeRandom::next()` clamp values into `[0, 1)`, `parse_journal` and `FileJournalSink::append()` reject `tape.random` entries outside `[0, 1)`, and `random_uuid`, `DirectClient` trace IDs, and pipeline trace suffixes clamp/bound samples before indexing or casting.
- **`FileJournalSink::append()` validates entries before preparing disk and defers `last_seq_` updates until flush succeeds** ([#1717](https://github.com/lushly-dev/afd/issues/1717)): `parse_bounded()` and `JournalEntry::from_json()` run before `resize_file`/`create_directories`/write, and `last_seq_` advances only after `flush()` succeeds, preventing permanent JSONL corruption when an initial append fails on an unterminated journal.
- **`StdioServer::serve()` guards its reader thread with an RAII joiner and catches callback/stream exceptions** under `AFD_HAS_EXCEPTIONS` ([#1718](https://github.com/lushly-dev/afd/issues/1718)): `context_hook` and `group_by` exceptions return JSON-RPC `-32603` instead of calling `std::terminate()`, and `StdioServerOptions::on_shutdown` lets a host unblock a blocking input stream when `serve()` exits early on output failure.
- **`CompiledSchema::validate()` bounds runtime recursion to 128 levels** (`too_deep`) and avoids copying remaining subtrees on error paths, preventing stack overflow on deeply nested inputs against self-recursive `$ref` schemas ([#1719](https://github.com/lushly-dev/afd/issues/1719)).
- The journal measures an integer beyond 2^53 − 1 in a declared context field's value as the double JavaScript reads it as (`99999999999999999` as `100000000000000000`), as TypeScript does, instead of as written, so a value within a byte of the 4096-byte cap is kept or omitted as in the other languages (#578). `canonical_json` still refuses such an integer for an approval. `tests/journal_context_cap_vectors_test.cpp` loads the new `spec/vectors/journal-context-cap.json`.

## [0.2.0] - 2026-10-27

Implements AFD contract `1.0-rc`.

### Added

- Approval policy and approval middleware, matching TypeScript (#272, #422; `spec/command-metadata.md`, "Approvals"). `CommandDefinition::approval` takes an `ApprovalDecision` (`required`, `not_required`) or an `ApprovalPolicyFunction` of the validated input and context; `approval_mode` and `approval_mode_name` report it (`conditional` for a function), and the todo backend's `tools/list` sends it as `_meta.approval`. `afd/approval.hpp` adds `create_approval_middleware`, which returns `APPROVAL_REQUIRED` before the handler with `details.approvalToken`, `expiresAt`, `summary` and, for a rejected token, `reason` (`ApprovalRejection`). Tokens are `afdap1.<payload>.<mac>`, byte for byte TypeScript's, so a token issued by one verifies on the other with the same secret: HMAC-SHA256 with an app-supplied secret (no default, at least 32 bytes, several for rotation), constant-time comparison, single-use by default (`ApprovalReplay::within_ttl`, `ApprovalNonceStore`), expiry from the middleware's own clock. Also `canonical_json` (keys in UTF-16 order, numbers as JavaScript writes them; refuses an integer beyond 2^53 − 1 unless it is spelled as JavaScript writes its double (so `2^53 + 1` and `2^60` are refused, `1e18` is accepted), non-finite numbers and invalid UTF-8 rather than risk two inputs sharing a digest), `ApprovalCommand`, `ApprovalRequest`, `summarize`, `include_token`, `on_approval_required` and `random_bytes`. `CommandContext` gains `approval`, the evidence a trusted surface sets; the journal names it in the context digest, never its value. HMAC-SHA256 is self-contained on the existing SHA-256 and checked against RFC 4231; a new `afd_fuzz_approval` target fuzzes token verification and the `canonical_json` round trip.
- Command journal and replay, matching TypeScript (#273, #427; `spec/journal.md`). `afd/journal.hpp` has `JournalEntry`, `JournalRecord`, `JournalTape`, `JournalContextDigest`, `JournalRange`, the `JournalSink` interface and a thread-safe `MemoryJournalSink`; `create_context_digest` (SHA-256 over the actor, the surface, the trace ID and the names of the other context members, never their values; the same hash as TypeScript for the same context), `journal_actor`, `is_journal_entry`, `JournalEntry::from_json`, `serialize_journal_entry`, `serialize_journal` and `parse_journal` (JSON Lines through `parse_bounded`, errors name the line). `create_journal_middleware` records each call after validation with its clock and random tape (`record_failures`, `filter`, which skips `auth-*` by default, `redact`, `max_tape_reads`, `on_error`). `replay_journal` re-executes entries through a `CommandRegistry` or any `CommandExecutor`, restoring the trace ID, actor, surface and tape, and reports `same`, `different` (path, kind, both values) or `error` with notes on tape over- and under-runs. `FileJournalSink` is in the optional `afd/journal_file.hpp` (`AFD_JOURNAL_FILE`, ON by default). `CommandContext` gains `journal`, internal state the middleware and replay share; leave it unset. `spec/wire/journal.jsonl` is recorded, round-tripped and replayed in the tests, and a new `afd_fuzz_journal` target fuzzes `parse_journal`.
- Clock, random and actor on `CommandContext`, matching TypeScript (#271, #274, #402). `context.clock` and `context.random` are filled from `CommandRegistryOptions::clock` and `random` when the caller set none, and the registry times handlers with `context.clock`. `context.actor` (`Actor`, `ActorKind`, `actor_kinds`, `is_actor`, `is_actor_kind`, `parse_actor_kind`, `actor_kind_name`) says who is calling; `DirectClient` fills `human` (option `actor`; its `clock` and `random` options, when set, also reach the context), `CommandRegistryOptions::actor` sets a default, and the registry stamps the kind, never the id, as the typed `ResultMetadata::actor_kind` (`metadata.actorKind` on the wire; an unknown kind stays in `extra`). Also `ContextDefaults` and `with_context_defaults`, `fixed_clock(ms)`, `ManualClock::set(ms)`, `RandomSource::seed()` and `SystemRandom`. The todo backend's stdio loop calls as `agent`.
- `error_codes::CONFIRMATION_REQUIRED` and `error_codes::CONFIRMATION_DECLINED`, for servers that enforce `confirm_prompt` (`spec/command-metadata.md`, "Confirmations"). Nothing emits them yet.
- `error_codes::APPROVAL_REQUIRED`, for an approval middleware that holds a call before the handler runs (`spec/command-metadata.md`, "Approvals"). `create_approval_middleware` emits it (#422).
- `afd_benchmarks` (behind `AFD_BUILD_BENCHMARKS`, OFF by default) replaces the dispatch-only benchmark and covers `execute` with and without `default_middleware()`, validation against 3, 20 and 100 property schemas, `DirectClient::call`, `execute_batch` and `execute_pipeline` at N = 1, 10 and 100, `get` and `list` on 1,000 commands, and `parse_bounded` and result serialization at 1 KB and 100 KB. CI runs it on the release preset and under Node (Emscripten) and uploads the numbers; there are no thresholds (#340).
- `afd_benchmarks` also has `json_parse/1KB` and `/100KB`, plain `Json::parse` of the same text, as the reference for `parse_bounded`.

### Changed

- **Breaking:** `SeededRandom` is now mulberry32 seeded with the FNV-1a hash of a string, `SeededRandom("seed")`, and gives the same sequence as TypeScript's `seededRandom("seed")`. The `std::uint64_t` and default constructors are gone (a numeric seed no longer compiles): use `SeededRandom(std::to_string(n))` for a numbered seed, and `SystemRandom` (the former randomly seeded `std::mt19937_64`) for real randomness. Library defaults now use `SystemRandom`.

### Fixed

- `parse_bounded` is linear in input size. It enforced the depth limit with a nlohmann parser callback, and the callback parser rescans the enclosing container after every object, so an array of N objects cost O(N²); 100 KB took about 6 to 9 times as long as plain `nlohmann::json::parse`. It now builds the document from SAX events and stops at the first container over the limit, and costs about the same as `Json::parse` (within 10 percent at 100 KB). Results are unchanged: the outermost container is level 1, and the input is reported too deep or malformed by whichever comes first (#397).

### Documentation

- The `asan` preset is documented as unsupported on macOS, where it hangs at startup; use the Linux CI sanitizer job (#331).

## [0.1.0] - 2026-10-12

### Changed

- Renamed to match TypeScript: `Handler` → `CommandHandler`, `Middleware` → `CommandMiddleware`, `RegistryOptions` → `CommandRegistryOptions`.
- Error suggestions name only tools the host provides (`spec/error-codes.md`, D4). An unknown command's suggestion ends with "Use afd-help to list all commands." when the caller can call `afd-help`, otherwise "Check the command name against the available commands.", instead of naming `afd-discover`. `COMMAND_NOT_IN_CONTEXT` names the contexts the command belongs to instead of the `afd-context-*` tools.

### Fixed

- CMake now rejects cl.exe older than MSVC 19.30 with a clear Visual Studio 2022 requirement while
  allowing clang-cl to use the Microsoft frontend with older Visual Studio headers. Configure tests
  cover the compiler floor and the warning sets selected for MSVC, clang-cl and Clang.
- Clang 21 and newer receive the designated-initializer warning suppression under both the GNU and
  Microsoft frontends, so `AFD_WARNINGS_AS_ERRORS=ON` works with clang-cl. Windows CI now builds and
  tests with both MSVC and a checksum-verified official LLVM 22.1.8 clang-cl installation, and CMake
  rejects the regression job unless it detects that exact Clang version with the MSVC frontend.
- Missing required boolean-true and untyped properties reject with `invalid_type` / `nonoptional`, including reference targets; presence, explicit null and defaults keep their schema behavior. An expired batch deadline takes precedence over cancellation when assigning unstarted results after inflight work drains.

- Schema string and array length bounds compare without narrowing huge JSON numbers into `size_t`; nonfinite bounds fail compilation. Pipeline reference indices must fit both JavaScript's safe-integer range and the host's index range, including wasm32.
- `ThreadTaskRunner` joins started workers during thread-start failure and captures task exceptions for rethrow on the caller after all tasks finish. No-exception builds retain their supported behavior.
- Successful registry dispatch only looks up its command; suggestion candidate lists are built on lookup and exposure failures.
- Shared validation vectors now cover all supported cases and explicit rejection of unsupported optional keywords. Missing required values use their full schema's enum and union errors, integer type errors distinguish numbers from other inputs, nullable type lists report the non-null type, and validation reports every issue without a fixed cap. Field lists and sibling issues follow the contract's duplicate-preserving multiset comparison.
- Caller cancellation stops queued batch commands and pipeline steps with COMMAND_CANCELLED while preserving outcomes of handlers already running.

- `DirectClient::call` with `timeout_ms` no longer drops the caller's cancellation token. The call's deadline token now chains to it, as batch and pipeline execution do and as TypeScript does with `AbortSignal.any`. Cancelling the caller, or a `DirectClient::pipe` step passing the pipeline's deadline, now reaches the handler. Only the call's own deadline produces TIMEOUT.
