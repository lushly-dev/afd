# @lushly-dev/afd-testing

## 3.0.0

### Major Changes

- [#2645](https://github.com/lushly-dev/afd/pull/2645) [`f01f103`](https://github.com/lushly-dev/afd/commit/f01f1033dd68f240aea655705f5e0d5fd9c76543) Thanks [@Falkicon](https://github.com/Falkicon)! - `zod` is now a peer dependency (`^4.6.6`) of `@lushly-dev/afd-server`, `@lushly-dev/afd-testing` and `@lushly-dev/afd-view-state` instead of a dependency, so an application's command schemas and the server use one copy of Zod. With two copies the schemas still validated, but TypeScript can reject an application's schema passed to `defineCommand`, because the two copies' types do not unify. `@lushly-dev/afd-cli` now depends on `zod` itself, since it runs the server, and `@lushly-dev/afd-auth`'s optional `zod` peer rises from `^4.0.0` to `^4.6.6` to match the server it runs on. Shape detection for a `VALIDATION_ERROR`'s `expectedFields`, `unexpectedFields` and `missingFields`, and `isObjectSchema()`, now read a schema's `_zod.def.type` instead of using `instanceof` against afd-server's own Zod classes, so they do not depend on which copy of Zod built the schema.

  This is a breaking install change, so it is a major. npm 7 or later, pnpm and Bun install a missing peer themselves, but these applications need a change:

  - One that depends on a `zod` outside `^4.6.6`, such as 3.25 (whose `zod/v4` entry it may have used for its commands): npm stops with `ERESOLVE` where it used to nest a second copy, and pnpm warns and then links the server to that `zod`, which it cannot run on. Upgrade the application to `zod@^4.6.6`.
  - One that never depended on `zod`, for example one that uses only `@lushly-dev/afd-view-state` or `@lushly-dev/afd-testing`, where peers are not installed automatically (Yarn, npm's `legacy-peer-deps`, or pnpm with `auto-install-peers=false`): the install warns, and the server may fail to import `zod` or find another package's copy. Add `zod@^4.6.6` to its dependencies.

### Minor Changes

- [#2864](https://github.com/lushly-dev/afd/pull/2864) [`b96288b`](https://github.com/lushly-dev/afd/commit/b96288b7e861937029f14f295c6c1484e51ee0e7) Thanks [@Falkicon](https://github.com/Falkicon)! - **Idempotency keys: a mutation a caller can safely send twice** ([#2675](https://github.com/lushly-dev/afd/issues/2675), `spec/idempotency.md`). A command declares `idempotency: 'natural'` (a repeat leaves the same state; reported as the MCP annotation `idempotentHint: true`) or `'keyed'` (a repeat with the same key and input is safe), in `_meta.idempotency`, `afd-detail` and `afd-help` (`full`). A caller sends a key in `_meta["dev.afd/idempotencyKey"]`, a meta-tool's `meta` argument, `context.idempotencyKey` in process, DirectClient's and `McpClient`'s `idempotencyKey` call option, or `afd call --idempotency-key`. Every engine validates it (1 to 200 of `A-Z a-z 0-9 . _ ~ -`, else `VALIDATION_ERROR` before confirmation, middleware or handler) and delivers it to the handler; batch items and pipeline steps run under `<key>:<i>` and `<key>:step:<i>`; a command a handler runs through the registry does not inherit it; the journal records it in `idempotencyKey` and replay restores it. `createMcpServer({ idempotency: { store, ttlMs, leaseMs } })` adds the engine's step, between the approval admission check and the handler: a repeat of a `keyed` call with a key is answered from the store with `metadata.idempotentReplay: true`, or refused with the new `IDEMPOTENCY_KEY_REUSED` (another input), `IDEMPOTENCY_IN_PROGRESS` (still running) or `OUTCOME_UNKNOWN` (the first call returned `TIMEOUT`, threw, or outlived its lease), and a `TIMEOUT` on such a call carries `recovery: { kind: 'retry' }`. A server that cannot tell its HTTP callers apart refuses such a call with `UNAUTHORIZED`, anonymous stdio connections never share keys, and `instances: 'multiple'` needs a shared `store`. A direct registry takes a step built with `createIdempotencyStep(options, { clock })`, so a host without one does not bundle it. **Behaviour changes:** the retry middleware now follows the declaration: it repeats a `natural` command, a `keyed` one only when the call carries a key, and any other unless it declares `mutation: true`; `retryMutations: true` still restores retrying everything. `idempotencyKey` is a reserved context name, so declaring a context field of that name now fails at startup, and a `context.idempotencyKey` that host code or `createContext` sets is now validated like a caller's, so a malformed one fails every call with `VALIDATION_ERROR`. A journal entry whose call carried a key hashes it as a member of `contextDigest` instead of listing its name in `keys`, so its hash differs from a recording made before. `afd validate --surface` gains `missing-idempotency`, an info finding for a `mutation: true` command that declares neither value. The three codes join the shared catalog in an `idempotency` profile.

- [#2476](https://github.com/lushly-dev/afd/pull/2476) [`0dc9bde`](https://github.com/lushly-dev/afd/commit/0dc9bde2e8da5670ce24b5b8f87d00a5a636f68f) Thanks [@Falkicon](https://github.com/Falkicon)! - Scenarios can check a refusal's structured recovery (`spec/recovery.md`). `expect.error.recovery` asserts its fields like `data`, and `follow` on a refused step takes the step the recovery describes (`call`, with `thenRetry` repeating the refused call; `fix-input`; `retry`) and fails unless it gets further: a followed call that comes back with the same refusal fails whatever the scenario expects, and a recovery with nothing a program can follow fails too. Each follow call's result is on the step result's `follow`. `follow.input` gives only the fields the recovery `needs`, so a scenario cannot correct a wrong recovery, and it takes step references; a recovery that names a field in both `input` and `needs` fails the step, and `expect.error.recovery` fails on a recovery no reader keeps. `validateScenario` checks `follow` in scenarios built in code, and `FollowExpectation` is exported. `@lushly-dev/afd-core/errors` is a new browser-safe entry for `CommandError`, `Recovery`, `isCommandRecovery` and the error helpers.

- [#2641](https://github.com/lushly-dev/afd/pull/2641) [`cae3ac1`](https://github.com/lushly-dev/afd/commit/cae3ac179a4ba563024f90dfb29f55748677041d) Thanks [@Falkicon](https://github.com/Falkicon)! - `afd validate --surface` now checks a server's skill catalog against Claude Code's limits when the server declares `io.modelcontextprotocol/skills`. It warns about a catalog of more than 100 skills, which Claude Code applies to every server, and, for the skills Claude Code scans (claude.ai Directory connectors and connectors with organization scanning), about a text file over 100 KB, a skill whose text files total over 400 KB, and a skill it would not load because it holds an archive, another binary file (such as WebP or OTF) or text under `dist/`. Each warning names the skill, the limit and Claude Code. Images, fonts, media and dependency lock files are not counted, and a KB is taken as 1,000 bytes. The check follows `skills/list` pages, counts dynamic skills toward the 100, and reports an entry or file it could not read as not checked; that, too, is a warning. The findings never fail the run unless `--strict` is set, and `--suppress <rule>` or `--suppress <rule>:<skill>` turns one off. `@lushly-dev/afd-testing` exports the check as `checkClaudeCodeSkillLimits`, with `CLAUDE_CODE_SKILL_LIMITS`. `McpClient.request` over `streamable-http` now forwards `skills/list` and `skills/get` instead of answering that the transport does not support them.

## 2.2.0

### Minor Changes

- [#406](https://github.com/lushly-dev/afd/pull/406) [`9b79b8e`](https://github.com/lushly-dev/afd/commit/9b79b8eac07b10080a0f3b411e79ffffc56219cd) Thanks [@Falkicon](https://github.com/Falkicon)! - Add standard `actor`, `clock` and `random` fields to `CommandContext` ([#271](https://github.com/lushly-dev/afd/issues/271), [#274](https://github.com/lushly-dev/afd/issues/274)).

  - **Core:** `Actor` (`kind`: `human`, `agent`, `service`, `script` or `test`, with optional `id`, `label` and `onBehalfOf`), `Clock`, `RandomSource`, `systemClock`, `systemRandom`, `fixedClock()` (a manual clock with `set` and `advance`), `seededRandom()` (reproducible, not cryptographic) and `withContextDefaults()`. `ResultMetadata` and `TelemetryEvent` gain `actorKind`. The core registry gives handlers a clock and a random source.
  - **Server:** new `clock`, `random` and `actor` options. MCP calls run as `{ kind: 'agent' }` unless the option or `createContext` says otherwise; every context gets a clock and a random source; results carry `metadata.actorKind` (the kind only, never the id). `executionTimeMs`, the telemetry middleware and HTTP session expiry use the clock. `createDirectRegistry()` accepts the same three defaults.
  - **Client:** `DirectClient` accepts `actor` (default `{ kind: 'human' }`), `clock` and `random` (default: the registry's own); a call's own context wins.
  - **Auth:** `createAuthMiddleware` fills `context.actor` from the verified session: a human actor gets the user's `id` and `label`, other actors get `onBehalfOf`.
  - **Testing:** `createTestContext()` sets `actor: { kind: 'test' }`, a clock and a random source (`now` stops the clock); `InProcessExecutor` takes a `context` for every step and runs steps as a test actor. `fixedClock` and `seededRandom` are re-exported.

  The golden wire fixtures now include `"actorKind": "agent"` in result metadata.

  The server engine, `createDirectRegistry()` and the core registry now pass handlers a copy of the caller's context (with the defaults filled in), so changes middleware or handlers make to it no longer show on the caller's object. The CLI talks to servers over MCP, so its calls run as `agent` unless the server's `actor` option or `createContext` says otherwise; the same holds for `ScenarioExecutor`, which runs steps through the CLI.

- [#392](https://github.com/lushly-dev/afd/pull/392) [`cf7fc58`](https://github.com/lushly-dev/afd/commit/cf7fc58dddd8b7005b50cd3a038e49849351eb63) Thanks [@Falkicon](https://github.com/Falkicon)! - Talk MCP 2026-07-28 from the client, CLI and testing tools.

  - `@lushly-dev/afd-client`: new `streamable-http` transport, built on the official MCP TypeScript SDK v2 client. It speaks MCP 2026-07-28 when the server offers it and falls back to the 2025 `initialize` handshake, so `McpClient` now talks to an AFD server's `/mcp` endpoint, the Python and Rust AFD servers, and any official MCP SDK server. It is the default for URLs that do not end in `/sse`; `protocolMode: 'auto' | 'legacy' | 'modern'` controls negotiation. `stream()` on a `/mcp` URL uses the sibling `/stream` path. The `sse` and `http` transports are deprecated and removed in 3.0.
  - `@lushly-dev/afd-cli`: `--transport` accepts `streamable-http`, and `connect`, `call --connect`, `shell` and `scenario run` infer the transport from the URL (`sse` for `/sse`, `http` for `/message`, `streamable-http` otherwise) instead of defaulting to `sse` or `http`.

### Minor Changes

- [#251](https://github.com/lushly-dev/afd/pull/251) [`f820855`](https://github.com/lushly-dev/afd/commit/f820855cb098e83cf311a8b2e361e4ca0fc4129a) Thanks [@Falkicon](https://github.com/Falkicon)! - Make the scenario runner, the testing MCP tools and surface validation fail loudly instead of passing silently, and confine the MCP tools to their working directory.

  - **Behaviour change: fixtures check every command.** `applyFixture` passes each command's real `CommandResult` to the adapter and fails on the first `success: false`, naming the command and error code (`Fixture command 'todo-create' failed with VALIDATION_ERROR: ...`). Adapter `warnings` are returned. The scenario is then reported as an `error` at the fixture step (`result.error.type: 'fixture_failed'`) and no step runs. The fixture handler must return a `CommandResult` (new `FixtureCommandHandler` type). The todo adapter uses the example's kebab-case commands (`todo-clear` with `{ all: true }`, `todo-create`, `todo-toggle`). The legacy hard-coded `todo`/`violet` switch is gone: a fixture is applied through a registered adapter, the built-in todo adapter, or the generic adapter for `setup`/`data` command lists, and a fixture for an app with no adapter is an error. Relative fixture paths resolve against the scenario file (`scenario.sourcePath`, set by `parseScenarioFile`), not the process working directory. `ScenarioExecutor` (CLI) now applies fixtures and resolves step references too.
  - **Behaviour change: no more false greens from expectations.** An object is a matcher only if all its keys are matcher keys; mixing in other keys, a typo next to a matcher, or a matcher given the wrong type of value is an error (parse error in YAML, `InvalidExpectationError` from `evaluateResult`, step `error` of type `parse_error` at run time). New `equals` matcher, and `error.suggestion` expectations (a string to contain, or a matcher). The YAML parser rejects unknown fields at every level, `data` on an expected failure, `error` on an expected success, and the unimplemented `verify`, `isolation` and `dependsOn` fields ("not supported"). Scenario-level `timeout` is implemented. An unresolved `${{ steps[N]... }}` reference fails the step with a `reference_error` instead of sending `''` or `undefined`. `testCommandMultiple` now fails a case whose `expectError` does not occur.
  - **Behaviour change: timeouts cancel.** `scenarioEvaluate({ timeout })` and a scenario's `timeout` abort an `AbortSignal` passed to the executor (`execute(scenario, { signal })`, new `ExecuteScenarioOptions`) and to the handler as an optional third argument; the running step is abandoned, later steps never run, the timer is cleared, and the result records `error: { type: 'timeout', message }`. `ScenarioExecutor` kills the CLI process. `failFast` reports scenarios it did not run with the new `skip` outcome and `summary.skippedScenarios` (the old path mislabelled them `partial` and dropped them). Unparseable scenario files are reported as `error` scenarios with a non-zero exit code in directory and explicit mode, and `scenario-list` returns them in `parseErrors`. The terminal reporter no longer prints "All scenarios passed!" when scenarios errored.
  - **Security: MCP tools are confined to `cwd`.** Every path argument, and every fixture file a scenario names, is resolved against the server's `cwd` and rejected with `PATH_OUTSIDE_WORKSPACE` when it leaves it, including through a symlinked parent. `scenario-create` rejects names and file names with path separators, strips line breaks from the generated header comment, and refuses to write a file its own parser would reject (the default template now has a placeholder step, so it parses). YAML and fixture JSON errors report a line or position but never echo file contents.
  - **MCP schemas match the implementations.** Tool inputs are validated against their schemas (types, enums, ranges, required and unknown fields) and invalid input returns a `VALIDATION_ERROR` result instead of throwing. `scenario-evaluate` takes `failFast` (`stopOnFailure` is kept as an alias), `timeout`, and defaults `format` to `json` as documented; `verbose` is gone. `scenario-create` lists the real templates (`blank`, `crud`, `error-handling`, `workflow`) and implements `commands`. `scenario-coverage` writes `output` (also a new `ScenarioCoverageInput.output`) and computes coverage only over known commands. `scenario-list` implements `recursive`, `pattern` and `format`, and rejects `status: 'passed' | 'failed'` with `UNSUPPORTED_FILTER` since it keeps no run history. The server no longer answers JSON-RPC notifications, and stdio replies to malformed input with a parse or invalid-request error. `scenario-suggest` is described as heuristic, uses kebab-case command names, finds known commands without scenarios, and `relatedCommands` lists tool names only.
  - **Surface validation scales.** Descriptions are tokenized once and only pairs sharing a term are scored against the threshold (`SimilarityOptions.threshold`); schema overlap prunes pairs that cannot reach the threshold; findings are appended without spreading, so 2,000 commands validate in well under a second and a rule with hundreds of thousands of findings no longer overflows the stack. `additionalInjectionPatterns` now extends the built-in `INJECTION_PATTERNS` instead of replacing them, and patterns with the `g` or `y` flag give the same answer on every scan.

### Patch Changes

- [#250](https://github.com/lushly-dev/afd/pull/250) [`31ab538`](https://github.com/lushly-dev/afd/commit/31ab5388f0e88e59f41b972daedf8c6fe12b0470) Thanks [@Falkicon](https://github.com/Falkicon)! - The core command registry now follows the MCP server's execution rules, and error and result helpers no longer leak or misreport.

  - **Batch and stream share one executor.** New `executeBatch()` and `executeStream()` in `@lushly-dev/afd-core` take an `execute` callback, like `executePipeline()`. `createCommandRegistry()` delegates to them, and the MCP server engine can adopt them later.
  - **Batch timeout at any parallelism.** `executeBatch` now enforces `options.timeout` when `parallelism > 1`. At the deadline, in-flight commands have their `signal` aborted and are reported as `BATCH_TIMEOUT`, and commands not yet started are reported as `BATCH_TIMEOUT` without running. Previously a 50 ms timeout with `parallelism: 2` took 405 ms and ran every command.
  - **Exposure is checked on every entry point.** `executeBatch(request, context)` and `executeStream(name, input, options, context)` take a `CommandContext`. Its `interface` reaches each batch entry and the stream, so a command that `execute` rejects with `COMMAND_NOT_EXPOSED` is no longer run through a batch or stream. `COMMAND_NOT_EXPOSED` now includes a `suggestion`.
  - **Malformed batches are rejected before anything runs.** The registry validates the whole envelope with `isBatchRequest()`, as the server does. A `null` entry, an empty command name, a non-string `id` or invalid options now return `INVALID_BATCH_REQUEST`. Previously a `null` entry was silently skipped, so two commands reported `total: 1`. `COMMAND_SKIPPED` and `BATCH_TIMEOUT` results now include a `suggestion`.
  - **Handler exceptions are redacted by default.** `execute` returns `COMMAND_EXECUTION_ERROR` with a generic message and no stack. Pass `createCommandRegistry({ devMode: true })` to include the raw message and the stack in `details.stack`, as the server's `devMode` does. Previously the message and stack were always included.
  - **The stack is no longer in `details`.** `wrapError()` builds a plain `CommandError` from a thrown `Error`. It keeps the message and any string `code`, string `suggestion` and boolean `retryable`, and drops every other field, such as a Node system error's `errno`, `syscall` and `path`. The stack is kept on a non-enumerable `stack` property for logging and is never serialized. `cause` is set only when the error's cause is itself a `CommandError`. `internalError(message, cause)` attaches `cause` non-enumerably, so `error.cause` still works in process but is never serialized.
  - **`isCommandError()` returns `false` for `Error` instances**, including errors from another realm, even when they carry a string `code` such as `ENOENT`.
  - **`isSuccess(success(undefined))` is now `true`.** `isSuccess` checks only `success === true`, so void commands no longer fall through both `isSuccess` and `isFailure`. It narrows `data` to the result's type `T`.
  - **`createTimeoutController()` returns a `TimeoutController`**, an `AbortController` with a `dispose()` method. The timer is `unref()`'d in Node and cleared on abort or `dispose()`. Call `dispose()` when the work finishes so the signal is not aborted afterwards and the process is not kept alive.
  - **Testing: `MockMcpServer` behaves like the server.** It lists and runs only commands with `expose.mcp: true`; any other command returns `COMMAND_NOT_EXPOSED`. It accepts the built-in `afd-batch` tool through the shared batch executor, and it redacts handler exceptions unless `createMockServer(commands, { devMode: true })` is used. `createMockCommand`, `createSuccessCommand` and `createFailureCommand` now set `expose.mcp: true`, so they stay callable through the mock server.
