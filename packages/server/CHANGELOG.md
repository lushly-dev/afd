# @lushly-dev/afd-server

## 3.0.0

### Major Changes

- [#2645](https://github.com/lushly-dev/afd/pull/2645) [`f01f103`](https://github.com/lushly-dev/afd/commit/f01f1033dd68f240aea655705f5e0d5fd9c76543) Thanks [@Falkicon](https://github.com/Falkicon)! - `zod` is now a peer dependency (`^4.6.6`) of `@lushly-dev/afd-server`, `@lushly-dev/afd-testing` and `@lushly-dev/afd-view-state` instead of a dependency, so an application's command schemas and the server use one copy of Zod. With two copies the schemas still validated, but TypeScript can reject an application's schema passed to `defineCommand`, because the two copies' types do not unify. `@lushly-dev/afd-cli` now depends on `zod` itself, since it runs the server, and `@lushly-dev/afd-auth`'s optional `zod` peer rises from `^4.0.0` to `^4.6.6` to match the server it runs on. Shape detection for a `VALIDATION_ERROR`'s `expectedFields`, `unexpectedFields` and `missingFields`, and `isObjectSchema()`, now read a schema's `_zod.def.type` instead of using `instanceof` against afd-server's own Zod classes, so they do not depend on which copy of Zod built the schema.

  This is a breaking install change, so it is a major. npm 7 or later, pnpm and Bun install a missing peer themselves, but these applications need a change:

  - One that depends on a `zod` outside `^4.6.6`, such as 3.25 (whose `zod/v4` entry it may have used for its commands): npm stops with `ERESOLVE` where it used to nest a second copy, and pnpm warns and then links the server to that `zod`, which it cannot run on. Upgrade the application to `zod@^4.6.6`.
  - One that never depended on `zod`, for example one that uses only `@lushly-dev/afd-view-state` or `@lushly-dev/afd-testing`, where peers are not installed automatically (Yarn, npm's `legacy-peer-deps`, or pnpm with `auto-install-peers=false`): the install warns, and the server may fail to import `zod` or find another package's copy. Add `zod@^4.6.6` to its dependencies.

- [#2864](https://github.com/lushly-dev/afd/pull/2864) [`b96288b`](https://github.com/lushly-dev/afd/commit/b96288b7e861937029f14f295c6c1484e51ee0e7) Thanks [@Falkicon](https://github.com/Falkicon)! - **Idempotency keys: a mutation a caller can safely send twice** ([#2675](https://github.com/lushly-dev/afd/issues/2675), `spec/idempotency.md`). A command declares `idempotency: 'natural'` (a repeat leaves the same state; reported as the MCP annotation `idempotentHint: true`) or `'keyed'` (a repeat with the same key and input is safe), in `_meta.idempotency`, `afd-detail` and `afd-help` (`full`). A caller sends a key in `_meta["dev.afd/idempotencyKey"]`, a meta-tool's `meta` argument, `context.idempotencyKey` in process, DirectClient's and `McpClient`'s `idempotencyKey` call option, or `afd call --idempotency-key`. Every engine validates it (1 to 200 of `A-Z a-z 0-9 . _ ~ -`, else `VALIDATION_ERROR` before confirmation, middleware or handler) and delivers it to the handler; batch items and pipeline steps run under `<key>:<i>` and `<key>:step:<i>`; a command a handler runs through the registry does not inherit it; the journal records it in `idempotencyKey` and replay restores it. `createMcpServer({ idempotency: { store, ttlMs, leaseMs } })` adds the engine's step, between the approval admission check and the handler: a repeat of a `keyed` call with a key is answered from the store with `metadata.idempotentReplay: true`, or refused with the new `IDEMPOTENCY_KEY_REUSED` (another input), `IDEMPOTENCY_IN_PROGRESS` (still running) or `OUTCOME_UNKNOWN` (the first call returned `TIMEOUT`, threw, or outlived its lease), and a `TIMEOUT` on such a call carries `recovery: { kind: 'retry' }`. A server that cannot tell its HTTP callers apart refuses such a call with `UNAUTHORIZED`, anonymous stdio connections never share keys, and `instances: 'multiple'` needs a shared `store`. A direct registry takes a step built with `createIdempotencyStep(options, { clock })`, so a host without one does not bundle it. **Behaviour changes:** the retry middleware now follows the declaration: it repeats a `natural` command, a `keyed` one only when the call carries a key, and any other unless it declares `mutation: true`; `retryMutations: true` still restores retrying everything. `idempotencyKey` is a reserved context name, so declaring a context field of that name now fails at startup, and a `context.idempotencyKey` that host code or `createContext` sets is now validated like a caller's, so a malformed one fails every call with `VALIDATION_ERROR`. A journal entry whose call carried a key hashes it as a member of `contextDigest` instead of listing its name in `keys`, so its hash differs from a recording made before. `afd validate --surface` gains `missing-idempotency`, an info finding for a `mutation: true` command that declares neither value. The three codes join the shared catalog in an `idempotency` profile.

- [#2846](https://github.com/lushly-dev/afd/pull/2846) [`7f994c7`](https://github.com/lushly-dev/afd/commit/7f994c7e4e32c94a210e90669e59824cac0b4221) Thanks [@Falkicon](https://github.com/Falkicon)! - A host can now key a record of its own by the call it describes, and record which approval admitted a held call ([`spec/dispatch.md`](https://github.com/lushly-dev/afd/blob/main/spec/dispatch.md), "The dispatch id", and [`spec/command-metadata.md`](https://github.com/lushly-dev/afd/blob/main/spec/command-metadata.md), "The approval summary").

  - **`context.dispatchId`.** `createMcpServer`, `createDirectRegistry` and the core registry give every call an id: 128 random bits from `crypto.getRandomValues`, as 22 characters of unpadded base64url, never taken from the caller. Each batch item, pipeline step and command a handler runs gets its own; a retry inside the middleware chain keeps it. It is a read-only property of the call's context: a write is ignored and it cannot be redefined, so every middleware, including each part of a `composeMiddleware`, and the handler read the same value. An app call's `callGrant` reads the id its handler will. It is not enumerable: results, journal entries and the journal's context digest are byte for byte what they were.
  - **`onApprovalAccepted(summary, dispatchId)`** on `createApprovalMiddleware`, called when the step admits a held call (a token, an answer over the MCP relay, a `HumanRelay`'s evidence, or DirectClient's private exchange), before the handler. The new `ApprovalSummary` type carries `via`, `command`, `inputDigest`, `approvalId`, and `issuedAt` and `expiresAt` when the evidence has them; it holds no token, nonce or decision id. The step waits for the hook, and a hook that throws or rejects fails the call with `COMMAND_EXECUTION_ERROR` before the handler runs.
  - **`approvalId`** on `onApprovalRequired`'s `ApprovalRequest` and on DirectClient's `DirectApprovalRequest`: the id the call's summary will carry, so the surface that asks a person can keep it beside their answer.

  Breaking for one rare case: `dispatchId` is now a reserved context name, as `spec/context-fields.md` requires from the release that sets the id. A declared context field of that name fails at registration (rename the field), and a context value a host put under it is replaced by the engine's (read the host's own value under another name). Code that builds an `ApprovalRequest` itself, such as a test's fake, now supplies `approvalId`. `spec/vectors/journal-seams.json` no longer lists TypeScript as a gap; every case runs.

- [#2652](https://github.com/lushly-dev/afd/pull/2652) [`5e33124`](https://github.com/lushly-dev/afd/commit/5e33124bc3d6d698192741dc38bfbe43186fd7f1) Thanks [@Falkicon](https://github.com/Falkicon)! - Every lane of an MCP server now admits a call through one pipeline with named stages (`evidence`, `meta`, `principal`, `approver`, `bind`, then the router's `scope`, `resolve`, `allow`, `lookup`, `context`, `host-verified`, `confirm`, `task` and `execute`). The lanes are `/mcp`, stdio in both eras, `/message`, `/rpc`, `/batch` and `/stream`. The HTTP routes now decode as the meta-tools they stand for: `/rpc` and `/stream` as `afd-call`, and `/batch` as `afd-batch`. So the same call gets the same answer on every lane. What changes on the HTTP routes (`/rpc`, `/batch`, `/stream`), each now matching the MCP lanes:

  - They check the active context before confirmation, as `spec/dispatch.md` requires. A confirm-gated command outside the session's active context now fails with `COMMAND_NOT_IN_CONTEXT`, not `CONFIRMATION_REQUIRED`. A batch still confirms every step first.
  - A caller the `approver` option names is decided as on the 2025-era `/message` lane:
    - its `APPROVAL_REQUIRED` results carry `details.approvalToken`;
    - its `_meta["dev.afd/approval"]` is refused with `APPROVAL_REQUIRED` (`retryable: false`) and nothing runs, where before it was ignored;
    - credentials that cannot be bound fail its call as an internal error.
  - `createContext` runs for every call, refused ones included, before the scope, host-verified and confirmation checks. A throwing `createContext` therefore answers a call that would have been refused as an internal error.
  - An unknown `Mcp-Session-Id` on `/batch` and `/stream` is answered with HTTP 404 before any refusal, as on `/rpc`.

  Smaller changes:

  - A `/stream/` path without a command name is HTTP 400.
  - On `/message`, `arguments` that are not an object are `INVALID_PARAMS` before the approval-evidence check.
  - `/rpc` and `/batch` trace IDs take the router's form (`rpc-<time>-<random>`, `batch-<time>-<random>`).

  The server's trusted state for a call is no longer nine private symbols on `CommandContext`. These are the session's context state, the scope view, the approver, the approval relay and up-front approval, the confirmation and human-relay channels, task dispatch and the direct registry's `allow`. They are now one frozen host-state record, which the context carries as a single opaque token. Copies carry it, so a nested call a handler makes with its own context is still decided under the caller's session and authorization. A handler cannot read it, change it or forge it: a token the server did not mint carries no state and refuses every command. As before, a handler that deliberately removes the token from its context makes what amounts to a fresh in-process call.

- [#2978](https://github.com/lushly-dev/afd/pull/2978) [`ea0155f`](https://github.com/lushly-dev/afd/commit/ea0155f120f98cb23757da697d3dd00456e77422) Thanks [@Falkicon](https://github.com/Falkicon)! - `createJournalMiddleware` gives each call its own view of the context's clock and random source where the runtime has `AsyncLocalStorage` (Node 22.3 and later), instead of swapping them on the context for the length of the call ([#2890](https://github.com/lushly-dev/afd/issues/2890)). So a chain composed by hand and run concurrently on one context object no longer puts an off-tape call's values on a sibling's tape, marks a sibling's tape `truncated`, or leaves a finished call's recorder on the context, and a second secret call inside a recorded parent now stays off the parent's tape like the first.

  Also changed: a context with no sources of its own no longer has the system clock and random source written onto it after a recorded call; a source a handler assigns during a call stays on the context, and marks that call's tape `truncated`; and a read made by work a recorded call started, while an off-tape call inside it runs, reaches no tape and marks the recorded call's tape `truncated`. Reads made by work started outside any call read the context's own source. `AsyncLocalStorage` is looked up at run time, so `/direct` imports nothing from Node; without it (a browser) the journal swaps the sources as before, and every engine there gives each dispatch its own context.
