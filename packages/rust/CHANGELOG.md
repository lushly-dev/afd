# Changelog

All notable changes to the `afd` Rust crate are documented here. The crate is versioned independently of the npm packages and other implementations. Rust releases are distributed through [crates.io](https://crates.io/crates/afd) and use tags of the form `rust-vX.Y.Z`.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this crate adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a minor release may break the API.

## [Unreleased]

### Added

- **A host's task store sees the call it records (`server` feature; `spec/command-metadata.md`, "Tasks"; Umbel phase 5 step 8):** `TaskStore::create_for(record, call)`, a default method that calls `create`, is what the server now calls to record a task; `TaskCall` gives the store the command, the input as the request gave it and the context the command will run with, so a host's shared store can keep its own fields (who owns the task by the host's mapping, which space the call names) and must keep neither the input nor the credentials. `Arc<T>` forwards it. `afd::server::failure_result(error)` returns the `CallToolResult` an inline call returns for a failure, for a store that ends a task itself (as one whose process died). `tests/server_tasks.rs` checks both.
- **A runner's heartbeat, and a runner whose task another process ended (`server` feature; Umbel phase 5 step 8):** `TaskStore::heartbeat(id, owner, now)`, a default method that does nothing, is called by a task's runner at every check, and never by a `tasks/*` request, so a store shared by several processes can lease a task to the process running it and find a dead or hung runner by its silence. A runner that reads its task finished in the store (another process ended it, as a host's store does when it finds the lease run out) now stops the handler (its cancellation signal fires) and writes nothing over that end; `tasks/cancel` of a task the store holds finished stops it too where it still runs. `tests/server_tasks.rs` checks all three.
- **What a host's relay reads, and what it gives the approved call (`server` feature; `spec/command-metadata.md`, "Host-verified confirmation"; Umbel phase 5 step 5):** `RelayCall` gains `input`, the validated input its `input_digest` names, and `context`, the `CommandContext` the command would run with (after the context hook, with the verified credentials, never relay evidence), with `RelayCall::with_input` and `with_context` for a host testing its relay; `HumanRelay::approved_context(decision_id, call)`, a default method returning no fields, lets the relay give an approved call host-owned `extra` fields (Umbel's person decision and `humanPresent`), which the server sets after the gate's checks and before the registry runs anything. They are not evidence: AFD reads none of them, and they stay on the context of a command the handler runs in process. `CommandRegistry::validate` is public, for a host asking its person through a channel of its own (a terminal that waits for a decision made elsewhere). All additive; `RelayCall`'s `Debug` prints neither the input nor the context.
- **The decision before dispatch for a host's own layer (feature `server-auth`; `spec/authorization.md`, M6, "A host's own layer"; Umbel phase 5's follow-up of 2026-11-08):** `McpServer::pre_dispatch_check()` returns a `PreDispatchCheck`, the bearer layer's own decision before dispatch, for a host whose own HTTP layer admits credentials (`Authorization::admit`) instead of the bearer layer, such as Umbel's gateway-trusted mode. After admitting the credentials and reading the body, the host calls `PreDispatchCheck::decide(&parts, &body)`, which returns `PreDispatch::Proceed` or `PreDispatch::Respond(response)`: the bearer layer's 403 naming every missing scope of a `tools/call` (every step of `afd-batch` and `afd-pipe`, grouped actions, hybrid tools, hidden and unknown names on the required scopes alone), its 400 for a JSON-RPC batch, or its 413 over the authorization's body cap, byte for byte. `BearerLayer` now runs the same `PreDispatchCheck`, so the two cannot drift. `PreDispatchCheck::max_body_bytes()` is the cap to read a body under; a longer body is the bearer layer's 413. Under the cap, only the credentials admitted for the server's own authorization are decided; any other request proceeds, and the server refuses it (M1). A host whose callers use another scheme sets the 403's challenge with `PreDispatchCheck::with_challenge(ScopeChallenge)`: `ScopeChallenge::new(scheme)?.with_param(name, value)?` renders `<scheme> <params>, error="insufficient_scope", scope="<missing>"` (never `Bearer`, no `resource_metadata`, `scope` under M5's rules); the body's suggestion comes from `ProtectedResource::with_scope_source`. Tests: `tests/server_auth_pre_dispatch.rs` sends every request of a matrix (every tool strategy, the static rule and a scope-naming resolver that hides commands, with and without required scopes, `POST`, `GET` and `DELETE`, batches, unparseable and oversized bodies) through the bearer layer and through a host layer running the check, and compares status, headers, body bytes, what passed on and every question put to the resolver.
- **`ProtectedResource::with_scope_source` (feature `server-auth`; Umbel phase 5 step 4):** a host whose callers are not token holders (Umbel's gateway-trusted mode, where a gateway asserts each caller's scopes) names what they obtain to gain a scope. The suggestion of a 403 body and of an `INSUFFICIENT_SCOPE` result then reads "Obtain `<source>` that also grants `<scopes>`, then retry." instead of "Obtain a token for `<resource>` ...". Additive: nothing published and no challenge changes, and without it every string is as `spec/authorization.md` M5 writes it.
- **MCP Tasks (`spec/command-metadata.md`, "Tasks"; the Tasks extension `io.modelcontextprotocol/tasks`, SEP-2663; Umbel phase 5 step 0e):** `CommandDefinition::with_task(TaskSupport)` (the public field `task: Option<TaskSupport>`, `task_support()`; `TaskSupport::{Never, Optional, Required}`, reported as `task` in the tool's `_meta`, grouped `_meta.actions` and `afd-detail` when set) says whether an MCP `tools/call` may run as a task. Registration (`register` and the schema variants, through `validate_person_gates`) refuses `Optional` or `Required` beside `confirm_prompt`, an approval policy other than `NotRequired`, or a `confirmation_mode`, naming the command and the setting: a task never asks a person. With the `server` feature, `McpServer` declares the extension when an MCP-exposed command may be a task and serves `tasks/get`, `tasks/update` and `tasks/cancel` (`afd::server::tasks`). Only an MCP 2026-07-28 request whose own `_meta` client capabilities declare the extension gets a task (never a 2025 request, whatever it declared at `initialize`); otherwise `Optional` runs inline and `Required` is JSON-RPC `-32021` naming the extension. A call routed to one command (its tool, a hybrid first-class tool, a grouped tool, `afd-call`) becomes a task after every check an inline call meets before dispatch (the bearer layer's 403, the context hook, the scope check, the context check, the confirmation gate); an `afd-batch` or `afd-pipe` step naming a `Required` command fails the whole request with `INVALID_BATCH_REQUEST` or `INVALID_PIPELINE_REQUEST` before any step runs, and an `Optional` step runs inline. The task id is 128 bits from the OS random source (26 characters of lowercase base32); the record (`TaskRecord`: id, owner, command, status, `statusMessage`, times, `ttlMs`, `pollIntervalMs`, `cancelRequested`, result or error; no token, credentials or input) is in the `TaskStore` before `CreateTaskResult` is returned, and a store that fails or is full fails the call with nothing run (`INTERNAL_ERROR` or `RATE_LIMITED`, both retryable). The owner (`TaskOwner`) is the call's `principal_binding`; credentials that cannot be bound get a generic `-32603`. The command runs through `CommandRegistry::execute` on a fresh context with the call's actor, credentials, trace id, declared context fields and output budget ask; its `CancellationSignal` fires on `tasks/cancel` (in this process at once, in another through the store's `cancelRequested`), when the task's `ttlMs` ends (the task is then gone) and at the credentials' `expiresAt`, which completes it with the failure `TASK_TOKEN_EXPIRED` (a token that expired before the task started never starts the handler, and a result arriving after expiry is not delivered; retryable unless the command is a mutation whose handler started, whose suggestion then says to check its effect); the server stops the handler at its next `.await`. Results are the inline `CallToolResult` (`completed`, with `isError` for a failed `CommandResult`; `failed` only for a JSON-RPC error; `cancelled` after a `tasks/cancel` that stopped it, while a handler that had already returned keeps its result); a result larger than `TaskOptions::max_result_bytes` (1 MiB) is replaced by an `INTERNAL_ERROR` that says the command ran. `CommandContext::report_progress` sets `statusMessage` and `lastUpdatedAt` (at most `MAX_PROGRESS_MESSAGE_BYTES`, 1024); `CommandContext::cancellation` and `is_cancelled` read the signal (`afd::CancellationSignal`, `afd::Cancelled`). `tasks/*` requests pass the checks of a request that names no command (fail closed without admitted credentials, the required scopes), run the context hook with `ContextHookRequest::tool` set to the method name, and then the owner check, in the store and again in the server: another principal's task (another actor, issuer, subject or client), an expired task, a malformed id and an unknown id all get the same `-32602` "Task not found", byte for byte. On an authorized server the owner must also still hold the command's `scopes` (or, under a resolver, its `visible`) to read or update it, else `-32600` with `data.code` `INSUFFICIENT_SCOPE`; `tasks/cancel` does not ask that. A server creates tasks only for callers it can tell apart: without an HTTP request (stdio), with verified credentials, or with `TaskOptions::with_callers_identified_by_hook()` and a context hook installed. Otherwise, decided per request, it does not declare the extension (`server/discover`, `initialize`), `tasks/*` are `-32601`, `Optional` runs inline and `Required` fails with `UNAUTHORIZED` (`retryable: false`) before anything runs. `tasks/update` acknowledges and ignores every `inputResponses` key (no AFD task waits for input); `tasks/cancel` acknowledges, and leaves a finished task unchanged. `McpServer::with_task_store(impl TaskStore)` takes a host's shared store (`create` durable before returning, `get` and `update` by owner, `expire(now)`; implemented for `Arc<T>`), and `McpServer::with_task_options(TaskOptions)` sets `ttlMs` (default 1 hour; `with_ttl_capped_at_token_expiry(grace_ms)` ends it at the token's `expiresAt` plus a grace), `pollIntervalMs` (1 s), the check interval (1 s), the result limit and the most tasks one process runs at once (64, whatever the store allows); the fields are read through getters and every value is at least 1. The default `InMemoryTaskStore` serves one process and holds at most 32 tasks per owner and 256 in all (`with_limits`), each until its `ttlMs` ends, dropping the owner's own, or the largest holder's, oldest finished task to make room. Every limit answers the same `RATE_LIMITED`. `error_codes::TASK_TOKEN_EXPIRED` joins the shared catalog (48 codes). `tests/server_tasks.rs` covers it over Streamable HTTP (with and without the bearer layer) and stdio.

- **Host-verified confirmation, `HumanRelay` and relay evidence (`spec/command-metadata.md`, "Host-verified confirmation" and "Relay evidence"; Umbel phase 5 step 0d):** `CommandDefinition::with_confirmation_mode(CommandConfirmationMode::HostVerified)` (the public field `confirmation_mode`, `is_host_verified`; named apart from the server's `ConfirmationMode` option) marks a command only the host can confirm, reported as `confirmationMode: "host-verified"` in its tool's `_meta`, grouped `_meta.actions` and `afd-detail`. With the `server` feature, `McpServer::with_human_relay(impl HumanRelay)` installs the host's relay (`afd::server::{HumanRelay, RelayCall, RelayPrompt, RelayOutcome, RELAY_INPUT_KEY}`: async `begin` and `resume`; `RelayCall::principal_binding` and `supports_url_elicitation`). For such a command, on every MCP route and whatever `with_confirmations` says (`Off` included), the server never sends a form, never advertises or accepts `confirm: true`, a `confirm` list, `_meta["dev.afd/confirm"]` or a form answer, and gates it with or without `confirm_prompt`; without a relay every call is `CONFIRMATION_REQUIRED`. Only a call that routes to the one command (its tool, a hybrid first-class tool, a grouped tool, `afd-call`) on an MCP 2026-07-28 request is relayed; an `afd-batch` or `afd-pipe` naming one and a 2025 request fail before any step runs. The server validates the input first (`VALIDATION_ERROR`, and the scope resolver asked again on the validated input), gives the relay `afd::input_digest` of the validated input, answers `begin`'s prompt with one URL-mode elicitation under `relay` (`elicitationId` the unpadded base64url SHA-256 of the URL, the relay's `state` as `requestState`) and never to a client that did not declare URL mode (`CONFIRMATION_REQUIRED`); on the retry `decline` or `cancel` is `CONFIRMATION_DECLINED` without asking the relay, and `accept` calls `resume`: `Approved` runs the command with relay evidence, `Declined` is `CONFIRMATION_DECLINED`, `Pending` asks again, `Invalid` begins again. A prompt whose URL is not an absolute `https` URL without user information, an empty state or an `Approved` without a decision id is a generic `-32603`, as are credentials that cannot be bound, before the relay is asked. Relay evidence is a crate-private `CommandContext` field: `create_approval_middleware` considers it and nothing else, checks the command, the digest of the validated input, the actor and the credentials binding in that order (`details.reason` `command-mismatch`, `input-mismatch`, `actor-mismatch`, `credentials-mismatch`), then spends `relay:<decisionId>` once in its nonce store for 24 hours whatever the replay setting (`already-used`); a refusal carries no token unless the middleware includes tokens. The evidence is removed before the handler runs, so a command the handler calls in process never runs on it.
- **The form-mode approval relay (`server` and `approval` features; `spec/command-metadata.md`, "Asking the human over MCP"):** `ApprovalMiddlewareOptions::with_relay(ApprovalRelay::McpElicitation)` (default `ApprovalRelay::Off`) asks the human behind an MCP client instead of failing a call to one command that can carry a form elicitation: `input_required` with one form under `approval` (one required boolean `approve`; the message is the summary, the command and its canonical validated input, truncated at 1000 characters) on MCP 2026-07-28, or a server-sent elicitation on a 2025 stdio connection, and the call runs on `accept` with `approve: true`. No token is issued. The answer is bound by a keyed digest of the command, validated input and actor under the approval secret, and its nonce and expiry by a MAC under the same secret, so the state's own key cannot mint one; it counts for 10 minutes from when it was asked, within the middleware's TTL, and its nonce is spent once (unless `WithinTtl`). A declined form is `APPROVAL_REQUIRED` with `details.reason: "declined"` and `retryable: false`; an expired or spent answer is asked again, saying so. Batch and pipeline steps, commands run by another command's handler, calls that cannot elicit and host-verified commands are never asked; on MCP their `APPROVAL_REQUIRED` never carries a token, whatever `with_include_token` says. `ApprovalRejection` gains `CredentialsMismatch` and `Declined`.
- **`afd::input_digest`:** the unpadded base64url SHA-256 of a value's canonical JSON, the relay input digest; `tests/authorization_cases.rs` now checks `spec/authorization.json`'s `inputDigests` against it.

- **MCP authorization (`server-auth` feature, implies `server`, Rust 1.88; `spec/authorization.md` M1 to M7, Umbel phase 5 step 0b):** `afd::server::auth` makes an HTTP `McpServer` an OAuth 2.1 protected resource. `McpServer::with_authorization(Authorization)` configures it (`Authorization::new(ProtectedResource, impl TokenVerifier)`, `with_required_scopes`, `with_resolver`, `with_filter_tools_by_scope`, `with_max_body_bytes`; the verifier's resource and binding rule must match the metadata's), and `McpServer::bearer_layer()` gives the `BearerLayer`, a `tower` layer to put outermost on the router holding the MCP endpoint. The layer serves RFC 9728 metadata (`ProtectedResource`: `resource`, `authorization_servers`, `scopes_supported` when published, `bearer_methods_supported: ["header"]`, `resource_name` when set, `tls_client_certificate_bound_access_tokens`) by `GET` at both well-known paths without authentication (405 otherwise); takes exactly one `Authorization: Bearer <b64token>` (`extract_bearer`: a token in the query or a form body, or a second header, is `token-location`); verifies it; answers every refusal with the exact 401 `WWW-Authenticate` and JSON body of M5 and logs the rule code (`RuleCode`) at `warn`, target `afd::auth`, with the issuer's configured alias, never the token or a claim value; reads the body (at most 1 MiB by default, else 413) and decides every command a `tools/call` names before dispatch (the command's tool, a hybrid first-class tool, a grouped action resolved as the router resolves it, `afd-call`, every step of `afd-batch` and `afd-pipe`, each message of a JSON-RPC batch), answering any missing scope with one 403 naming every missing scope in step order; every other request needs the required scopes; then strips the `Authorization` header, so nothing behind the layer (the context hook included) sees the token, and passes the verified `Credentials` on in the request extensions. `JwtVerifier` (`TokenRules`: the resource as the only audience, clock skew at most 300 s, lifetime, scope prefix and limit, bound tokens; `JwtIssuer`: alias, exact `iss`, `SigningAlgorithm`s, a host `KeySource`; `StaticKeys` for a fixed JWKS) applies M3 in order with its own code: route by shape and exact unverified `iss` (`with_introspection` sends every other token to a host `TokenVerifier`), the header (`typ` `at+jwt`, `alg` listed and never `none` or `HS*`, a non-empty `kid`, no `crit`, no `jku`, `x5u`, `x5c` or `jwk`), the key's fit (`kid`, `kty`, `crv`, `alg`, `use`, `key_ops`), the signature through `jsonwebtoken`'s `aws-lc-rs` provider called directly (no `decode`, no `Validation`, no library default), then the claims (`check_claims`: issuer, exactly one audience under M3.1's comparison, required claims of at most 255 code points with no control character, time with the skew, lifetime, the strict `scope` grammar and limit, `cnf.jkt` refused as `dpop-unsupported`, `cnf["x5t#S256"]` against the `ClientCertificate` thumbprint the host's TLS layer inserts). A JOSE header or claims set with a repeated member name is refused. `check_introspection` applies the same rules 5 to 10 to an RFC 7662 answer for a host's introspection verifier. On the server: an HTTP request that reaches it without verified credentials (the layer left out) fails closed with `UNAUTHORIZED` on every handler, `initialize` included; each call's `CommandContext::credentials` holds them and its actor defaults to `{ kind: "agent", id: <clientId>, onBehalfOf: <subject> }`, which the context hook may map but cannot change the credentials; after the hook and before the confirmation gate every call with credentials is decided again, failing with `INSUFFICIENT_SCOPE` (`retryable: false`, `details.scopes`), a batch or pipeline as a whole; with `with_filter_tools_by_scope(true)`, `tools/list` (every strategy, then `cacheScope: "private"`), `afd-discover`, `afd-detail`, `afd-help`, `afd-docs`, `afd-schema` and grouped actions show only the commands the caller may see. A `ScopeResolver` (`resolve` returning `ScopeDecision::{Allowed, Missing, Defer}`, and `visible`) decides each call instead of the static rule (`static_decision`, `forbidden_scopes`); the required scopes apply either way. stdio, `DirectClient` and in-process calls are unaffected. An independent security review's fixes are part of this change: `McpServer::authorized_http_service(HttpOptions)` builds the service and its layer from the same server (the documented path), and the server accepts only credentials admitted for its own configuration (`Authorization::admit`, which the layer and a host's gateway layer call), so a layer from another server, or credentials put in the extensions without it, are refused; an authorized server refuses requests on any transport but HTTP and stdio (`serve_stdio`) unless the host calls `McpServer::with_trusted_transport()`; any `Missing` refuses, even an empty one or one with names that are not scope tokens (`RequestDecision` and `request_decision` replace a list of scopes; with no valid name the 403 has no `scope` parameter); with a resolver the registry decides again at execution on the validated input (defaults, resolved pipeline references, batch items, nested calls that pass their context); "did you mean" suggestions never name a command the scope filter hides, and a grouped tool with every action hidden answers as an unknown tool; JSON-RPC batch bodies are 400; a JWT whose `exp` precedes its `iat` is `lifetime`; `CommandContext`'s `Debug` redacts the actor's id and principal. `ResourceProvider` gains default methods `list_for` and `read_for`, given a `ResourceCaller` with the request's credentials (additive). `tests/authorization_cases.rs` loads all 184 cases of `spec/authorization.json`, `tests/server_auth_hardening.rs` pins each review finding, `tests/auth_verifier.rs` holds one test per M3 rule with RSA, EC P-256 and P-384 and Ed25519 keys generated in the test, `tests/server_auth.rs` the layer end to end, and `tests/auth_canary.rs` captures every log line at `TRACE` to show no token or claim value reaches them. New optional dependencies: `jsonwebtoken` 11.1 (`aws_lc_rs`), `base64`, `bytes`, `http-body`, `http-body-util`, `tower-layer`, `tower-service`, `tracing`.
- **Command `scopes` and `Credentials` (no feature; `spec/command-metadata.md`, "Scopes"; `spec/authorization.md`, M4 and M8):** `CommandDefinition::with_scopes` and the public field `scopes` declare the OAuth scopes a command needs on an authorized server; registration refuses a scope that is not an RFC 6749 scope token, naming the command and the scope. They surface as `_meta.scopes` on the command's tool (an empty list is omitted), in grouped `_meta.actions` and in `afd-detail`; without `server-auth` they are metadata only. `afd::Credentials` (`issuer`, `subject`, `client_id`, `scopes`, `resource`, `expires_at`, `issued_at`, `auth_time`, `acr`, `certificate_thumbprint`; `Debug` prints only `issuer` and `expires_at`; `Serialize` writes the specification's JSON) is on `CommandContext::credentials` (`with_credentials` for trusted host code), with `afd::is_scope_token`, `afd::principal_binding` and `afd::credentials_binding` (M8's canonical JSON, for step 0c). `error_codes::INSUFFICIENT_SCOPE` joins the shared catalog (47 codes).
- **Output budgets (`spec/output-budgets.md`, B1 to B8, Umbel phase 2 step 0b):** `CommandDefinition::with_output_budget(default_bytes, max_bytes)` declares a budget (`CommandDefinition::output_budget`, `afd::OutputBudget`), refused when the command is registered unless both are integers from 1 to 9007199254740991 with the default not above the maximum (the error names the command and the field). A caller asks per call with `CommandContext::with_output_budget_ask(max_bytes)` in process (also through `DirectClient::call`'s context), or over MCP with `_meta["dev.afd/outputBudget"] = { "maxBytes": n }` on every route and both eras, or the meta-tools' `meta` argument (`dev.afd/outputBudget` joins the keys it accepts; the same value in both places, or `VALIDATION_ERROR`); a value the context hook sets wins, and the key is never read from headers. `CommandRegistry::execute` validates the ask after the input and the declared context fields, whether or not the command declares a budget (an invalid ask is `VALIDATION_ERROR` with `details` `{ "field": "outputBudget", "meta": "dev.afd/outputBudget" }`), and sets the effective budget, `min(ask, max_bytes)` or the default, for `CommandContext::output_budget()`. The innermost link of the middleware chain checks a successful result right after the handler, before `metadata` is stamped: it measures the UTF-8 length of the result's canonical JSON without `metadata` (the journal's number spelling and escaping); a read over budget is replaced by an `OUTPUT_BUDGET_EXCEEDED` failure with `details.limitBytes`, `actualBytes` and `maxBytes` and the specified suggestion; a mutation over budget keeps its result and gains a warning of that code; a result within budget carries `metadata["dev.afd/outputBudget"] = { limitBytes, usedBytes }`. A handler's own failure passes unchanged and nothing truncates structured output. Batch items and pipeline steps each get the ask and are checked on their own. The declaration surfaces as `_meta["dev.afd/outputBudget"]` on the command's tool (so on hybrid first-class tools too) and in grouped `_meta.actions`, in `afd-detail` and in `afd-help` (`full`). `JournalEntry` and `JournalRecord` gain `output_budget` (`outputBudget` on disk, after `contextOmitted`), which joins the context digest only when set, and `replay_journal` restores it as the call's ask. `outputBudget`, `output_budget` and `output_budget_ask` are reserved context field names. `tests/output_budget.rs` loads every case of `spec/output-budgets.json` in process and over Streamable HTTP and stdio in both MCP eras. The error code is `error_codes::OUTPUT_BUDGET_EXCEEDED`, which joins the shared catalog (46 codes).
- **Public frontmatter reader, `afd::frontmatter` (feature `frontmatter`, enabled by `server`):** the skills loader's YAML 1.2 core-schema reader (no tags, anchors or aliases; unchanged rules) moves out of the private `server` module. `parse(text) -> Result<Option<Frontmatter>, FrontmatterError>` returns `Ok(None)` when the first line is not `---` (no frontmatter) and a typed error when it is malformed; `Frontmatter { fields, body_offset, body_line }` gives the mapping, the body's byte offset and its 1-based line; `FrontmatterError` (`#[non_exhaustive]`: `Unclosed`, `NotAMapping`, `Forbidden { what, line }`, `TooDeep { line }`, `Syntax { line, column, message }`, `MoreThanOneDocument { line }`) has generic messages that name no file (the skills loader still words its own `SKILL.md: …` errors). The reader sets no size cap. Without `server`, `default-features = false, features = ["frontmatter"]` reads frontmatter without the MCP server.
- **MCP resources, the Skills extension, extra tool `_meta` and advertised schemas (`server` feature for the first two, `spec/mcp-resources.md`, Umbel phase 1 step 0b, #608):**
  - `McpServer::with_resources(impl ResourceProvider)` serves `resources/list`, `resources/read` and an empty `resources/templates/list`, declaring the `resources` capability (never `subscribe` or `listChanged`; a server with neither a provider nor a catalog declares nothing, as before). `ResourceProvider::list` is called each time the server lists, so entries may change; `read` is async and defaults to `ResourceReadError::NotFound`; a `Vec<ResourceEntry>` is a static provider. `ResourceEntry` carries `uri`, `name`, `title`, `description`, `icons`, `annotations`, `mimeType`, `size` and `_meta`; `with_bytes` / `with_text` give the content up front, so the server serves it, sets `size` and adds `_meta["dev.afd/digest"]` (`sha256:` and 64 lowercase hex). Entries are checked when the server starts (`McpServer::validate`) and each time they are listed (`-32603` for a list that breaks a rule): absolute URI with a scheme, unique, non-empty `name`, no `skill://` entry, a `ui://` entry needs `text/html;profile=mcp-app`, `size` equal to the bytes, `_meta` keys under the key rule (`ui` not allowed on an entry). Content is `text` when UTF-8 and `blob` (base64) otherwise; a provider's `ResourceContents` may add `_meta` to the item, where `ui` is allowed. An unknown URI is `-32602` with `Resource not found` and `data.uri` on both eras (rmcp would send `-32002` to a 2025 client). A cursor is `-32602` on every list: the server never issues one. A modern result carries `resultType`, `ttlMs` (the `tools/list` option, not lowered by contexts) and `cacheScope: "public"`; a 2025 result omits them. A read runs no command, middleware, confirmation, approval or journal entry and skips the context hook; a panicking provider is a generic `-32603`.

### Security

- **Scope bypass, `server-auth` feature: a call without an `action` of a tool that is both a group and a command, on a server that filters its listings in the grouped strategy (`spec/authorization.md`, M6, "Which commands a request names"):** when the caller was shown no member of the group, the router ran the command the tool names, but the decisions before dispatch and after routing treated the call as an unresolved group call (as long as some member existed for the caller). Under the static rule the command then ran without its `scopes`; under a resolver whose `known` is wider than `visible` it reached the confirmation gate before the decision at execution refused it. A call without an `action` is now a grouped call only when the caller is shown a member, as the router decides; otherwise it is decided as the command it runs. Found by the independent review of `PreDispatchCheck`; `tests/server_auth_pre_dispatch.rs` holds it under both rules, through the bearer layer, a host layer and after routing alone.

### Fixed

- **`server-auth` feature: `afd-help`'s `firstClassTools` on a filtered server (`spec/authorization.md`, M6, "Listing"):** a hybrid server's `afd-help` reported every configured first-class tool, including one the caller's filtered `tools/list` leaves out (under the static rule as under a resolver), so it named commands hidden from the caller. It now names only the first-class tools the caller's list shows.
- **`server` feature: confirmation state bound to the principal ([#532](https://github.com/lushly-dev/afd/issues/532); `spec/command-metadata.md`, "Confirmations"; `spec/authorization.md`, M8; Umbel phase 5 step 0c):** the confirmation `requestState` was bound to the command and its input only, so with a context hook admitting several actors, a state one caller answered could confirm the same command and input for another. Its HMAC associated data now also holds the call's principal binding (`afd::principal_binding`): the actor the context hook left, after the server's default, and, on an authorized server (`server-auth`), the verified credentials' `issuer`, `subject` and `clientId`. The binding is associated data, never in the state, so the state names no one. A retry from another actor, or with another issuer, subject or client (a different client of the same person included), fails to verify exactly as an altered state does, and the server asks again; nothing runs. The associated data's layout carries a version label, so a state minted before this change does not verify either and is asked again. A 2025 connection's server-sent elicitation holds no state and is unchanged. Credentials with an empty `issuer`, `subject` or `client_id` (only host code can build them) are never bound: such a call gets no state, and a retry carrying one is refused, both with a JSON-RPC internal error that names no one.

Two behaviours follow `rmcp`. First, `skills/get` for a URI that is not a `SKILL.md` URI (a supporting file, a directory) is `-32602` with no `data`, because `rmcp` refuses it before the handler runs; `spec/mcp-resources.md` S4 now allows that. Second, a non-string `cursor` on `skills/list` is ignored, as `rmcp` already ignores one on `resources/list`. The `rmcp` floor is now 3.9; its minimum Rust is still 1.88.
- **`server` feature: the manifest boundary (`spec/mcp-resources.md`, S2):** `SkillCatalog::new` refuses, naming the skill and the URI, a file whose `skill://` URI does not identify a distinct file inside the skill's directory once RFC 3986 normalization decodes percent-encoded unreserved characters. - **Journal context cap (#578):** the journal measures a declared context field's value against `MAX_JOURNAL_CONTEXT_BYTES` as JavaScript writes it (`spec/journal.md`, "Declared context fields"), so a value within a few bytes of the cap is kept or omitted as in TypeScript, Python and C++. It measured serde's spelling: `1.0` for `1`, `1e+20` for `100000000000000000000`, `-0.0` for `0`, and an integer past 2^53 as written rather than as the double JavaScript reads it as. ### Changed

- **`server-auth` feature: a grouped call that resolves to no single command is decided as a name that does not exist (`spec/authorization.md`, M6, "Which commands a request names"). A behaviour change for a server with a resolver in the grouped strategy:** such a call (an `action` that no member of the tool's group has, or several do, or a group's call without an `action`) was decided before dispatch and after routing as a tool named after the grouped tool, so `ScopeResolver::resolve` was asked about that name. The router treats any tool name with an `action` as a group, so `{ "name": "<hidden command>", "arguments": { "action": "x" } }` asked the resolver about a hidden command's name, and a resolver that looks names up could answer it otherwise than a name that does not exist (found by the parity tests of `PreDispatchCheck`). Such a call runs nothing and the router answers it (`COMMAND_NOT_FOUND`, `AMBIGUOUS_ACTION` or `INVALID_GROUPED_CALL`), so it now needs the required scopes alone and `resolve` is never asked about it. Under the static rule nothing changes. A meta-tool that names no command (`afd-detail`, a malformed `afd-batch`) is still decided under its own name, with its arguments as sent, which may name hidden commands: the resolver must not decide on whether they exist.
- **`server-auth` feature: a hidden command is unknown on every route, before validation (`spec/authorization.md`, M6, "Hidden commands"; Umbel phase 5's follow-up of 2026-11-08). A behaviour change for a server with filtered listings and a resolver:** a command left off a caller's listings was still looked up as a command when called, so its input was validated before any middleware or scope gate ran (invalid input answered `VALIDATION_ERROR` rather than `COMMAND_NOT_FOUND`), and a direct `tools/call` of it, a grouped action naming it, or an `afd-batch` or `afd-pipe` step with it could reach the confirmation gate, a host-verified relay or a task. The new `ScopeResolver::known(command, credentials)` says whether a command exists for the caller; it defaults to `visible`, so with `Authorization::with_filter_tools_by_scope(true)` and a resolver, a command the caller cannot list is now unknown to it unless the resolver overrides `known` (override it to keep a command the caller may step up to callable, and refused with a 403 naming its scope). Such a command is looked up as a name that does not exist on every route, by the router and by `CommandRegistry::execute` for every batch item, pipeline step and nested call that passes the context on, so the answer is byte-identical to a missing name's. A command name that does not exist for the caller (unknown, unexposed or hidden) is decided before dispatch and after routing on the required scopes alone: `resolve` is never asked about it, so no resolver can answer it otherwise. The server decides `visible` and `known` once per request, as it arrives (a task runs with that answer, never asking again), the listings show a command only when both hold, `requires` (grouped `_meta.actions`, `afd-help`, `afd-docs`) names only commands that exist for the caller, and `tasks/get`, `tasks/update` and `tasks/cancel` on a task whose command no longer exists for its owner get the unknown-task answer. Servers without filtered listings, a resolver or credentials are unchanged, except that a resolver is no longer asked about a command name that does not exist. `tests/server_auth_hidden.rs` compares every route, in every tool strategy, with a twin server that does not have the commands.

A caller that sent values this way must send declared fields in `_meta` instead; for anything else, set it in trusted code with `McpServer::with_context_hook`. `BatchRequest::context` and `CommandRegistry::execute_batch_with_context`, the in-process batch API, are unchanged.

- **Breaking (`server` feature):** the default tool strategy is now `Grouped`, as in TypeScript (parity D5: agents see the same tool list whatever language serves it). `tools/list` lists `afd-batch`, `afd-pipe`, `afd-call` and `afd-detail`, then one tool per group; call `with_tool_strategy(ToolStrategy::Individual)` for one tool per command, which now also lists `afd-batch`, `afd-pipe` and `afd-call` first. Calls by command name keep working in every strategy.
- **`server` feature:** a call to an unknown or unexposed tool now returns TypeScript's `COMMAND_NOT_FOUND` (`Command '<name>' not found`, with close matches and `Use afd-discover to list all commands.`) instead of `Unknown tool: <name>` / `Call tools/list to see the available tools`.
- `CommandDefinition::contexts` is enforced (see Added); it was metadata only. A caller that sets no active context sees no change.

### Added

- **Confirmations (`server` feature):** `McpServer::with_confirmations(ConfirmationMode::Enforce | RequireHuman)` and `with_confirmations_key` enforce `confirm_prompt` on tool calls (`spec/command-metadata.md`, "Confirmations"). A gated call runs after the user accepts an elicitation (an `input_required` result with an HMAC-signed `requestState` on MCP 2026-07-28, a server-sent request on a 2025 stdio connection), or, under `Enforce`, after `confirm: true` or `_meta["dev.afd/confirm"]`. Otherwise it fails with `CONFIRMATION_REQUIRED` or `CONFIRMATION_DECLINED`. The feature now enables `rmcp`'s `request-state` and `elicitation` features and depends on `getrandom`.

- **Trust fields:** `CommandDefinition` gains `destructive`, `confirm_prompt` and `undoable`, with `with_destructive`, `with_confirm_prompt` and `with_undoable`. `afd-help` (full) reports `destructive` and `undoable`, `afd-docs` reports all three, and a mutation's `destructiveHint` annotation follows `destructive`. `afd-help`'s `CommandInfo` gains two optional fields, so code that builds it with a struct literal must add them.
- **Confirmation error codes:** `error_codes::CONFIRMATION_REQUIRED` and `error_codes::CONFIRMATION_DECLINED`, for servers that enforce `confirm_prompt`. Nothing emits them yet.
- **Approval error code:** `error_codes::APPROVAL_REQUIRED`, returned by the approval middleware before the handler runs (`spec/command-metadata.md`, "Approvals").
- **Approval policy and middleware** (#421, parity with TypeScript #272): `CommandDefinition::with_approval` takes an `ApprovalPolicy` (`Required`, `NotRequired`, or a function of the validated input and context through `ApprovalPolicy::when` and `when_async`), reported by `approval_mode` as `_meta.approval` on `CommandRegistry::get_tool`, in `afd-help` (full) and in `afd-docs` (`conditional` for a function). `create_approval_middleware(ApprovalMiddlewareOptions)`, behind the new default `approval` feature, holds a call with `APPROVAL_REQUIRED` and `details.approvalToken`, `expiresAt`, `summary` and, for a rejected token, `reason` (`malformed`, `invalid-signature`, `expired`, `command-mismatch`, `input-mismatch`, `actor-mismatch`, `already-used`). Tokens (`afdap1.<payload>.<mac>`, HMAC-SHA256 with an app-supplied secret of at least 32 bytes, keyed digests of the canonical input and actor, constant-time comparison) are byte-compatible with TypeScript's, so a token issued by one verifies on the other; `canonical_json` writes numbers and orders keys as JavaScript does and refuses integers a float cannot hold. Single-use by default (`ApprovalReplay::WithinTtl` allows reuse until expiry), with an in-memory or supplied `ApprovalNonceStore`, key rotation (`with_previous_secret`), `with_summarize`, `with_include_token`, `with_on_approval_required` and a security clock that never comes from the context. `CommandContext` gains `approval` (`with_approval`), which only trusted surface code sets; the MCP server never sets it from tool arguments or `_meta`. `CommandContext`'s `Debug` output redacts the token. New dependencies: `hmac`, `subtle`, `ryu-js` (ECMAScript number spelling) and `getrandom` (0.3 or 0.4) outside the `server` feature; the `approval` feature turns on `serde_json/float_roundtrip`, so floats parse exactly as JavaScript parses them; `wasm` enables `getrandom`'s browser backend (Rust 1.85 or later with `approval`). `CommandInfo` gains an optional `approval` field, so code that builds it with a struct literal must add it.

- **`server` feature:** `afd::server::McpServer` serves a `CommandRegistry` over MCP Streamable HTTP (`streamable_http_service`, a `tower` service) and stdio (`serve_stdio`), built on the official MCP Rust SDK (`rmcp` 3.7). It serves MCP 2026-07-28 statelessly and 2025 `initialize` clients from one endpoint, lists only MCP-exposed commands (`with_tools` supplies full tool definitions), returns `COMMAND_NOT_FOUND` for unknown and unexposed tools, carries `ttlMs` cache hints on `tools/list` (`with_tools_list_ttl_ms`) and refuses unlisted browser origins. The feature is off by default and needs Rust 1.88; the crate's minimum stays 1.82 without it.
- **MCP tool annotations:** `CommandRegistry::get_tool` adds `annotations` (`readOnlyHint: false`, `destructiveHint: false`) for a command with `mutation: true` (`spec/command-metadata.md`).
- **Actor, clock and random on `CommandContext`** (#401, parity with TypeScript #271/#274): `Clock` and `RandomSource` traits with `SYSTEM_CLOCK`, `SYSTEM_RANDOM`, `fixed_clock` (a `ManualClock` moved with `set` and `advance`; clones share time) and `seeded_random` (mulberry32 over FNV-1a of the UTF-8 seed, bit-for-bit the TypeScript sequence). `Actor` and `ActorKind` (`human`, `agent`, `service`, `script`, `test`), `ACTOR_KINDS`, `is_actor`, `is_actor_kind`, `ContextDefaults` and `with_context_defaults`. `CommandContext` gains `actor`, `clock` and `random` (with `with_*` builders and `clock()`/`random()` accessors); `CommandRegistry::execute` always fills the clock and random source and stamps the actor's kind as `metadata.actorKind`. The `wasm` feature reads the system time through `web-time`. The `server` feature runs tool calls as actor `agent`, configurable with `McpServer::with_actor`, `with_clock` and `with_random`.
- **Typed `actorKind`:** `ResultMetadata::actor_kind` and `TelemetryEvent::actor_kind` (it used to round-trip in `extra`); an unknown kind on the wire reads as `None`.
- **Command journal and replay** (#426, parity with TypeScript #273; `spec/journal.md`): `JournalEntry`, `JournalRecord`, `JournalTape`, `JournalContextDigest`, `JournalRange`, the `JournalSink` trait with `MemoryJournalSink`, and `FileJournalSink` (JSON Lines, with torn-line recovery) behind the new default `journal-file` feature. `create_context_digest` hashes the actor, interface, trace ID and the names (never the values) of the other context keys, as TypeScript does; `journal_actor`, `is_journal_entry`, `parse_journal`, `serialize_journal` and `serialize_journal_entry` read and write the shared format, and `spec/wire/journal.jsonl` round-trips. `CommandRegistry::set_journal(JournalRecorder)` records each call after validation and around the middleware chain (`with_record_failures`, `with_filter`, `with_redact`, `with_max_tape_reads`, `with_on_error`; `auth-*` commands are skipped by default; timed-out calls are not recorded, and a `timeout_ms` deadline covers the middleware chain only, not the journal append). `replay_journal` re-executes entries with their clock and random tapes restored and reports `same`, `different` (with per-path differences) or `error`, plus notes on tape over- and under-runs. New dependency: `sha2`.
- **MCP 2026-07-28 error codes:** `McpErrorCodes::HEADER_MISMATCH` (-32020), `MISSING_REQUIRED_CLIENT_CAPABILITY` (-32021) and `UNSUPPORTED_PROTOCOL_VERSION` (-32022).

## [0.1.0] - 2026-10-12

First release. It implements AFD contract **1.0-rc**. Published on
[crates.io](https://crates.io/crates/afd/0.1.0), with
[API documentation](https://docs.rs/afd/0.1.0/afd/). Git and path dependencies remain usable.

### Fixed

- Reject references outside named schema definitions, preventing references into uninspected annotation/default data, and enforce both `const` and `enum` when combined.

- Explicit `null` remains a value instead of taking a default or being reported missing (#282).
- Apply schema and nested defaults as-is; export defaulted parameters as optional and preserve parameter default precedence (#284).
- Empty legacy parameter lists enforce their advertised empty object schema, and validation reports every issue (#332). Applications needing open payloads should use whole-schema registration.
- Pipeline references use the shared 1,024 UTF-16-unit limit, including astral characters (#283).

### Added

- `CommandRegistry::register_with_schema` and `get_tool` preserve whole input schemas without changing existing public field types. Validation supports the required shared subset and `const`; unsupported keywords fail registration. Bootstrap schema/docs discovery uses the same authoritative schema (#311).
- Shared validation vectors exercise supported cases through actual registry dispatch and verify optional unsupported cases fail registration. Boundary tests cover defaults, null, authoritative discovery, uncapped issues, oversized numeric bounds, and UTF-16 limits.

- The wire types, which serialize exactly like `@lushly-dev/afd-core` (camelCase keys, unset fields omitted, unknown metadata keys kept in `extra`). `tests/wire_fixtures.rs` round-trips every `spec/wire` fixture:
  - `CommandResult<T>`, `ResultMetadata`, `CommandError` and `ErrorCode`;
  - `Source`, `PlanStep`, `Alternative` and `Warning`;
  - the batch, pipeline and stream result shapes.
- The result helpers `success`, `success_with`, `failure`, `failure_with`, `error`, `is_success` and `is_failure`, and the error constructors `validation_error`, `not_found_error`, `rate_limit_error`, `timeout_error`, `internal_error`, `wrap_error` and `create_error`.
- `CommandRegistry` (`create_command_registry`). It validates input against the declared parameters and applies defaults, honors `expose` and `CommandContext.timeout_ms`, runs `CommandMiddleware`, and propagates the context into batches (#251).
- Batch execution (`BatchRequest`, `BatchOptions`, `BatchResult`). A batch runs every command unless `stopOnError` is set, and honors `parallelism` and the deadline (#225, #250).
- Pipelines: `execute_pipeline`, which runs through a `CommandExecutor` callback, conditions, and variable resolution that follows `spec/pipeline-variables.md` (#250).
- Stream chunk types and helpers: `ProgressChunk`, `DataChunk`, `CompleteChunk`, `ErrorChunk` and `StreamChunk`.
- The bootstrap commands `afd-help`, `afd-docs` and `afd-schema` (`register_bootstrap_commands`).
- Handoff types and helpers, MCP JSON-RPC types with command-to-tool conversion (there is no MCP server or client), telemetry events, and `find_similar_tools`.
- `AFD_META_TOOL_NAMES`, `AFD_BOOTSTRAP_COMMAND_NAMES`, `AFD_CONTEXT_COMMAND_NAMES`, `AFD_BUILTIN_TOOL_NAMES` and `is_afd_builtin_name`, with the same names as the other languages (#292).
- The `native` feature (default), which enforces deadlines through `tokio::time::timeout`, and the `wasm` feature for `wasm32-unknown-unknown`, which measures durations with `web-time`.
- CI: `rust.yml` runs `cargo fmt --check`, clippy with `-D warnings` and the tests, each with and without default features, and checks the `wasm` build, on a pinned toolchain (#234).
- `execution_failure(message, dev_mode)` and `error_codes::COMMAND_EXECUTION_ERROR`, matching the TypeScript and C++ helpers (#306).
- `afd::CONTRACT_VERSION`, the AFD contract version from `spec/VERSION` (now `1.0-rc`). `afd-help` returns it as `contractVersion` (#313).
- `rust-version = "1.82"` declares the minimum supported Rust version. The README badge said 1.70, which no longer built (#313).
- `error_codes` holds the 42-code shared catalog of `spec/error-codes.md`, adding `COMMAND_NOT_IN_CONTEXT`, `COMMAND_NOT_ALLOWED`, `UNKNOWN_TOOL`, `AMBIGUOUS_ACTION`, `INVALID_GROUPED_CALL`, the context, batch, pipeline and stream codes. `tests/error_codes.rs` checks it against `spec/vectors/error-codes.json`, and the executors use the constants instead of string literals.

### Changed

These changes affect code that used the crate as a git dependency before this release.

- **Breaking:** types serialize exactly like `@lushly-dev/afd-core` (metadata, batch, pipeline and stream shapes). Batches continue on error by default. Public structs are `#[non_exhaustive]`, with constructors and `with_*` builders; `ResultOptions` and `FailureOptions` stay open for `..Default::default()`. A panicking handler fails only its own batch command or pipeline step (#250).
- **Breaking:** pipeline variable references follow `spec/pipeline-variables.md`, as in every language. `$input` is the request's own `input` field and never the host or caller context; `$`-prefixed literals such as `$9.99` pass through; `$$` escapes; paths follow only own JSON keys and in-bounds indices; unresolved references are omitted; `$eq`/`$ne` compare structurally; nesting deeper than 64 is rejected with `VALIDATION_ERROR` (#250).
- **Breaking:** a pipeline step with `stream: true` fails with `UNSUPPORTED_OPTION`, and every other step is skipped before any command runs, as in TypeScript. `stream: false` is still accepted (#253).
- `CommandRegistry::execute` builds its `COMMAND_NOT_FOUND` suggestion the way the TypeScript server does: up to three close matches (`Did you mean 'todo-create'? Other close matches: 'todo-list'.`) instead of a fixed hint. It matches only against commands exposed to `CommandContext.interface` when that is set, so unexposed names are not revealed. It ends with "Use afd-help to list all commands." when `afd-help` is registered and callable, otherwise "Check the command name against the available commands." (#278)
- **Breaking:** `CommandRegistry::execute` behaves like the TypeScript engine in three ways (#286). (1) `VALIDATION_ERROR` has the message `Input validation failed`. The issues and the unknown, missing and expected fields move to `suggestion`, formatted as TypeScript formats them. Each `details.errors` entry gains a Zod `code` (`invalid_type`, `invalid_value`, `too_small`, `too_big` or `invalid_format`), plus `expected` for `invalid_type`. Paths are joined with dots (`tags.1`, or `(root)` for the whole input), and empty `missingFields`/`unexpectedFields` are omitted. (2) Handlers and middleware no longer receive keys the parameters do not declare, nor keys missing from a nested schema's `properties` unless it has `additionalProperties`. A command that read undeclared keys must declare them. (3) An unknown command name is cut to 128 UTF-16 code units in the error message. `find_similar_tools` and `calculate_similarity` count UTF-16 code units, so names with emoji or other characters outside the Basic Multilingual Plane get the same suggestions as in TypeScript. `packages/rust/README.md` lists the differences that remain.
- **Breaking:** a panic in `execute`, a batch or a pipeline returns `COMMAND_EXECUTION_ERROR` with "An internal error occurred" instead of `INTERNAL_ERROR`. The panic payload is never included (#306).
- `is_success` and `is_failure` test only the `success` flag, as in TypeScript (#306).
- **Breaking:** `BatchRequest` and `PipelineRequest` deserialize only envelopes that TypeScript accepts (`spec/vectors/batch-controls.json`). A command name must not be blank. An optional field may be omitted but not `null`, except a pipeline's `input`. A step `input` must be an object, `timeoutMs` a non-negative number, and `onProgress` unset. An invalid batch returns `INVALID_BATCH_REQUEST` with TypeScript's message, "Invalid batch request envelope" (#317).
- With the `native` feature, deadlines and durations use `tokio::time::Instant`, the clock `tokio::time::timeout` enforces them with, so they follow a paused Tokio test clock (#317).

### Fixed

- Batch concurrency, stop and deadline controls are honored, and a pipeline with `parallel: true` fails with `UNSUPPORTED_OPTION` instead of running sequentially (#225).
- Deadline options (`timeoutMs`) fail with `UNSUPPORTED_OPTION` before anything runs in builds without the `native` feature (#225).
- Stream serialization is corrected, and JSON-RPC request IDs may be negative integers (#225).
- Fuzzy matching of unknown command names is bounded, so an oversized name no longer blocks for seconds. Echoed names are truncated (#232).
- The `wasm`, MCP and handoff types are fixed (#251).
- Pipeline deadlines behave as in TypeScript: `timeoutMs: 0` fails step 0 with `PIPELINE_TIMEOUT` instead of skipping every step, and a step that ends past the deadline skips every later step with that error (#317).
- A `when` condition treats a first operand that is not a reference (`"$$prev"`, `"text"`) as absent, and `$eq`/`$ne` compare numbers by value (`2` equals `2.0`), as in TypeScript. `tests/pipeline_vectors.rs` and `tests/batch_controls_vectors.rs` load the shared `spec/vectors` files (#317).
- `CommandRegistry::execute` catches a panic in a middleware layer or the handler, including one raised while building the future and one under `timeout_ms`, instead of letting it unwind to the caller (#306).
