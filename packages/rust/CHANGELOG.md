# Changelog

All notable changes to the `afd` Rust crate are documented here. The crate is versioned independently of the npm packages and other implementations. Rust releases are distributed through [crates.io](https://crates.io/crates/afd) and use tags of the form `rust-vX.Y.Z`.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this crate adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a minor release may break the API.

## [Unreleased]

### Added

- **`secret` commands in the journal (`spec/journal.md`; TypeScript #2576).** `CommandDefinition::as_secret()` sets the new `secret` field (default `false`; a `bool`, so a value of another type cannot be declared, and not reported in any tool, `afd-detail` or `afd-help` output). A `JournalRecorder` never records a call to such a command unless it has a redactor (`with_redact` or the new `with_redact_info`), whatever `with_filter` says; the default filter still skips `auth-*`. The registry reads the declaration from the command it runs, never from its name or the context, and passes it to the recorder. `with_redact_info(|record, info| ...)` is told `JournalRedactInfo { secret }` with each record; `with_redact` keeps its one-argument signature, so existing callers compile unchanged, and each replaces a redactor set before. The recorder runs inside the registry, so unlike TypeScript the answer is always known (`bool`, never unknown). **Caution:** a redactor set with `with_redact` now admits calls to secret commands without being told which they are, so a redactor that keeps records it does not recognise should move to `with_redact_info` and drop or sanitise those whose `info.secret` is `true` (Umbel's host and Loam mail's engine now do). A secret call never puts its clock readings or random values on a recording parent's tape (every recording ancestor, not only the nearest): given the parent's recording sources themselves, it runs on the sources under them and each such tape is marked `truncated`; given them inside a host's own wrapper, each tape refuses its readings and is marked `truncated` only once the call reads through it. A recorded secret call keeps its reads on its own entry. Two mechanisms hold this: the call runs on the sources under the recording ones (a hidden, defaulted `journal_taping` method on `Clock` and `RandomSource`, answered only by the journal's sources and forwarded by `Arc`), and its middleware steps, handler and its recorder's own timing run in a secret scope (taken again by every step, so a middleware that moves the rest of the chain to another task does not leave it) in which a tape accepts readings only from its own call's scope or a non-secret call inside it, so a host's own clock or random source wrapping a recording one leaks nothing either, not even to a sibling secret call's tape. `CommandDefinition::execute`, which calls a handler directly, does the same for a secret definition. A task the secret call spawns runs outside its scope, so its reads through a host's wrapper around a recording source can still reach a parent's tape. `JournalRecorder::records` still answers for the filter alone. Behaviour changes only for commands that declare `secret`.
- **MCP task post-completion retention and execution run budget ([#2500](https://github.com/lushly-dev/afd/issues/2500)).** `TaskOptions` now separates execution run budget (`with_max_run_ms`, getter `max_run_ms()`, default `DEFAULT_TASK_MAX_RUN_MS` = 1 hour) from post-completion retention (`with_ttl_ms`, default `DEFAULT_TASK_TTL_MS` = 1 hour). A new task's initial `ttlMs` (counted from `createdAt`) starts at `max_run_ms + ttl_ms` (2 hours by default) and tightens atomically on terminal transition to `(finished_at - created_at) + ttl_ms` (still capped at `expires_at + grace` when `with_ttl_capped_at_token_expiry` is set), so a task that finishes near the end of its run budget keeps its result readable for a full hour after finishing. A task still working when `max_run_ms` elapses is stopped and completes with `TIMEOUT` (`retryable: true` for reads or unstarted tasks, `false` for mutations that started), retained for `ttl_ms` after stopping.
- **`JwksKeySource`, `JwksKeySourceOptions` and `JwksLoader` (`server-auth`; `spec/authorization.md`, M3 rule 3).** The counterpart of TypeScript's `jwksKeySource(load, options)` and Python's `jwks_key_source`: a `KeySource` over the JWKS document a host's `JwksLoader` fetches (any `Fn(&str) -> impl Future<Output = Result<Value, E>>` with a `Display` error, or a type of the host's), so a host no longer writes its own cache. AFD still opens no socket. Per issuer, loaded keys are used for `with_max_age_ms` (default 5 minutes); an unknown `kid` loads again at most once per `with_min_refetch_interval_ms` (default 30 seconds), so a storm of made-up `kid`s costs one load per interval; concurrent callers that need a load share one call of the loader; a failed load (the loader's error or panic, or a document that `StaticKeys::from_jwks` would refuse) keeps the last good keys for up to `with_max_stale_ms` (default 1 hour, at least the maximum age: `JwksKeySource::new` refuses less), and with none, keys older than that, or a failed load for an unknown `kid` the answer is `KeyError::Unavailable`. Unlike TypeScript, the loader is given the issuer and the state is kept per issuer, so one source (clones share it) can serve several issuers; and a load runs while a caller awaits it, resuming with the next caller if every waiting one is dropped. `StaticKeys` now looks keys up by `kid` in a map. `tests/auth_jwks.rs` covers each rule on a manual clock, including concurrent loads and an unknown-`kid` storm.
- **`CommandDefinition::map_handler`.** Replaces a definition's handler with a wrapper of it and keeps every other field, so a host registering a definition built elsewhere can run code around its handler; Umbel puts its compiled-plugin turn and deadline around a plugin's finished definitions this way. TypeScript and Python reach `handler` as a field.
- **`McpServer::with_instances(ServerInstances::Single | Multiple)` and `McpServer::with_confirmation_key` ([#2242](https://github.com/lushly-dev/afd/issues/2242)).** `ServerInstances::Multiple` fails `McpServer::validate()` (and `try_streamable_http_service`, `streamable_http_service`, `authorized_http_service`, and `serve_stdio`) when active confirmations, `ApprovalRelay::McpElicitation`, or in-memory approval nonce stores (including inside `compose_middleware`, and beside `HumanRelay` even under `ApprovalReplay::WithinTtl`) rely on per-process defaults. When `with_instances` is omitted, starting an HTTP service logs one warning per process to stderr (`ServerInstances::Single` silences it; `serve_stdio` logs nothing). `McpServer::with_confirmations` now preserves an already-configured shared key.
- **`CommandError.recovery` ([`spec/recovery.md`](../../spec/recovery.md)).** A failed command can now carry the step its `suggestion` describes in a form a program can follow and a test can check, as `recovery: Option<Box<Recovery>>` (boxed, as `cause` is, so an error without one grows by one pointer), set with `CommandError::with_recovery`. `Recovery` has one variant per kind, each holding only its own fields, so a recovery that puts `command` on a `retry` cannot be built: `Call` (`command`, `input`, `needs`, `then_retry`), `FixInput` (`input`, `needs`), `Retry` (`after_ms`), `External {}` and `Stop {}`. Every variant is `#[non_exhaustive]`, so code outside the crate builds one only through its constructors, `Recovery::call`, `call_with`, `fix_input`, `retry`, `external` and `stop`, and a field added to a kind later breaks no caller; it reads the fields by pattern with `..` (`Recovery::Call { command, .. }`). `call`, `call_with` and `fix_input` return `Result<Recovery, InvalidRecovery>` and refuse what `$defs/recovery` refuses: an empty `command`, an empty `input` or one carrying `confirm`, an empty `needs` or one with an empty or repeated name, and a `fix-input` with neither `input` nor `needs`. A value changed through a `&mut` pattern after it was built is not checked again; `Recovery::validate` checks it. Neither checks rule 3 (`input` and `needs` naming the same field), which the schema does not check either. It serializes as the spec's object (`{"kind": "call", "command": "lane-resume", "thenRetry": true}`, unset fields omitted). Reading follows rule 7: a recovery that breaks `$defs/recovery` (an unknown kind or member, a `null` member, a member of the wrong JSON type or on the wrong kind, an empty `input` or one with `confirm`, an empty, repeated or empty-string `needs`, a `fix-input` that sets neither, a negative or fractional `afterMs`) reads as `recovery: None`, on the error and on its `cause`, and the rest of the error is kept, `suggestion` included. No member is coerced: `"30000"` is not a number and `"true"` not a boolean. `afterMs` reads as JSON Schema reads an integer, so `30000.0` reads as `30000`; an `afterMs` above 2^53 − 1, the schema's maximum and `MAX_AFTER_MS`, is refused however it is written, and `Recovery::retry` refuses one too. The error-level rules tying `retryable` to `retry` and `stop` are not enforced on read. `Recovery::kind` and `RECOVERY_KINDS` name the kinds, and `is_command_recovery(&Value)` says whether a JSON value is a recovery a reader keeps, as TypeScript's `isCommandRecovery` and Python's `is_command_recovery` do. `CommandError` is `#[non_exhaustive]`, so the new field breaks no code outside the crate; a `match` over `Recovery` needs a wildcard arm, since new kinds may be added. A context hook's refusal now passes `recovery` to the caller beside `code`, `message`, `suggestion` and `retryable`. `tests/recovery_vectors.rs` runs the `valid`, `normalizes` and `invalid` lists of `spec/vectors/recovery.json` against `spec/schema/error.json`: each valid error round-trips unchanged, and each normalizing and invalid error reads to exactly its `readsAs`, with every recovery on an error or its cause kept exactly when it passes `$defs/recovery`. The schema validator it shares with `tests/wire_fixtures.rs` now supports `anyOf`, `uniqueItems`, `minItems` and `minProperties` and refuses a schema keyword it does not implement.
- **The engine's own errors carry a recovery ([`spec/recovery.md`](../../spec/recovery.md), "Engine errors").** Each error the registry, the MCP server, the router, the middleware, the confirmation and approval steps, the context commands and `DirectClient` emit now sets the recovery the spec's table gives, and a batch item or pipeline step carries its call's. `COMMAND_NOT_FOUND` at lookup (a call, `afd-call`, a batch item or a pipeline step) is a `call` of `afd-discover` for an MCP caller, of `afd-help` for an in-process caller that can call it, and none otherwise; the suggestion and the recovery come from the one decision, so they always name the same command. A grouped tool's unknown action and `afd-detail`'s per-entry not-found set none. `COMMAND_NOT_EXPOSED`, `CALL_NOT_GRANTED`, `CONFIRMATION_REQUIRED` and `APPROVAL_UNAVAILABLE` (`no-approval-step`, `admission-mismatch`) are `external`; `input-not-canonical` sets none. `COMMAND_NOT_IN_CONTEXT` is a `call` of `afd-context-list` only when the caller can call it (registered, exposed to its interface, in its context, existing for it and in its listing), which now also decides whether the suggestion names it; its "or afd-context-enter to switch" clause appears only when the caller can call `afd-context-enter` by the same test. `afd-context-enter`'s `CONTEXT_NOT_FOUND` is a `call` of `afd-context-list`, and its `CONTEXT_DEPTH_EXCEEDED` a `call` of `afd-context-exit` with `thenRetry`, each only when the server's filters for the caller (which commands exist for it, and its listing) admit that command; otherwise the suggestion leaves the command out ("Available contexts: …", "Leave a context before entering another") and there is no recovery. `CONFIRMATION_DECLINED`, a declined `APPROVAL_REQUIRED` and a `DirectClient` whose `on_approval_needed` hook returns `Ok(false)` are `stop` (a hook that errors or panics keeps the hold's `external`). An `APPROVAL_REQUIRED` the caller reshapes (an `afd-batch` or `afd-pipe` refused up front, a gated step to call on its own, an approver's token sent the wrong way) sets none; every other one is `external`. The rate limiter's `RATE_LIMITED` is a `retry` with `afterMs` the suggestion's whole seconds × 1000, or with no wait when its client capacity is full, and the MCP task limit's is a `retry` with no wait. `rate_limit_error()` and `CommandError::rate_limited()` set `{kind: "retry"}`, with `afterMs` when given the wait; the other helpers set none. Every error keeps its `retryable`. The default server instructions' first sentence now reads "`<name>` is an AFD server. Every tool returns a CommandResult as JSON text: { success, data, error: { code, message, suggestion, recovery } }; follow error.suggestion to recover. When error.recovery is present, it is the same step in a form a program can follow." `tests/dispatch_vectors.rs` and `tests/tool_strategies_vectors.rs` compare each case's `recovery` (`null`: none), and the dispatch registry surface registers the context commands as plain commands (`setup.contextCommands: "plain"`); `tests/app_calls_vectors.rs` already compares the whole refusal.
- **`DirectClient` and pipeline deadlines fire the command's cancellation signal; pipelines stop at a cancelled call ([#1599](https://github.com/lushly-dev/afd/issues/1599)).** A `DirectClient` call with `timeout_ms` gives the command a child of the caller's signal and fires it when the call's deadline passes (both attempts and the approval wait); the caller's own signal is never fired. The caller's signal also ends the approval wait (`COMMAND_CANCELLED`), as in TypeScript. `execute_pipeline_with_cancellation` (`execute_pipeline` delegates to it) skips a step, and every later one, with `COMMAND_CANCELLED` once its signal has fired (`spec/execution-controls.md`), and fires that signal when the pipeline's deadline passes with steps still to run; the MCP server's `afd-pipe` passes a child of the call's signal when there is a deadline, else the call's own.
- **Stream executor, `afd::execute_stream` and `CommandRegistry::execute_stream` ([#1601](https://github.com/lushly-dev/afd/issues/1601)), as TypeScript's `executeStream` behaves:** the command runs once through `CommandRegistry::execute` (every check applies), then a lazy `Stream` yields one data chunk per array item (or one for any other data) and a complete chunk with the result's confidence, reasoning and metadata, or one error chunk for a failure (`recoverable` when retryable). The call's cancellation signal stops it with `STREAM_ABORTED` before execution, after it or before a data chunk (`resumeFrom` in the data phase); `StreamExecutorOptions::timeout_ms` gives the command a child of that signal, fires it at the deadline and ends the stream with `STREAM_TIMEOUT` even if the command ignores it (`0` is a deadline already passed, as in TypeScript; `native` feature, otherwise `UNSUPPORTED_OPTION`). Once the last data chunk is sent, the complete chunk follows. A streamed command's result is not checked against its output budget (`spec/output-budgets.md`, B7), as in TypeScript and C++; the ask is still validated and the handler still sees its budget. Nothing runs until the stream is polled, and dropping it stops the command.
- **`AsyncFileJournalSink` and `FileJournalSink::with_sync_data` ([#1764](https://github.com/lushly-dev/afd/issues/1764)).** `AsyncFileJournalSink` (the `native` and `journal-file` features) runs a `FileJournalSink`'s blocking calls on Tokio's blocking pool, so an append, a read of the whole file and a shared sink's wait for its lock never hold an async worker; a fair async lock keeps appends in the order calls arrived. `with_sync_data(true)` waits for each append to reach the device (`File::sync_data`); without it an append is handed to the OS before it returns, which survives a process crash but not a power loss. `FileJournalSink`'s docs now state this durability policy. `native` enables Tokio's `rt` and `sync` features for it.

### Changed

- **Pre-1.0 breaking (behaviour):** `wrap_error` now returns a generic non-retryable `INTERNAL_ERROR` (`"An internal error occurred"`, `retryable: Some(false)`, operator-facing suggestion) instead of forwarding raw `Display` text into an agent-visible message marked retryable.
- **Pre-1.0 breaking (`server` feature, [#2500](https://github.com/lushly-dev/afd/issues/2500)):** `TaskChange::{Completed, Failed, Cancelled}` gain `ttl_ms: Option<u64>`, applied by `TaskRecord::apply` and custom `TaskStore::update` implementations to tighten `ttl_ms` on terminal transition. Custom `TaskStore` implementations and callers constructing `TaskChange` directly must handle or set `ttl_ms` (`None` keeps the existing `ttl_ms`).
- **One compiled input validator, built once at registration ([#1762](https://github.com/lushly-dev/afd/issues/1762)).** Replaced the separate legacy `parameters` validator and raw-`Value` whole-schema walker with a single arena-backed `CompiledSchema` compiled once at registration (`register`, `register_with_schema`, `register_with_schemas`, `set_context_fields`, and MCP meta-tools) and shared in an `Arc`. Legacy `parameters` are converted to whole JSON Schemas (including `JsonSchema::min_length`/`max_length` on arrays mapped to `minItems`/`maxItems`), `pattern` regexes are pre-compiled per node, `format` is treated as an annotation (unblocking `schemars`-generated schemas), and valid inputs move through validation without cloning. Legacy `parameters` now emit the same Zod-style `VALIDATION_ERROR` diagnostics as whole schemas. All 116 `spec/vectors/validation.json` executions (now including `pattern` and `format`, leaving 5 unsupported optional cases) pass. On `cargo bench --bench execute` (50-item payload), `0 middleware` drops from 559 allocations / 42,138 bytes / ~64 µs per call to 6 allocations / 2,125 bytes / ~44 µs per call.

### Fixed

- **`ServerInstances::Multiple` runtime guard retryability:** the runtime per-process approval-state guard in `CommandRegistry::execute` now returns `retryable: Some(false)` with an operator-facing suggestion instead of `retryable: Some(true)` with `"Please try again."`.
- **`DirectClient` `timeout_ms`** ([#1599](https://github.com/lushly-dev/afd/issues/1599)): `0` is no deadline, as `CommandRegistry::execute` reads it (it timed out at once), and a caller's deadline replaces the registry's `default_timeout_ms` for the call (the default applied too).
- **Journal replay of streamed budgeted calls** ([#2361](https://github.com/lushly-dev/afd/issues/2361)): `replay_journal` now skips the B5 output-budget result check when replaying a successful budgeted entry that carries no B6 `dev.afd/outputBudget` report (buffered `execute_stream`, B7), matching TypeScript and C++ so over-budget streamed calls replay without falsely diverging while normal budgeted calls still run B5.

## [0.3.0] - 2026-11-24

Implements AFD contract **1.0-rc**.

### Changed

- **Breaking: middleware passes the context to `next`, and shares the input ([#1764](https://github.com/lushly-dev/afd/issues/1764), [#1600](https://github.com/lushly-dev/afd/issues/1600)).** `MiddlewareNext` is now `Fn(CommandContext)`, and a `CommandMiddleware` receives the validated input as `Arc<serde_json::Value>`. A middleware calls `next(context)` with the context it was given, refined if it needs to be (a trace ID, a field of `extra`), and the layers after it and the handler see that context; before, `next()` took no arguments and every layer saw a copy made when the chain was built. To migrate, write `next(context)` for `next()` (`next(context.clone())` where the middleware reads the context afterwards or calls `next` more than once), and read the input through the `Arc` (`input["id"]`, `&*input`). Every step of the chain (each inner layer and the handler) restores the call's own state from the context `execute` built: the crate-owned state (output budget, approval admission, the caller's hidden-command and scope filters, the active-context scope, the server's default-deadline choice, and the call's cancellation signal, whether the caller's, the deadline's or a task's, which a middleware cannot replace), `interface`, `credentials`, `clock` and `random`. So a middleware that passes a new or stale context cannot strip them from the layers after it or detach a journaled call's tape; it refines only the other public fields (`trace_id`, `actor`, `extra`, `approval`, and `timeout_ms`, which reaches only the calls the handler makes, since the call's own deadline is set before the chain). The journal records the context as it was before the chain, so a trace ID a middleware sets is not the journaled `traceId`. The chain no longer deep-copies the input and the context at each layer: a call makes one copy of the input for the handler (none without middleware), and the context moves down the chain.
- **Breaking: `PipelineContext::previous_result` is now a method ([#1764](https://github.com/lushly-dev/afd/issues/1764)).** The field became `previous: Option<usize>`, the position in `steps` of the previous successful step, so `$prev` reads that entry instead of a clone of every successful step. `push_step` sets it; a hand-built context sets `previous` instead of `previous_result`. It is a position, so a caller that removes or reorders `steps` afterwards must update it.
- **Breaking (App-to-app calls):** `ExposeOptions` gains the public field `apps`, so a struct literal needs `..Default::default()` or the builders, and `CommandInterface` gains `Apps`, so a `match` over it needs the arm or a wildcard. Serialization is unchanged: `apps` is written only when `true`.
- **Breaking (`server` feature, [#532](https://github.com/lushly-dev/afd/issues/532)):** `afd::server::confirmations::confirmation_binding(command, input, principal)` takes the call's principal binding (`afd::principal_binding`) as its third argument and returns the `afd.confirm.v3` associated-data layout `["afd.confirm.v3", <principal binding>, [[command, input as sent], ...every command the call runs]]`. A confirmation `requestState` is now one state per call that also carries the form-mode approval relay's answers (`{ p, a }`, as TypeScript's round state). A state minted before this change does not verify, so its call is asked again.
- **Breaking:** `JournalEntry` and `JournalRecord` gain `output_budget` (the effective output budget, `None` for a call without one), `context` and `context_omitted` (declared context fields); code that builds either with a struct literal must set them (`None`).
- **Breaking:** `CommandInfo` gains `title`, `output_budget` and `first_class`, `HelpOutput` gains `tool_strategy`, `first_class_tools` and `context_fields`, and `McpTool` gains `title`; code that builds any of them with a struct literal must set the new fields (`None`).
- **Breaking (`server` feature):** the default tool strategy is now `Grouped`, as in TypeScript (parity D5: agents see the same tool list whatever language serves it). `tools/list` lists the five meta-tools first, then one tool per group; call `with_tool_strategy(ToolStrategy::Individual)` for one tool per command, which also lists the five meta-tools first. Calls by command name keep working in every strategy.
- **Breaking (MSRV 1.85, was 1.82):** `hmac` moves to 0.13 and `sha2` to 0.11, which need Rust 1.85. Token and digest bytes are unchanged, and neither crate appears in the public API.
- **Breaking (behaviour, `spec/execution-controls.md`, #2130):**
  - `McpServer` enforces a default per-command deadline of `30000` ms (`McpServer::with_default_timeout_ms`, `None`/`Some(0)` disables; MCP Tasks remain bounded by their task TTL). `CommandRegistry` also supports `set_default_timeout_ms` / `default_timeout_ms`.
  - Deadlines cancel a linked `CancellationSignal` (`CancellationToken` alias) on `CommandContext` in addition to dropping the timed-out future, and return `TIMEOUT` (`retryable: true`, `details: { command, timeoutMs }`).
  - Pre-cancelled single commands and batches skip unstarted middleware/handlers and return `COMMAND_CANCELLED` (`retryable: false`, `durationMs: 0` for unstarted batch items).
  - Batch execution and `McpServer`'s `afd-batch` enforce `DEFAULT_MAX_BATCH_SIZE` (`500`) and `DEFAULT_MAX_BATCH_PARALLELISM` (`16`) before confirmations or dispatch (`INVALID_BATCH_REQUEST`, `retryable: false`), configurable via `CommandRegistry::set_max_batch_size` / `set_max_batch_parallelism` and `afd::check_batch_limits`.
  - Validation caps reported issues at `DEFAULT_MAX_VALIDATION_ISSUES` (`100`, configurable via `CommandRegistry::set_max_validation_issues`) with `details.truncated: true`, `details.limit`, `details.totalErrors`, and an explicit truncation notice in `suggestion`.
- **Breaking (behaviour): `ApprovalMiddlewareOptions::with_include_token` defaults to off on MCP ([#1665](https://github.com/lushly-dev/afd/issues/1665); `spec/command-metadata.md`, "Approvals", rule 6).** When `with_include_token` is not called, `APPROVAL_REQUIRED` omits `details.approvalToken` for calls whose `context.interface` is `CommandInterface::Mcp` (non-approver MCP callers), matching TypeScript, Python and C++; non-MCP callers and server-named approvers still receive the token. Call `with_include_token(true)` to opt in to returning the token on MCP calls.
- **Breaking (behaviour): approval admission ([#1886](https://github.com/lushly-dev/afd/issues/1886); `spec/command-metadata.md`, "Approvals"; see "Added").** A registry without the approval middleware now refuses a command whose approval policy is neither unset nor `NotRequired` with `APPROVAL_UNAVAILABLE` (`no-approval-step`) before the handler runs; it ran the handler before. A command missing from the middleware's commands list is now held by its own policy; it was not held. A retry placed after the approval middleware is refused with `admission-mismatch` instead of running the handler again; put retrying middleware before it. An input the middleware would hold that has no exact canonical JSON answers `APPROVAL_UNAVAILABLE` with `input-not-canonical`, not `COMMAND_EXECUTION_ERROR`. Replaying a journal against a registry without the middleware answers `APPROVAL_UNAVAILABLE` for each entry of a gated command. Add one approval middleware per registry: a second one none of whose policies gate a command admits nothing, but two that both gate a command's own policy each ask for it.
- **Breaking (behaviour, `server` feature):** a call to an unknown or unexposed tool now returns TypeScript's `COMMAND_NOT_FOUND` (`Command '<name>' not found`, with close matches and `Use afd-discover to list all commands.`) instead of `Unknown tool: <name>` / `Call tools/list to see the available tools`.
- **Breaking (behaviour):** `CommandDefinition::contexts` is enforced (see Added); it was metadata only. A caller that sets no active context sees no change.
- **Target-selected WebAssembly time source and crate lints ([#1765](https://github.com/lushly-dev/afd/issues/1765)):** `afd` now selects `web-time` automatically on `wasm32-unknown-unknown` (by target `cfg`, rather than requiring the `wasm` feature for monotonic and wall-clock time; `wasm` continues to enable `getrandom/wasm_js` for `approval`). `[lints.rust]` now sets `unsafe_code = "deny"` and `missing_docs = "warn"`, and `src/lib.rs` sets `#![forbid(unsafe_code)]`.
- **Per-call allocation ([#1764](https://github.com/lushly-dev/afd/issues/1764)).** Input schemas registered with `register_with_schema` are shared, not copied for every call; the middleware list is taken with one reference count; the output budget counts the canonical length of a result's data without serializing it to a `Value` or a string (`cargo bench --bench execute` measures `execute` with 0 and 4 middleware, with and without a budget).
- **Always-on ECMAScript number formatting and round-trip float parsing (#578):** `ryu-js` is now a regular dependency (instead of optional under `approval`) and `serde_json`'s `float_roundtrip` feature is always enabled, so floats parse and format as JavaScript numbers across all feature sets (for approval digests, output budgets and journal context caps).

### Added

- **Built-in middleware, `afd::middleware` ([#1600](https://github.com/lushly-dev/afd/issues/1600)), as TypeScript and C++ ship it:** `default_middleware` (`create_auto_trace_id_middleware`, `create_logging_middleware`, `create_timing_middleware`, in that order), `create_retry_middleware` (capped exponential backoff with jitter; the wait ends when the call's cancellation signal fires; `tokio::time::sleep` with `native`, or `RetryOptions::sleep`), `create_rate_limit_middleware` (fixed windows per key, at most `max_keys` keys, `RATE_LIMITED` with `retryable: true`), `create_telemetry_middleware` (a `TelemetryEvent` per call from the context's clock; a panicking sink is ignored), `compose_middleware` (restoring the call's state between its layers) and `random_uuid`. The logging and telemetry middleware see a command that panics (an `Error` line, an `UNHANDLED_ERROR` event) and let the panic reach the registry. The trace-ID, logging, timing and rate-limit middleware read their own clock and random source, and the telemetry middleware reads the journal's untaped clock while a journal records or replays the call (`replay_journal` now sets one), so a journaled call's tape holds only what the command read, and a journal recorded without these middleware replays with them. The journal records the caller's trace ID, not one the middleware makes, and the registry does not stamp the trace ID on the result's metadata. There is no tracing middleware: a host wraps calls in `tracing` or OpenTelemetry spans in its own.
- **`error_codes::APPROVAL_UNAVAILABLE`**, which joins the shared catalog (`spec/command-metadata.md`, "Approvals"): a server engine refuses a command whose declared approval policy is not `not-required` when no approval step admitted the call.
- **A declared approval policy holds without the approval middleware** ([#1886](https://github.com/lushly-dev/afd/issues/1886); `spec/command-metadata.md`, "Approvals"). `CommandRegistry::execute` gives every call (each batch item, pipeline step and nested call too) its own admission record, and dispatches a command whose policy is neither unset nor `NotRequired` only when an approval step admitted that call to run that command on that canonical validated input. The admission is taken as the handler is dispatched, so one admission runs one handler. Otherwise the call answers `APPROVAL_UNAVAILABLE` (`retryable: false`) before the handler runs, with `details.reason` `no-approval-step`, or `admission-mismatch` when an approval step ran but did not admit this dispatch (a retry or another input after it); a policy function is not evaluated there. `create_approval_middleware` decides from the policy and `confirm_prompt` of the command each call runs, also for commands registered after it was built, and holds a call when either that policy or the one its commands list gives holds it. The list is optional: `ApprovalMiddlewareOptions::from_secret`. A gate the list alone gives a command is taken at dispatch the same way. When the approval middleware would hold a call whose input has no exact canonical JSON (an integer a JavaScript number cannot hold, such as 2^53 + 1), no approval can be bound to it, so the middleware answers `APPROVAL_UNAVAILABLE` with `details.reason` `input-not-canonical` (before, `COMMAND_EXECUTION_ERROR`) without asking anyone, for a single call and for an up-front `afd-batch` or `afd-pipe` step; a call its policy lets through still runs, its admission compared by value. A command missing from the list is now held by its own policy, and middleware that retries belongs before the approval middleware. Only an approval middleware whose own policies (the command's and its list's) may gate a call admits it, and it computes the canonical input only then; the registry keeps every such admission and dispatches only when there is at least one and all name this command and input, and every approval step that ever admitted the call admitted it again since the last dispatch, so a later middleware neither replaces an earlier one's binding nor admits a retry placed between them. Over MCP, `afd-batch` and `afd-pipe` from a client that can elicit are planned up front whatever their commands declare, so a step gated only by the middleware's list is asked about before any step runs, and every step whose input is known up front runs on the input validated then (a pipeline step whose input reads an earlier step's data is validated when it runs).

- **The decision before dispatch for a host's own layer (feature `server-auth`; `spec/authorization.md`, M6, "A host's own layer"; Umbel phase 5's follow-up of 2026-11-08):** `McpServer::pre_dispatch_check()` returns a `PreDispatchCheck`, the bearer layer's own decision before dispatch, for a host whose own HTTP layer admits credentials (`Authorization::admit`) instead of the bearer layer, such as Umbel's gateway-trusted mode. After admitting the credentials and reading the body, the host calls `PreDispatchCheck::decide(&parts, &body)`, which returns `PreDispatch::Proceed` or `PreDispatch::Respond(response)`: the bearer layer's 403 naming every missing scope of a `tools/call` (every step of `afd-batch` and `afd-pipe`, grouped actions, hybrid tools, hidden and unknown names on the required scopes alone), its 400 for a JSON-RPC batch, or its 413 over the authorization's body cap, byte for byte. `BearerLayer` now runs the same `PreDispatchCheck`, so the two cannot drift. `PreDispatchCheck::max_body_bytes()` is the cap to read a body under; a longer body is the bearer layer's 413. Under the cap, only the credentials admitted for the server's own authorization are decided; any other request proceeds, and the server refuses it (M1). A host whose callers use another scheme sets the 403's challenge with `PreDispatchCheck::with_challenge(ScopeChallenge)`: `ScopeChallenge::new(scheme)?.with_param(name, value)?` renders `<scheme> <params>, error="insufficient_scope", scope="<missing>"` (never `Bearer`, no `resource_metadata`, `scope` under M5's rules); the body's suggestion comes from `ProtectedResource::with_scope_source`. - **`ProtectedResource::with_scope_source` (feature `server-auth`; Umbel phase 5 step 4):** a host whose callers are not token holders (Umbel's gateway-trusted mode, where a gateway asserts each caller's scopes) names what they obtain to gain a scope. - **MCP Tasks (`spec/command-metadata.md`, "Tasks"; the Tasks extension `io.modelcontextprotocol/tasks`, SEP-2663; Umbel phase 5 step 0e):** `CommandDefinition::with_task(TaskSupport)` (the public field `task: Option<TaskSupport>`, `task_support()`; `TaskSupport::{Never, Optional, Required}`, reported as `task` in the tool's `_meta`, grouped `_meta.actions` and `afd-detail` when set) says whether an MCP `tools/call` may run as a task. Registration (`register` and the schema variants, through `validate_person_gates`) refuses `Optional` or `Required` beside `confirm_prompt`, an approval policy other than `NotRequired`, or a `confirmation_mode`, naming the command and the setting: a task never asks a person. With the `server` feature, `McpServer` declares the extension when an MCP-exposed command may be a task and serves `tasks/get`, `tasks/update` and `tasks/cancel` (`afd::server::tasks`). Only an MCP 2026-07-28 request whose own `_meta` client capabilities declare the extension gets a task (never a 2025 request, whatever it declared at `initialize`); otherwise `Optional` runs inline and `Required` is JSON-RPC `-32021` naming the extension. A call routed to one command (its tool, a hybrid first-class tool, a grouped tool, `afd-call`) becomes a task after every check an inline call meets before dispatch (the bearer layer's 403, the context hook, the scope check, the context check, the confirmation gate); an `afd-batch` or `afd-pipe` step naming a `Required` command fails the whole request with `INVALID_BATCH_REQUEST` or `INVALID_PIPELINE_REQUEST` before any step runs, and an `Optional` step runs inline. The task id is 128 bits from the OS random source (26 characters of lowercase base32); the record (`TaskRecord`: id, owner, command, status, `statusMessage`, times, `ttlMs`, `pollIntervalMs`, `cancelRequested`, result or error; no token, credentials or input) is in the `TaskStore` before `CreateTaskResult` is returned, and a store that fails or is full fails the call with nothing run (`INTERNAL_ERROR` or `RATE_LIMITED`, both retryable). The owner (`TaskOwner`) is the call's `principal_binding`; credentials that cannot be bound get a generic `-32603`. The command runs through `CommandRegistry::execute` on a fresh context with the call's actor, credentials, trace id, declared context fields and output budget ask; its `CancellationSignal` fires on `tasks/cancel` (in this process at once, in another through the store's `cancelRequested`), when the task's `ttlMs` ends (the task is then gone) and at the credentials' `expiresAt`, which completes it with the failure `TASK_TOKEN_EXPIRED` (a token that expired before the task started never starts the handler, and a result arriving after expiry is not delivered; retryable unless the command is a mutation whose handler started, whose suggestion then says to check its effect); the server stops the handler at its next `.await`. Results are the inline `CallToolResult` (`completed`, with `isError` for a failed `CommandResult`; `failed` only for a JSON-RPC error; `cancelled` after a `tasks/cancel` that stopped it, while a handler that had already returned keeps its result); a result larger than `TaskOptions::max_result_bytes` (1 MiB) is replaced by an `INTERNAL_ERROR` that says the command ran. `CommandContext::report_progress` sets `statusMessage` and `lastUpdatedAt` (at most `MAX_PROGRESS_MESSAGE_BYTES`, 1024); `CommandContext::cancellation` and `is_cancelled` read the signal (`afd::CancellationSignal`, `afd::Cancelled`). `tasks/*` requests pass the checks of a request that names no command (fail closed without admitted credentials, the required scopes), run the context hook with `ContextHookRequest::tool` set to the method name, and then the owner check, in the store and again in the server: another principal's task (another actor, issuer, subject or client), an expired task, a malformed id and an unknown id all get the same `-32602` "Task not found", byte for byte. On an authorized server the owner must also still hold the command's `scopes` (or, under a resolver, its `visible`) to read or update it, else `-32600` with `data.code` `INSUFFICIENT_SCOPE`; `tasks/cancel` does not ask that. A server creates tasks only for callers it can tell apart: without an HTTP request (stdio), with verified credentials, or with `TaskOptions::with_callers_identified_by_hook()` and a context hook installed. Otherwise, decided per request, it does not declare the extension (`server/discover`, `initialize`), `tasks/*` are `-32601`, `Optional` runs inline and `Required` fails with `UNAUTHORIZED` (`retryable: false`) before anything runs. `tasks/update` acknowledges and ignores every `inputResponses` key (no AFD task waits for input); `tasks/cancel` acknowledges, and leaves a finished task unchanged. `McpServer::with_task_store(impl TaskStore)` takes a host's shared store (`create` durable before returning, `get` and `update` by owner, `expire(now)`; implemented for `Arc<T>`), and `McpServer::with_task_options(TaskOptions)` sets `ttlMs` (default 1 hour; `with_ttl_capped_at_token_expiry(grace_ms)` ends it at the token's `expiresAt` plus a grace), `pollIntervalMs` (1 s), the check interval (1 s), the result limit and the most tasks one process runs at once (64, whatever the store allows); the fields are read through getters and every value is at least 1. The default `InMemoryTaskStore` serves one process and holds at most 32 tasks per owner and 256 in all (`with_limits`), each until its `ttlMs` ends, dropping the owner's own, or the largest holder's, oldest finished task to make room. Every limit answers the same `RATE_LIMITED`. `error_codes::TASK_TOKEN_EXPIRED` joins the shared catalog. `tests/server_tasks.rs` covers it over Streamable HTTP (with and without the bearer layer) and stdio.

### Security

- **One approval runs one handler ([#1886](https://github.com/lushly-dev/afd/issues/1886)):** a command's declared approval policy no longer depends on the approval middleware being installed or listing the command, an approval admits one dispatch of the approved command on the approved input, and a gate given only in the middleware's list now holds each step of an `afd-batch` or `afd-pipe` before an earlier step's handler runs. See "Changed" for what this refuses that ran before.

- **Pipeline step inputs are bounded as in TypeScript** ([#1722](https://github.com/lushly-dev/afd/issues/1722); `spec/pipeline-variables.md`, "Limits"):
  - **Before:** a step input that repeated a reference to a large value cloned it in full each time, and a referenced value was cloned at any depth; only the template's depth was checked, before any step ran.
  - **Now:** `execute_pipeline` fails the step with `VALIDATION_ERROR` (`retryable: false`, `details: {"stepIndex", "limit"}`) without running its command when a value copied into the input nests deeper than 64 levels, or the resolved input exceeds `MAX_RESOLVED_NODES` (100,000) values or `MAX_RESOLVED_CHARS` (16 MiB) string and key characters, counted in UTF-16 code units. Only a repeated expansion of the same referenced value is charged for its contents.
  - **New API:** `try_resolve_variables` applies the limits and returns a `ResolutionLimitError` naming the `ResolutionLimit` it exceeded. `resolve_variables` is unchanged and unbounded.
  - **Up-front approvals:** an `afd-pipe` step over the limits is not resolved for approval and fails when it runs.
  - **`$prev` and `$steps[N]`:** the budget counts them as one value when they name the same step: `$prev` is the entry of `steps` at `PipelineContext::previous`, so both reach one value.
  - **Deadline:** the executor measures the time left for a step after resolving its input, as TypeScript does, so a step whose resolution used up the deadline fails with `PIPELINE_TIMEOUT` instead of running.

### Fixed

- **Pipeline reference keys and aliases match JavaScript's `\s` whitespace set** ([#1962](https://github.com/lushly-dev/afd/issues/1962); `spec/pipeline-variables.md`). `resolve_variable`, `resolve_variables`, `try_resolve_variables`, `get_nested_value`, `evaluate_condition` and up-front `afd-pipe` approval checks now use an explicit 25-code-point character class matching ECMAScript `WhiteSpace` and `LineTerminator` instead of `regex`'s Unicode `\s`: `U+0085` (NEL) is now allowed in keys and aliases (resolving and enforcing expansion limits as in TypeScript and C++), and `U+FEFF` (BOM) is treated as whitespace (making strings containing it literals).
- **Boolean schemas are accepted wherever a schema may appear** ([#2047](https://github.com/lushly-dev/afd/issues/2047); `spec/validation.md`), as in C++. `true` is `{}`, and `false` is `not: {}`, whose issue is `invalid_type` with `expected: "never"`. Before, registration refused `"properties": {"x": true}` and a `$ref` to a `true` definition. A command's whole input schema must still be an object: `register_with_schema` refuses a boolean root, which the new rule would otherwise have let through.
- **A `$ref` inside a subschema with its own `$id` resolves against that subschema** ([#1700](https://github.com/lushly-dev/afd/issues/1700); `spec/validation.md`, "Annotations"): the input validator read `$id` as an annotation only and resolved every local `$ref` against the root, so a schema whose nested `$id` subschema holds its own `$defs`, such as a structured-result envelope's `data` schema, was refused at registration. A string `$id` now starts a schema resource, as in Draft 2020-12. A bare fragment such as `"#node"`, which draft-07 used as an anchor, starts no resource. The `$id` value is never resolved as a URI.
- **`afd-help` leaves out empty `tags` in the `full` format** ([#1480](https://github.com/lushly-dev/afd/issues/1480); `spec/command-metadata.md`, "Reporting rules"): a command that set them to an empty list was reported with `tags: []`, where `afd-detail` leaves them out.
- **Native timers follow Tokio's clock** even when Cargo also enables the `wasm` feature. This keeps batch and pipeline durations, deadlines and the streaming timeout controller in sync with a paused runtime. ([#1592](https://github.com/lushly-dev/afd/issues/1592))
- **`server` feature: confirmation state bound to the principal ([#532](https://github.com/lushly-dev/afd/issues/532); `spec/command-metadata.md`, "Confirmations"; `spec/authorization.md`, M8; Umbel phase 5 step 0c):** the confirmation `requestState` was bound to the command and its input only, so with a context hook admitting several actors, a state one caller answered could confirm the same command and input for another. Its HMAC associated data now also holds the call's principal binding (`afd::principal_binding`): the actor the context hook left, after the server's default, and, on an authorized server (`server-auth`), the verified credentials' `issuer`, `subject` and `clientId`. The binding is associated data, never in the state, so the state names no one. A retry from another actor, or with another issuer, subject or client (a different client of the same person included), fails to verify exactly as an altered state does, and the server asks again; nothing runs. The associated data's layout carries a version label, so a state minted before this change does not verify either and is asked again. A 2025 connection's server-sent elicitation holds no state and is unchanged. Credentials with an empty `issuer`, `subject` or `client_id` (only host code can build them) are never bound: such a call gets no state, and a retry carrying one is refused, both with a JSON-RPC internal error that names no one.
- **`server` feature:** `server/discover` carries the same `ttlMs` and `cacheScope` (`public`) as `tools/list`, as `spec/tool-strategies.md` specifies; it answered `ttlMs: 0` with `cacheScope: private`. `capabilities.tools.listChanged` is now an explicit `false` instead of omitted (no strategy sends `notifications/tools/list_changed`).
- **`server` feature (#531):** a panic in the server's own request handling no longer leaves the MCP request unanswered. `rmcp` runs each request on its own task, so a panic that escaped `CommandRegistry::execute` (a `with_group_by` closure, for example) ended the task and the client waited forever, on stdio and Streamable HTTP. `tools/call` now answers a failed `CommandResult` with `INTERNAL_ERROR`, a suggestion and `retryable: true`, with `structuredContent`; `tools/list` answers a `-32603` error; neither carries the panic message. The context hook's panic uses the same failure. A panicking command handler was already a redacted `COMMAND_EXECUTION_ERROR` through `CommandRegistry::execute` (the code TypeScript and the shared catalog use for a handler that throws, so not `INTERNAL_ERROR`); tests now pin that on a command's own tool, grouped tools, `afd-call`, `afd-batch` (continue, `stopOnError`, `maxFailures`, parallel) and `afd-pipe`, on stdio and Streamable HTTP, and in the journal. Only unwinding panics are caught: `panic = "abort"` builds, and `wasm32-unknown-unknown`, still abort (now in the rustdoc).

### Added

- **Confirmations (`server` feature):** `McpServer::with_confirmations(ConfirmationMode::Enforce | RequireHuman)` and `with_confirmations_key` enforce `confirm_prompt` on tool calls (`spec/command-metadata.md`, "Confirmations"). A gated call runs after the user accepts an elicitation (an `input_required` result with an HMAC-signed `requestState` on MCP 2026-07-28, a server-sent request on a 2025 stdio connection), or, under `Enforce`, after `confirm: true` or `_meta["dev.afd/confirm"]`. Otherwise it fails with `CONFIRMATION_REQUIRED` or `CONFIRMATION_DECLINED`. The feature now enables `rmcp`'s `request-state` and `elicitation` features and depends on `getrandom`.

- **Trust fields:** `CommandDefinition` gains `destructive`, `confirm_prompt` and `undoable`, with `with_destructive`, `with_confirm_prompt` and `with_undoable`. `afd-help` (full) reports `destructive` and `undoable`, `afd-docs` reports all three, and a mutation's `destructiveHint` annotation follows `destructive`. `afd-help`'s `CommandInfo` gains two optional fields, so code that builds it with a struct literal must add them.
- **Confirmation error codes:** `error_codes::CONFIRMATION_REQUIRED` and `error_codes::CONFIRMATION_DECLINED`, for servers that enforce `confirm_prompt`. Nothing emits them yet.
- **Approval error code:** `error_codes::APPROVAL_REQUIRED`, returned by the approval middleware before the handler runs (`spec/command-metadata.md`, "Approvals").
- **Approval policy and middleware** (#421, parity with TypeScript #272): `CommandDefinition::with_approval` takes an `ApprovalPolicy` (`Required`, `NotRequired`, or a function of the validated input and context through `ApprovalPolicy::when` and `when_async`), reported by `approval_mode` as `_meta.approval` on `CommandRegistry::get_tool`, in `afd-help` (full) and in `afd-docs` (`conditional` for a function). `create_approval_middleware(ApprovalMiddlewareOptions)`, behind the new default `approval` feature, holds a call with `APPROVAL_REQUIRED` and `details.approvalToken`, `expiresAt`, `summary` and, for a rejected token, `reason` (`malformed`, `invalid-signature`, `expired`, `command-mismatch`, `input-mismatch`, `actor-mismatch`, `already-used`). Tokens (`afdap1.<payload>.<mac>`, HMAC-SHA256 with an app-supplied secret of at least 32 bytes, keyed digests of the canonical input and actor, constant-time comparison) are byte-compatible with TypeScript's, so a token issued by one verifies on the other; `canonical_json` writes numbers and orders keys as JavaScript does and refuses integers a float cannot hold. Single-use by default (`ApprovalReplay::WithinTtl` allows reuse until expiry), with an in-memory or supplied `ApprovalNonceStore`, key rotation (`with_previous_secret`), `with_summarize`, `with_include_token`, `with_on_approval_required` and a security clock that never comes from the context. `CommandContext` gains `approval` (`with_approval`), which only trusted surface code sets; the MCP server never sets it from tool arguments or `_meta`. `CommandContext`'s `Debug` output redacts the token. New dependencies: `hmac`, `subtle`, `ryu-js` (ECMAScript number spelling) and `getrandom` (0.3 or 0.4) outside the `server` feature; the `approval` feature turns on `serde_json/float_roundtrip`, so floats parse exactly as JavaScript parses them; `wasm` enables `getrandom`'s browser backend (Rust 1.85 or later with `approval`). `CommandInfo` gains an optional `approval` field, so code that builds it with a struct literal must add it.

- **`server` feature:** `afd::server::McpServer` serves a `CommandRegistry` over MCP Streamable HTTP (`streamable_http_service`, a `tower` service) and stdio (`serve_stdio`), built on the official MCP Rust SDK (`rmcp` 3.7). It serves MCP 2026-07-28 statelessly and 2025 `initialize` clients from one endpoint, lists only MCP-exposed commands (`with_tools` supplies full tool definitions), returns `COMMAND_NOT_FOUND` for unknown and unexposed tools, carries `ttlMs` cache hints on `tools/list` (`with_tools_list_ttl_ms`) and refuses unlisted browser origins. The feature is off by default and needs Rust 1.88; the crate's minimum stays 1.82 without it.
- **MCP tool annotations:** `CommandRegistry::get_tool` adds `annotations` (`readOnlyHint: false`, `destructiveHint: false`) for a command with `mutation: true` (`spec/command-metadata.md`).
- **Actor, clock and random on `CommandContext`** (#401, parity with TypeScript #271/#274): `Clock` and `RandomSource` traits with `SYSTEM_CLOCK`, `SYSTEM_RANDOM`, `fixed_clock` (a `ManualClock` moved with `set` and `advance`; clones share time) and `seeded_random` (mulberry32 over FNV-1a of the UTF-8 seed, bit-for-bit the TypeScript sequence). `Actor` and `ActorKind` (`human`, `agent`, `service`, `script`, `test`), `ACTOR_KINDS`, `is_actor`, `is_actor_kind`, `ContextDefaults` and `with_context_defaults`. `CommandContext` gains `actor`, `clock` and `random` (with `with_*` builders and `clock()`/`random()` accessors); `CommandRegistry::execute` always fills the clock and random source and stamps the actor's kind as `metadata.actorKind`. The `wasm` feature reads the system time through `web-time`. The `server` feature runs tool calls as actor `agent`, configurable with `McpServer::with_actor`, `with_clock` and `with_random`.
- **Typed `actorKind`:** `ResultMetadata::actor_kind` and `TelemetryEvent::actor_kind` (it used to round-trip in `extra`); an unknown kind on the wire reads as `None`.
- **Command journal and replay** (#426, parity with TypeScript #273; `spec/journal.md`): `JournalEntry`, `JournalRecord`, `JournalTape`, `JournalContextDigest`, `JournalRange`, the `JournalSink` trait with `MemoryJournalSink`, and `FileJournalSink` (JSON Lines, with torn-line recovery) behind the new default `journal-file` feature. `create_context_digest` hashes the actor, interface, trace ID and the names (never the values) of the other context keys, as TypeScript does; `journal_actor`, `is_journal_entry`, `parse_journal`, `serialize_journal` and `serialize_journal_entry` read and write the shared format, and `spec/wire/journal.jsonl` round-trips. `CommandRegistry::set_journal(JournalRecorder)` records each call after validation and around the middleware chain (`with_record_failures`, `with_filter`, `with_redact`, `with_max_tape_reads`, `with_on_error`; `auth-*` commands are skipped by default; timed-out calls are not recorded, and a `timeout_ms` deadline covers the middleware chain only, not the journal append). `replay_journal` re-executes entries with their clock and random tapes restored and reports `same`, `different` (with per-path differences) or `error`, plus notes on tape over- and under-runs. New dependency: `sha2`.
- **MCP 2026-07-28 error codes:** `McpErrorCodes::HEADER_MISMATCH` (-32020), `MISSING_REQUIRED_CLIENT_CAPABILITY` (-32021) and `UNSUPPORTED_PROTOCOL_VERSION` (-32022).

## [0.1.0] - 2026-10-12

First release. It implements AFD contract **1.0-rc**. Published on
[crates.io](https://crates.io/crates/afd/0.1.0), with
[API documentation](https://docs.rs/afd/0.1.0/afd/). Git and path dependencies remain usable.

### Fixed

- Reject references outside named schema definitions, preventing references into uninspected annotation/default data, and enforce both `const` and `enum` when combined.

- Explicit `null` remains a value instead of taking a default or being reported missing (#282).
- Apply schema and nested defaults as-is; export defaulted parameters as optional and preserve parameter default precedence (#284).
- Empty legacy parameter lists enforce their advertised empty object schema, and validation reports every issue (#332). Applications needing open payloads should use whole-schema registration.
- Pipeline references use the shared 1,024 UTF-16-unit limit, including astral characters (#283).

### Added

- `CommandRegistry::register_with_schema` and `get_tool` preserve whole input schemas without changing existing public field types. Validation supports the required shared subset and `const`; unsupported keywords fail registration. Bootstrap schema/docs discovery uses the same authoritative schema (#311).
- Shared validation vectors exercise supported cases through actual registry dispatch and verify optional unsupported cases fail registration. Boundary tests cover defaults, null, authoritative discovery, uncapped issues, oversized numeric bounds, and UTF-16 limits.

- The wire types, which serialize exactly like `@lushly-dev/afd-core` (camelCase keys, unset fields omitted, unknown metadata keys kept in `extra`). `tests/wire_fixtures.rs` round-trips every `spec/wire` fixture:
  - `CommandResult<T>`, `ResultMetadata`, `CommandError` and `ErrorCode`;
  - `Source`, `PlanStep`, `Alternative` and `Warning`;
  - the batch, pipeline and stream result shapes.
- The result helpers `success`, `success_with`, `failure`, `failure_with`, `error`, `is_success` and `is_failure`, and the error constructors `validation_error`, `not_found_error`, `rate_limit_error`, `timeout_error`, `internal_error`, `wrap_error` and `create_error`.
- `CommandRegistry` (`create_command_registry`). It validates input against the declared parameters and applies defaults, honors `expose` and `CommandContext.timeout_ms`, runs `CommandMiddleware`, and propagates the context into batches (#251).
- Batch execution (`BatchRequest`, `BatchOptions`, `BatchResult`). A batch runs every command unless `stopOnError` is set, and honors `parallelism` and the deadline (#225, #250).
- Pipelines: `execute_pipeline`, which runs through a `CommandExecutor` callback, conditions, and variable resolution that follows `spec/pipeline-variables.md` (#250).
- Stream chunk types and helpers: `ProgressChunk`, `DataChunk`, `CompleteChunk`, `ErrorChunk` and `StreamChunk`.
- The bootstrap commands `afd-help`, `afd-docs` and `afd-schema` (`register_bootstrap_commands`).
- Handoff types and helpers, MCP JSON-RPC types with command-to-tool conversion (there is no MCP server or client), telemetry events, and `find_similar_tools`.
- `AFD_META_TOOL_NAMES`, `AFD_BOOTSTRAP_COMMAND_NAMES`, `AFD_CONTEXT_COMMAND_NAMES`, `AFD_BUILTIN_TOOL_NAMES` and `is_afd_builtin_name`, with the same names as the other languages (#292).
- The `native` feature (default), which enforces deadlines through `tokio::time::timeout`, and the `wasm` feature for `wasm32-unknown-unknown`, which measures durations with `web-time`.
- CI: `rust.yml` runs `cargo fmt --check`, clippy with `-D warnings` and the tests, each with and without default features, and checks the `wasm` build, on a pinned toolchain (#234).
- `execution_failure(message, dev_mode)` and `error_codes::COMMAND_EXECUTION_ERROR`, matching the TypeScript and C++ helpers (#306).
- `afd::CONTRACT_VERSION`, the AFD contract version from `spec/VERSION` (now `1.0-rc`). `afd-help` returns it as `contractVersion` (#313).
- `rust-version = "1.82"` declares the minimum supported Rust version. The README badge said 1.70, which no longer built (#313).
- `error_codes` holds the 42-code shared catalog of `spec/error-codes.md`, adding `COMMAND_NOT_IN_CONTEXT`, `COMMAND_NOT_ALLOWED`, `UNKNOWN_TOOL`, `AMBIGUOUS_ACTION`, `INVALID_GROUPED_CALL`, the context, batch, pipeline and stream codes. `tests/error_codes.rs` checks it against `spec/vectors/error-codes.json`, and the executors use the constants instead of string literals.

### Changed

These changes affect code that used the crate as a git dependency before this release.

- **Breaking:** types serialize exactly like `@lushly-dev/afd-core` (metadata, batch, pipeline and stream shapes). Batches continue on error by default. Public structs are `#[non_exhaustive]`, with constructors and `with_*` builders; `ResultOptions` and `FailureOptions` stay open for `..Default::default()`. A panicking handler fails only its own batch command or pipeline step (#250).
- **Breaking:** pipeline variable references follow `spec/pipeline-variables.md`, as in every language. `$input` is the request's own `input` field and never the host or caller context; `$`-prefixed literals such as `$9.99` pass through; `$$` escapes; paths follow only own JSON keys and in-bounds indices; unresolved references are omitted; `$eq`/`$ne` compare structurally; nesting deeper than 64 is rejected with `VALIDATION_ERROR` (#250).
- **Breaking:** a pipeline step with `stream: true` fails with `UNSUPPORTED_OPTION`, and every other step is skipped before any command runs, as in TypeScript. `stream: false` is still accepted (#253).
- `CommandRegistry::execute` builds its `COMMAND_NOT_FOUND` suggestion the way the TypeScript server does: up to three close matches (`Did you mean 'todo-create'? Other close matches: 'todo-list'.`) instead of a fixed hint. It matches only against commands exposed to `CommandContext.interface` when that is set, so unexposed names are not revealed. It ends with "Use afd-help to list all commands." when `afd-help` is registered and callable, otherwise "Check the command name against the available commands." (#278)
- **Breaking:** `CommandRegistry::execute` behaves like the TypeScript engine in three ways (#286). (1) `VALIDATION_ERROR` has the message `Input validation failed`. The issues and the unknown, missing and expected fields move to `suggestion`, formatted as TypeScript formats them. Each `details.errors` entry gains a Zod `code` (`invalid_type`, `invalid_value`, `too_small`, `too_big` or `invalid_format`), plus `expected` for `invalid_type`. Paths are joined with dots (`tags.1`, or `(root)` for the whole input), and empty `missingFields`/`unexpectedFields` are omitted. (2) Handlers and middleware no longer receive keys the parameters do not declare, nor keys missing from a nested schema's `properties` unless it has `additionalProperties`. A command that read undeclared keys must declare them. (3) An unknown command name is cut to 128 UTF-16 code units in the error message. `find_similar_tools` and `calculate_similarity` count UTF-16 code units, so names with emoji or other characters outside the Basic Multilingual Plane get the same suggestions as in TypeScript. `packages/rust/README.md` lists the differences that remain.
- **Breaking:** a panic in `execute`, a batch or a pipeline returns `COMMAND_EXECUTION_ERROR` with "An internal error occurred" instead of `INTERNAL_ERROR`. The panic payload is never included (#306).
- `is_success` and `is_failure` test only the `success` flag, as in TypeScript (#306).
- **Breaking:** `BatchRequest` and `PipelineRequest` deserialize only envelopes that TypeScript accepts (`spec/vectors/batch-controls.json`). A command name must not be blank. An optional field may be omitted but not `null`, except a pipeline's `input`. A step `input` must be an object, `timeoutMs` a non-negative number, and `onProgress` unset. An invalid batch returns `INVALID_BATCH_REQUEST` with TypeScript's message, "Invalid batch request envelope" (#317).
- With the `native` feature, deadlines and durations use `tokio::time::Instant`, the clock `tokio::time::timeout` enforces them with, so they follow a paused Tokio test clock (#317).

### Fixed

- Batch concurrency, stop and deadline controls are honored, and a pipeline with `parallel: true` fails with `UNSUPPORTED_OPTION` instead of running sequentially (#225).
- Deadline options (`timeoutMs`) fail with `UNSUPPORTED_OPTION` before anything runs in builds without the `native` feature (#225).
- Stream serialization is corrected, and JSON-RPC request IDs may be negative integers (#225).
- Fuzzy matching of unknown command names is bounded, so an oversized name no longer blocks for seconds. Echoed names are truncated (#232).
- The `wasm`, MCP and handoff types are fixed (#251).
- Pipeline deadlines behave as in TypeScript: `timeoutMs: 0` fails step 0 with `PIPELINE_TIMEOUT` instead of skipping every step, and a step that ends past the deadline skips every later step with that error (#317).
- A `when` condition treats a first operand that is not a reference (`"$$prev"`, `"text"`) as absent, and `$eq`/`$ne` compare numbers by value (`2` equals `2.0`), as in TypeScript. `tests/pipeline_vectors.rs` and `tests/batch_controls_vectors.rs` load the shared `spec/vectors` files (#317).
- `CommandRegistry::execute` catches a panic in a middleware layer or the handler, including one raised while building the future and one under `timeout_ms`, instead of letting it unwind to the caller (#306).
