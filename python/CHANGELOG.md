# Changelog

All notable changes to the Python `afd` package are documented here. The package is versioned independently of the npm packages and the other implementations, is published to [PyPI](https://pypi.org/project/afd/), and is released with tags of the form `python-vX.Y.Z`.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this package adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a minor release may break the API.

Changes that are not released yet are the files in [`.changeset/`](../.changeset/README.md) that name `afd-python`, one per pull request. `pnpm version-track python` writes them here as a dated section when a release is prepared, so nothing is added under `Unreleased` by hand.

## [0.14.0] - 2026-11-27

Implements AFD contract `1.0-rc`.

Gives every error a structured recovery a program can follow, from the engine's own errors to scenarios that follow them; adds secret commands and journal redaction, `afd.auth`, host-verified confirmation and a single telemetry type; and stops the retry middleware from repeating a mutation.

### Breaking changes

- **A handler that returns something other than a `CommandResult` fails the same way on every path** ([#1760](https://github.com/lushly-dev/afd/issues/1760); `spec/error-codes.md`). A single call (`server.execute`, an individual or grouped tool, `afd-call`, an MCP task, and `CommandRegistry.execute`, `DirectClient.call` and the testing `MockServer`, which share the executor) now gets the `INVALID_COMMAND_RESULT` failure (not retryable) that a batch item, pipeline step or stream already got, instead of the raw value passed through with no metadata. A dict with a boolean `success` is still parsed as a result, so `{"success": True, "data": ...}` keeps working. The coerced result is stamped with execution metadata and is what middleware sees, and a middleware that returns a plain value is coerced too. Return `success(...)` or `error(...)` from handlers that returned plain values.
- **`afd[server]` and `afd[client]` require `mcp>=2.3,<2.4`**, capped at the newest minor the full suite has passed on ([#1756](https://github.com/lushly-dev/afd/issues/1756)). Before, any `mcp` 2.x was accepted, though the server relies on SDK internals that a minor release could change. The weekly `Python newest MCP SDK` workflow runs the full suite on the newest 2.x and says when the cap can be widened.
- **Telemetry events from `create_telemetry_middleware` carry `error` as a `CommandError`** ([#1760](https://github.com/lushly-dev/afd/issues/1760)), not a dict. `event.error["code"]` and `event.error.get("code")` still work with a `DeprecationWarning`; read `event.error.code`. `ConsoleTelemetrySink`'s text line is now TypeScript's (`[Telemetry] [trace] todo-create SUCCESS in 150ms (confidence: 0.9) - CODE: message`), and its JSON line is the whole event in camelCase with `_prefix`, for both constructors: it now includes `metadata`, `commandVersion` and, with `include_input=True`, the command's `input`, which the middleware's former sink left out. `ConsoleTelemetrySink(format=...)` refuses anything but `"text"` or `"json"` with `ValueError`.
- **`afd.server.middleware.TelemetryEvent` is now the Pydantic model `afd.core.telemetry.TelemetryEvent`, not a dataclass.** Build it with keyword arguments; positional construction, `dataclasses.asdict()` and `dataclasses.replace()` no longer work (use `model_dump()` and `model_copy(update=...)`). `"code" in event.error` and comparing `event.error` with a dict no longer work; read its attributes.
- **A journal outside the execution engine records nothing without `redact`.** Where the recorder cannot read a command's `secret` declaration (a `DirectClient`'s own middleware, a direct call of the middleware, another host's middleware chain such as Botcore's `CommandHost`, a chain a handler runs itself, or any recorder run with a `next` the engine did not build), it used to record every call `filter` allowed; it now records a call there only when it was given `redact`. Give such a journal a `redact`, or run it behind the engine; an engine of its own binds the declaration with `afd.core.open_dispatch`.
- **`create_retry_middleware` no longer repeats a mutation** ([#2673](https://github.com/lushly-dev/afd/issues/2673)). It used to retry any command whose failure code was `TRANSIENT_ERROR` or `TIMEOUT`, so a handler that returned `TIMEOUT` after a downstream write could have that write applied twice. A command that declares `mutation=True` now runs once and its failure is returned. The middleware reads the declaration from the command the engine's dispatch runs, through the continuation it was handed (as the journal reads `secret`), never from its name; a call whose declaration it cannot read (a direct call, or a `next` the engine did not build) counts as a mutation. Pass `retry_mutations=True` to restore the old behaviour, and only when every mutation it wraps is safe to repeat.
- **A gated step whose validator changes the value it reads back fails inside `afd-batch` or `afd-pipe`** ([#1511](https://github.com/lushly-dev/afd/issues/1511)). A gated command whose schema returns another value, or changes its type, no longer validates to itself, so inside `afd-batch` or `afd-pipe` it now fails with `VALIDATION_ERROR`. Call it on its own, or make the transform idempotent.
- **The client names left `afd.__all__`** (#1758). The lazy `client`-extra names (`McpClient`, `McpClientConfig`, `ClientStatus`, `TaskInfo`, `DetailedTask`, `TaskProgressCallback`, `create_client`, `ElicitationHandler`, `ElicitationRequest`, `ElicitationResponse`) are no longer exported by `from afd import *`. Import them by name (`from afd import McpClient`) or from `afd.client`.
- **`CommandError.model_dump()` includes `"recovery": None`** when no recovery is set. Results still omit an unset `recovery`, as they omit an unset `cause`, now on a nested `cause` too. Code that compares a dumped error with a dict adds the key.
- **An MCP task still working after `max_run_ms` (one hour by default) stops with `TIMEOUT`.** `TaskOptions` separates the run budget (`max_run_ms`, `DEFAULT_TASK_MAX_RUN_MS`) from post-completion retention (`ttl_ms`, default one hour). A new task starts with `ttlMs = max_run_ms + ttl_ms` (two hours by default) and on finishing tightens it to `min(max_run_ms, max(0, finished_at - created_at)) + ttl_ms` (capped at `token_expiry_grace_ms` when configured), so results stay readable for a full hour after completion. A task that runs out completes with `TIMEOUT` (`retryable=True` for reads or unstarted tasks, `False` for started mutations), retained for `ttl_ms`. Raise `max_run_ms` for longer tasks.

### Added

- **`CommandError.recovery`** (`spec/recovery.md`): the step a suggestion describes, as an `afd.Recovery` with `kind` `call`, `fix-input`, `retry`, `external` or `stop`, and `command`, `input`, `needs`, `then_retry` and `after_ms` (camelCase on the wire). `error()` and `create_error()` take `recovery=`. A `Recovery` built in Python refuses what the specification forbids: a field on the wrong kind, an unknown field, a value of the wrong type (no string or boolean coerced to a number), an empty `input` or one with `confirm`, empty or repeated `needs`, and a `fix-input` that sets neither `input` nor `needs`. An error read from the wire whose recovery breaks those rules, or has a `null` member, gets `recovery=None` and keeps everything else (rule 7); so does a `CommandError` given such a recovery as a plain dict. A `Recovery` changed after it was built so that it breaks them raises when given to a `CommandError`. `afd.is_command_recovery()` says whether a value is a recovery a reader keeps, the same test as TypeScript's `isCommandRecovery`; it checks a `Recovery` in its wire form. `tests/test_recovery_vectors.py` runs `spec/vectors/recovery.json`.
- **`follow` on a scenario step**: a step that expects a refusal can follow the refusal's structured `error.recovery` (`spec/recovery.md`) and fail unless it gets further. `follow: true` or `follow: { input, expect, retry }` (`afd.testing.FollowExpectation`): a `call` recovery runs its command, and with `thenRetry` repeats the refused call; `fix-input` repeats the command with the fixed input; `retry` repeats it unchanged. Each call is judged by `expect` or `retry` (default: it succeeds), and a call that comes back with the refused command's same error code fails the step. `follow.input` gives only the fields the recovery `needs`, so a scenario cannot correct a wrong recovery, and it takes step references; a recovery that names a field in both `input` and `needs`, or that `$defs/recovery` refuses, fails the step. A refusal without a recovery, or with an `external` or `stop` one, fails a `follow`. The calls appear in order on `StepResult.follow`, and run only when the refused step itself passed. The YAML keys and failure messages match the TypeScript runner's.
- **`expect.error.recovery` in scenarios**: assert a refusal's structured recovery like `data`. Each named field must match, others are ignored, and a refusal without a recovery, or with one no reader keeps, fails the assertion.
- **`validate_scenario` checks `follow`**: a `follow` on a step that does not expect a refusal, and a forward step reference in `follow.input`, are errors.
- **Commands can declare `secret=True`** (`spec/command-metadata.md`, `spec/journal.md`) when they take or return a secret, such as a password or an issued token: on `CommandDefinition`, `define_command`, `@server.command`, `SimpleRegistry.command`/`register` and `MockServer.command` (the last two also read it from a `define_command` decoration on the handler). A non-boolean `secret` raises `TypeError` when the command is defined or registered. `create_journal_middleware` never records a call to such a command unless it was given `redact`, whatever its `filter` returns, in `create_server`, `create_direct_registry`, the core `CommandRegistry`, `SimpleRegistry` and `MockServer`: the shared executor binds the declaration of the command each dispatch runs to the continuations it builds for that dispatch's middleware chain (`compose_middleware` passes it on to its own), and the recorder reads it only through the `next` it was handed, while the dispatch runs and on the dispatch's own context, never from the name. It holds across a middleware that moves the rest of the chain to a worker thread; a recorder given a `next` of its own, a handler or another host's chain included, reads unknown. A secret call reads neither of a recording parent's taped sources, and the tape of every recording layer around it is marked `truncated`; a recorded secret call keeps its reads on its own entry. The default filter still skips `auth-*`. `afd.auth`'s `auth-sign-in`, which takes a password, now declares it.
- **`redact` may receive an `afd.server.JournalRedactInfo`** whose `secret` is `True`, `False` or `None` (when the recorder cannot read the declaration). It is passed as the second argument when the redactor's second positional parameter has no default, or as `info=` when the redactor has a parameter named `info`. Any other redactor, one that takes `*args` or a defaulted second parameter included, is called with the record alone, as before.
- **`afd.core.open_dispatch(context, secret=...)` lets an engine of its own give AFD middleware a command's `secret` declaration.** An engine that runs AFD middleware outside AFD's executor, such as Botcore's `CommandHost`, opens a `CommandDispatch` on the context it passes down its chain, hands the chain the continuation `dispatch.bind(next_fn)` returns (a new one each call) and closes the dispatch when the call ends (as a context manager it closes itself); `compose_middleware` passes the binding on. `create_journal_middleware` then reads the declaration as it does behind AFD's own executor: it records a non-secret call without `redact`, never records a secret one without it, passes `JournalRedactInfo(secret=True|False)` to `redact`, and keeps a secret call off a recording parent's tape. An optional `mutation` gives the retry middleware the command's `mutation` declaration; left out, it reads unknown there, so nothing is retried on a guess. A non-boolean `secret`, or a `mutation` that is neither a boolean nor `None`, raises `TypeError`; binding to a closed dispatch raises `RuntimeError`.
- **`afd.server.run_off_tape(context, next_fn)`** runs a secret call off every recording tape around it, for an engine whose own chain may hold no recorder. `create_journal_middleware`'s recorder, and a `compose_middleware` composition holding one, carry `__afd_journal__ = True`, so such an engine can tell when AFD's journal already handles a call.
- **`afd.auth`**: the provider-agnostic `AuthAdapter` protocol, discriminated `AuthSessionState` models (`UNAUTHENTICATED`, `LOADING`, `AuthenticatedSessionState`), `AuthAdapterError`, `ListenerSet`, `create_auth_middleware` (including `is_verified_credentials` awareness and server startup backstop), `create_auth_commands` (`auth-sign-in`, `auth-sign-out`, `auth-session-get`), and `MockAuthAdapter`. `MCPServer.register()` accepts `CommandDefinition` objects directly.
- **Host-verified confirmation**: confirmation mode (`confirmation_mode="host-verified"`), `HumanRelay`, private relay evidence in `create_approval_middleware`, and `input_digest` (`spec/authorization.json` `inputDigests` conformance).
- **`instances` server option (`"single" | "multiple"`) and `confirmation_key` validation ([#2242](https://github.com/lushly-dev/afd/issues/2242)).** `create_server(..., instances="multiple")` raises `ValueError` when confirmations, `relay="mcp-elicitation"`, or single-use approval middleware (directly or inside `compose_middleware`) rely on per-process defaults without a shared `confirmation_key` or `nonce_store`. When omitted, serving over HTTP logs one warning per process to stderr (`instances="single"` silences it; stdio logs nothing). `confirmation_key` (at least 32 bytes) is validated and copied at server creation.
- **More of the API is exported from `afd` and `afd.core`**: `execute_batch`, `execute_stream`, `CommandExecutor`, `ExecutorOptions`, `StreamExecutorOptions`, `CommandRegistryOptions`, `is_exposed_to`, `is_mcp_exposed` and `commands_to_mcp_tools` (executors from `afd.server` too), with `execute_batch()` and `execute_stream()` methods on `CommandRegistry`, `MCPServer`, `SimpleRegistry` and `MockServer`; and the handoff reconnect-policy defaults and guards, the MCP error codes, types, factories and guards, the similarity helpers, `execution_failure`, and the pipeline models, condition guards and helpers that do not collide with other names (part 1 of #550).

### Changed

- **Engine errors carry a recovery** (`spec/recovery.md`, "Engine errors"): the errors the registry, server, tool router, middleware, confirmation and approval steps, context commands and direct client emit now set the structured `error.recovery` the specification's table gives, beside an unchanged `retryable`. `COMMAND_NOT_FOUND` names `afd-discover` (`{kind: "call"}`) only where the caller can call it: over MCP, and from an in-process `server.execute`, which also runs the meta-tools outside the `apps` interface, unless an `allow` list refuses it; its `afd-batch` items agree. Where the caller cannot call `afd-discover`, it names `afd-help` when the caller can call it (`bootstrap=True`) and otherwise ends "Check the command name against the available commands." with no recovery. The core registry and `create_direct_registry` name `afd-help` when the caller can call a registered command by that name, and otherwise keep "List available commands to see valid options" with no recovery. `COMMAND_NOT_IN_CONTEXT` names `afd-context-list` in its suggestion and recovery only when the caller can call it (registered, exposed to its interface, in context, admitted by any `allow` list and shown under its scopes), and adds "or afd-context-enter to switch" only when it can call that too; otherwise it names the command's contexts with no recovery. Only registered commands cross a direct registry's boundary, never the server's built-in context commands, so there a registered `afd-context-list` gives `{kind: "call", command: "afd-context-list"}` and otherwise the suggestion names the contexts. `COMMAND_NOT_EXPOSED`, `CALL_NOT_GRANTED`, `CONFIRMATION_REQUIRED` and an approval a person must give carry `{kind: "external"}`; `CONFIRMATION_DECLINED`, a declined approval and a `DirectClient` whose `on_approval_needed` answers `False` carry `{kind: "stop"}`; an `on_approval_needed` hook that raises or answers anything but a boolean leaves the call held, `{kind: "external"}`; `CONTEXT_NOT_FOUND` from `afd-context-enter` now lists the configured contexts ("Available contexts: …."), and names and calls `afd-context-list` when the caller can call it; `CONTEXT_DEPTH_EXCEEDED` says "Call afd-context-exit to leave a context before entering another" and calls `afd-context-exit` with `thenRetry` when the caller can call it, and otherwise says "Leave a context before entering another" with no recovery. The rate limiter sets `{kind: "retry", afterMs}` with the same whole seconds its suggestion gives, and `{kind: "retry"}` at client capacity and at a task limit. A grouped tool's unknown action now says "Use afd-call with the full command name, or list tools to find a valid action.", the text every language uses, instead of naming `afd-discover` and `afd-detail`. A `DirectClient` whose `on_approval_needed` answers `False` now says not to run the call again without asking the user.
- **`rate_limit_error()`** sets `{kind: "retry"}`, with `after_ms` of the given seconds × 1000 rounded up to a whole millisecond when that is a finite wait from 0 to 2^53 − 1, and no `after_ms` otherwise; it never raises. The rate-limit middleware does the same, and a window too long to state (`window_ms=float("inf")`) now refuses with `{kind: "retry"}` instead of raising. The other error helpers set no recovery.
- **The default server instructions** begin "`<name>` is an AFD server. Every tool returns a CommandResult as JSON text: { success, data, error: { code, message, suggestion, recovery } }; follow error.suggestion to recover. When error.recovery is present, it is the same step in a form a program can follow."
- **One telemetry type** ([#1760](https://github.com/lushly-dev/afd/issues/1760)): `afd.core.telemetry.TelemetryEvent`, `TelemetrySink` and `ConsoleTelemetrySink` are the only ones, exported from `afd`, `afd.core` and `afd.server`. `TelemetryEvent` is a `WireModel`: `to_wire(event)` and `model_dump(by_alias=True)` give camelCase keys (`commandName`, `startedAt`, `durationMs`, `traceId`, ...) as TypeScript's does, and it accepts snake_case names or camelCase keys. `TelemetrySink.record` may return an awaitable. `ConsoleTelemetrySink` takes `format=` as before and `log=`, `json_mode=` and `prefix=` from the middleware's former sink. `is_telemetry_event` accepts the camelCase wire form, and the middleware records the result's metadata in its wire form (camelCase, unset fields left out) instead of a snake_case dump with `None`s.
- **Per-call schema work is cached** ([#1760](https://github.com/lushly-dev/afd/issues/1760)). A Pydantic input model's JSON Schema is generated once per model class (again after `model_rebuild`), not on every call, and the MCP tool list is built once per tool strategy, active context and listed commands, not on every `tools/list`; registering a command or changing those options rebuilds it. `get_tool_definitions()` still returns a copy the caller may change. A registered definition changed in place (its description, schema or contexts) is not seen by `tools/list` until the list is built again; register a new definition instead. `python/benchmarks/per_call_overhead.py` times both.
- **Fewer MCP SDK internals** ([#1756](https://github.com/lushly-dev/afd/issues/1756)). The server no longer registers tools in the SDK's tool manager (`MCPServer._tool_manager`, `Tool`, `FuncMetadata`, `ArgModelBase`): its `call_tool` routes every name itself, and Mcp-Param header validation reads AFD's own tool schemas. The request-state middleware is installed through the public `MCPServer.middleware`, and `InputRequiredResult` is recognised by type, not class name. The internals left (`MCPServer._lowlevel_server`, `Server._request_handlers`, the instance's `get_capabilities`, `MCPServer._tool_input_schema`, `ServerSession._connection`, and AFD's place just before the SDK's `RequestStateBoundary` in the provisional middleware chain) are listed in `afd.server.sdk_internals`, each with a guard test that names it and what breaks. A session without `_connection` now logs one warning instead of silently losing context state between requests.
- **One execution path**: single-command execution in `CommandRegistry`, `SimpleRegistry`, `MockServer` and `MCPServer` runs through the shared `afd.core.single_executor.execute_command`, preserving middleware order, exposure, `allow`, contexts, output budgets, cancellation, deadlines and exception redaction, and `DirectClient.pipe()` runs through `afd.core.pipeline.execute_pipeline()`, keeping only an adapter for `DirectPipelineResult` and legacy string `when` references.
- **`afd.transports`** loads transport implementations lazily, so `afd.testing` installs and imports cleanly with only `afd[testing]` (without `httpx` or `mcp`), and `from afd import *` succeeds on a base install (#1758).
- **Context-hook refusals keep `recovery`** beside `code`, `message`, `suggestion` and `retryable`, as Rust's do: a refused caller needs it.
- **PyPI classifier** now says `Development Status :: 4 - Beta`, matching the Beta status the README and afd.dev give the Python package; it said `3 - Alpha` (#2473).

### Deprecated

- `afd.server.middleware.TelemetryEvent`, `TelemetrySink` and `ConsoleTelemetrySink` are deprecated aliases of the `afd.core.telemetry` names and warn on access. Import them from `afd`, `afd.core` or `afd.server`.
- **The direct-client dataclasses' old names** are deprecated aliases of `DirectContext`, `DirectCommandDefinition`, `DirectCommandParameter`, `DirectPipelineStep`, `DirectPipelineStepResult` and `DirectPipelineResult`, renamed to stop colliding with `afd.core`, and warn on access in `afd`, `afd.direct` and `afd.direct_pipeline`. They are removed in 0.15.0 (#1758).

### Fixed

- **A declared context field whose validator raises** an exception other than a validation error no longer returns the exception's text to the caller (#2141). Outside `dev_mode`, `details.errors[0].message` is "The value could not be validated"; with `dev_mode=True` it is the exception's text, as before. The exception is logged to the `afd.server` logger either way, on the in-process, MCP and host-verified relay paths.
- **`check_batch_limits`** (`afd.core.batch`) accepts a finite integral float `options.parallelism` (such as `17.0`) in a raw dict input, as `BatchOptions` does ([#2316](https://github.com/lushly-dev/afd/issues/2316)).
- **`McpClient.call()`** fails closed to `OUTCOME_UNKNOWN` (`retryable=False`, with the underlying cause in `details["cause"]`) when a timeout, connection/transport loss, HTTP 5xx, JSON-RPC `-32603`, or failed MCP task poll leaves the outcome unknown for any tool not positively declared `_meta.mutation: false` (without contradicting `destructive`, `destructiveHint`, or `readOnlyHint: false`) before dispatch; clears cached tool metadata on reconnect discovery failure; preserves `ToolInfo.annotations` from `tools/list` ([#2319](https://github.com/lushly-dev/afd/issues/2319)).
- **Python scenario runner (`afd.testing.scenarios`)** now matches TypeScript's `data` assertions: lists containing objects are matched item by item on named fields, mixed or mistyped matchers are rejected at parse and evaluation time with `InvalidExpectationError`, and deep equality no longer treats `bool` values as `int` (#2428). `expect.error.suggestion` is also read now and checked, as the TypeScript runner does: a string the suggestion must contain, or an assertion matcher. The parser used to drop it, so a scenario that asserted a suggestion passed without the suggestion being checked. A suggestion matcher is as strict as TypeScript's: every key must be a matcher key (a typo beside a real matcher is refused, not ignored) and each value must suit its matcher. `{equals: ...}` is now a matcher in Python too, as it is in TypeScript.
- **Up-front batch approval follow-ups** ([#1511](https://github.com/lushly-dev/afd/issues/1511)). A step of an `afd-batch` or `afd-pipe` approved up front is now validated, when it runs, on the input it is about to run as well as on the input as sent: a validator that reads live state (a default id that an earlier step has since taken) fails the step with `VALIDATION_ERROR` instead of running the approved value unchecked. A retry whose gated step had no kept input (over `MAX_KEPT_INPUT` with the steps before it), whose input no longer has the binding of any approval it carries (it validated to another input, such as a random default), and that cannot be kept with a new question either is refused with `APPROVAL_REQUIRED` and `details["reason"] == "input-not-kept"`, with a suggestion to call that command on its own, instead of being asked about again on every retry. An approval of the step's own input that only expired is still asked about again.

## [0.13.0] - 2026-11-24

Implements AFD contract `1.0-rc`.

Brings Python to parity across MCP HTTP authorization and scope enforcement, MCP Tasks, opt-in resources and Skills over MCP, output budgets, per-request context hooks, app-to-app calls, and execution controls, while raising the minimum Python version to 3.11.

### Breaking changes

- **`afd` now requires Python 3.11 or newer** (`requires-python >=3.11`). Python 3.10 reached end of life in October 2026. On 3.10, pip and uv keep resolving `afd` 0.12, the last release that supports it, and a pin to this release or later fails to install; move to 3.11 to upgrade. CI tests 3.11, 3.12, 3.13 and 3.14, and the classifiers list the same four ([#1805](https://github.com/lushly-dev/afd/issues/1805)).

- **A `$ref` outside the subset fails at registration** ([#1910](https://github.com/lushly-dev/afd/issues/1910); `spec/validation.md`). The subset is `#`, `#/$defs/<name>` and `#/definitions/<name>`, as in Rust. Before, any deeper pointer under `#/$defs/` or `#/definitions/` was followed, such as `#/$defs/A/properties/x`. A pointer into a nested `$id` subschema then resolved that subschema's own references against the wrong resource. Name the target as its own definition instead.

- **`create_approval_middleware`'s `include_token` now defaults to `None`**, matching `spec/command-metadata.md`, "Approvals", rule 6 ([#1665](https://github.com/lushly-dev/afd/issues/1665)). When unset, `APPROVAL_REQUIRED` omits `details.approvalToken` for calls whose `context.extra["interface"]` is `"mcp"` and includes it elsewhere, matching TypeScript, Rust and C++. Pass `include_token=True` to opt in on MCP calls, or `include_token=False` to omit it on non-MCP calls.

- **MCP commands now time out after 30 seconds by default** (`spec/execution-controls.md`, [#2129](https://github.com/lushly-dev/afd/issues/2129)). `ServerConfig.default_timeout_ms` defaults to `DEFAULT_COMMAND_TIMEOUT_MS` (`30000`), and `MCPServer` returns `TIMEOUT` when a command without a caller timeout runs past that limit (MCP Tasks remain bounded by their task TTL). Commands that run longer than 30 seconds now fail with `TIMEOUT` after upgrading: pass `create_server(default_timeout_ms=None)` (or `0`) to restore the unbounded default, or pass a larger millisecond limit.

- **`VALIDATION_ERROR` issue codes use AFD's nine-code catalog and cap at 100 issues by default** (`spec/validation.md`, `spec/execution-controls.md`, [#2129](https://github.com/lushly-dev/afd/issues/2129)). `afd.server.validation` maps Pydantic v2 error types into AFD's nine-code catalog (`VALIDATION_ISSUE_CODES`, `map_pydantic_issue_code`: `invalid_type`, `invalid_value`, `too_small`, `too_big`, `unrecognized_keys`, `invalid_format`, `invalid_union`, `not_multiple_of`, `custom`) instead of emitting raw Pydantic strings such as `missing` or `string_type`, and `ServerConfig.max_validation_issues` caps `VALIDATION_ERROR` issue lists at `DEFAULT_MAX_VALIDATION_ISSUES` (`100`, setting `details.truncated: True`). Update clients matching Pydantic error strings to match the nine-code catalog, and pass a larger `max_validation_issues` to `create_server()` (or handle `details.truncated`) if you need more than 100 issues reported.

### Added

- **App-to-app calls and `ExposeOptions.apps` parity** (`spec/command-metadata.md`, "App-to-app calls"; Loam phase 5 step 0b; #1513): `ExposeOptions.apps` (default `False`), `CallGrant`, `call_not_granted()`, `create_command_registry(call_grant=...)`, `create_server(..., call_grant=...)`, `list_by_exposure("apps")` on core `CommandRegistry`, `DirectCommandRegistry` refusing `interface="apps"`, and grant-checked `replay_journal` on `CommandRegistry` and `MCPServer`. `tests/test_app_calls_vectors.py` now runs and passes every case of `spec/vectors/app-calls.json`.

### Fixed

- **Pipeline reference keys and aliases match JavaScript's `\s` whitespace set** ([#1962](https://github.com/lushly-dev/afd/issues/1962); `spec/pipeline-variables.md`). `parse_reference`, `parse_path`, `get_nested_value`, `resolve_variable`, `resolve_variables`, `evaluate_condition` and `reads_step_data` now use an explicit 25-code-point character class matching ECMAScript `WhiteSpace` and `LineTerminator` instead of Python `re`'s Unicode `\s`: `U+001C`–`U+001F` and `U+0085` are now allowed in keys and aliases (resolving and enforcing expansion limits as in TypeScript and C++), and `U+FEFF` (BOM) is treated as whitespace (making strings containing it literals).

- Removed the MCP SDK's default `prompts` capability (always) and `resources` capability (unless `resources` or `skills` is configured), and set `resources.subscribe` and `resources.listChanged` to `false` when resources are enabled (R1).

- **A step that succeeded with `null` data reads as `null`** ([#1961](https://github.com/lushly-dev/afd/issues/1961); `spec/pipeline-variables.md`). This applies to `execute_pipeline`, `afd-pipe` and `DirectClient.pipe`, and matches TypeScript.
  - **Before:** `$prev` and `$steps.<alias>` read such a step as absent, so a reference to it was dropped from an object, and `$eq` against `null` was false.
  - **No data:** a step whose result has no data at all is still absent. `StepResult.data` is now set only when the result's data was set.

- **Boolean schemas are accepted wherever a schema may appear** ([#2047](https://github.com/lushly-dev/afd/issues/2047); `spec/validation.md`), as in C++.
  - **`true`:** it is `{}`.
  - **`false`:** it is `not: {}`, whose issue is `invalid_type` with `expected: "never"`.
  - **Command paths:** schema registration, the missing-field details, the `oneOf` discriminator and the surface complexity score all handle a boolean property. `@server.command` and `afd-schema`'s TypeScript export already handled one (#2192).
  - **Before:** registration refused `"properties": {"x": true}` and a `$ref` to a `true` definition.

- **`command_result_output_schema` follows the validators' resource rule:** `data` keeps its definitions only when its `$id` is a string that is not a bare fragment. In any other `data` schema, a `"$ref": "#"` naming `data` becomes `"#/properties/data"`. Before, it named the envelope, which is the form a recursive root schema takes. Draft-07 `dependencies` schemas are retargeted too.

- **The output schema's nullable pass walks only schema positions.** A `required` list inside a `const`, `enum`, `default` or `examples` value is data, and is now left as it is. The pass also decodes `~1` and `~0` in a reference.

- **Pipeline step inputs are bounded as in TypeScript** ([#1722](https://github.com/lushly-dev/afd/issues/1722); `spec/pipeline-variables.md`, "Limits"). Before, Python checked only the depth of the template. A step input that repeated a reference to a large value expanded it in full each time, so a small request could build an arbitrarily large input.
  - **Engines:** `execute_pipeline`, `afd-pipe` and `DirectClient.pipe` now fail the step with `VALIDATION_ERROR` (`retryable: false`, `details: {"stepIndex", "limit"}`) without running its command in these cases:
    - a value copied into the input nests deeper than 64 levels;
    - the resolved input exceeds 100,000 values;
    - it exceeds 16 MiB of string and key characters, counted in UTF-16 code units.
  - **What is charged:** only a repeated expansion of the same referenced value is charged for its contents, so one large step output still flows through `$prev`.
  - **Deep or circular step data:** before, step data nested 255 levels or deeper, or circular, could not be converted to JSON, so a reference to it resolved as absent and the step ran without it. Such data is now still viewed, as TypeScript sees it: a reference may pass through it, and copying more than 64 levels of it, or a cycle, into a step input fails on `depth`.
  - **Up-front approvals:** a step input over the limits is not resolved for approval; the step fails when it runs.

- **Referenced values in a resolved step input are copies:** a handler that mutates its input no longer changes another step's data.

- **`afd.core.wire.to_wire`** keeps `"data": null` on a `CommandResult`, a `StepResult` and a `PipelineResult` whose `data` was set to `None`, and still omits `data` that was never set, as TypeScript does. `success(None)` from a Python MCP server, its `afd-pipe` steps and its pipeline result now reach a client as `null`, not as absent. A pipeline that fails sends no `data` (#2073).

## [0.12.0] - 2026-11-22

Implements AFD contract `1.0-rc`.

### Breaking changes

- **A declared approval policy holds without the approval middleware** ([#1886](https://github.com/lushly-dev/afd/issues/1886); `spec/command-metadata.md`, "Approvals"). `create_server` and `create_direct_registry` run a command whose `approval` is `"required"` or a function only when an approval step admitted that call, for that command and that validated input. Without one the call fails with `ErrorCodes.APPROVAL_UNAVAILABLE` before the handler runs (not retryable, `details.reason: "no-approval-step"`; a policy function is not evaluated). Each batch item, pipeline step and command run from inside another command's handler is checked on its own. A server or direct registry that declares `approval` on a command and installs no `create_approval_middleware` now refuses that command: add the middleware, or set `approval="not-required"` where no approval is wanted. Core's `create_command_registry` runs no middleware and has no check.
- **A command missing from `create_approval_middleware`'s `commands` is now held** as its own policy says, under `create_server` and `create_direct_registry`: the middleware decides from the policy and `confirm_prompt` of the command each call runs, so a command registered after the middleware was built is held too. A policy given only in `commands` still holds: a call is held when either policy holds it.
- **One approval runs one handler, on the input approved.** The engine takes the admission as it dispatches, so a retry middleware placed after the approval middleware, another command name, or an input changed after the approval answers `APPROVAL_UNAVAILABLE` with `details.reason: "admission-mismatch"`. This holds for a policy given only in `commands` too. Put `create_retry_middleware`, and any middleware that changes the input, before the approval middleware. A middleware that moves `next_fn` to a thread should use `asyncio.to_thread` or `contextvars.copy_context().run`; without them, a call whose context object overlapping calls share is refused. An approval middleware admits only a call a policy of its own may gate, and every one that ever admitted a call must admit it again, matching, before each dispatch, so a second middleware that does not gate a command leaves the first one's admission to decide. Install one approval middleware per engine: two that both gate a command's own policy each ask for it.
- **An input that changes while the approval middleware decides** (in a policy function, including one an up-front `afd-batch` or `afd-pipe` step runs) answers `APPROVAL_UNAVAILABLE` with `details.reason: "admission-mismatch"`, and nobody is asked or notified. One that changes later, while a token is spent or a relayed answer awaited, is refused at dispatch the same way, so nothing runs on it.
- **An input that needs approval and has no canonical form is answered by the approval middleware** with `APPROVAL_UNAVAILABLE`, `details.reason: "input-not-canonical"`, before anyone is asked or the handler runs, where it raised `TypeError` (a `COMMAND_EXECUTION_ERROR` result) before. That covers a token check, a relayed approval and an up-front `afd-batch` or `afd-pipe` step. Send such a value in a form canonical JSON accepts (an integer above 2^53, for example, as a string). A call whose policy lets it through on such an input still runs.
- **Replaying gated journal entries needs the approval middleware.** A `replay_journal` target without it now refuses a gated command. A journal entry does not prove an approval, so replay gated commands against a target with the approval middleware, or pass only the entries recorded as successful to a target that serves those commands with `approval="not-required"`.

- **`afd-help` in the `full` format leaves out empty lists** ([#1480](https://github.com/lushly-dev/afd/issues/1480)): an entry no longer carries `tags` or `examples` when the command declares none (see Fixed). Code that reads one of them, such as `entry["tags"]`, should treat a missing key as empty.

- **The bootstrap tools are opt-in** (parity decision D5, #542): `create_server` no longer registers `afd-help`, `afd-docs` and `afd-schema` unless it is given `bootstrap=True` (also `ServerConfig.bootstrap`), as TypeScript's `bootstrap: true`. With it, the default instructions add "afd-help, afd-docs and afd-schema describe this server." The meta-tools and the context tools are listed either way. Pass `bootstrap=True` to keep the earlier tool list.

- **A command named like a built-in that is on is refused** (#1731), as TypeScript's `assertValidCommandNames` refuses it: with `bootstrap=True`, registering `afd-help`, `afd-docs` or `afd-schema` raises `ValueError`, and with `contexts`, so does `afd-context-list`, `afd-context-enter` or `afd-context-exit`. The same check runs before each `tools/list` and command call (the meta-tools included), so a command added through `server.registry` directly, a built-in turned on in `server.config` after registration, or a definition renamed after registration is refused there too, and renaming the command afterwards rebuilds the server's lookups. (`server.registry.execute` still runs the registry's own commands by any name: the built-ins are not in it.) Before, the command silently replaced the built-in. Without those options the names are ordinary commands, as before. Rename the command, or leave the option off.

- **A `$ref` inside a subschema with its own `$id` resolves against that subschema** ([#1700](https://github.com/lushly-dev/afd/issues/1700); `spec/validation.md`, "Annotations"): the JSON Schema input validator read `$id` as an annotation only and resolved every local `$ref` against the root, so a schema whose nested `$id` subschema holds its own `$defs`, such as a structured-result envelope's `data` schema, was refused at registration. A string `$id` now starts a schema resource, as in Draft 2020-12. A bare fragment such as `"#node"`, which draft-07 used as an anchor, starts no resource. The `$id` value is never resolved as a URI.
- **The advertised output schema reads a nullable definition in its own resource** (#1700): `command_result_output_schema` stops requiring a property that accepts `null`, which the wire form omits. It looked such a property's `$ref` up from the root of the `data` schema, so a nullable definition inside a nested `$id` subschema was missed, and the envelope required a property the server's own result leaves out.

- **`afd shell` keeps running when a request fails** (#1835), as TypeScript's shell does: a failed `call` prints "Call failed: ..." and a failed `tools` prints "Listing tools failed: ...", and the prompt returns. Before, the exception ended the shell with a traceback. `call` followed by a tab is a call, and a bare `call` prints its usage instead of "Unknown command".
- **The CLI prints server text as written.** A result's error code, message and suggestion, reasoning, plan steps and alternatives, tool names and descriptions, and the messages of `afd validate`, `connect` and the other commands are shown as plain text: terminal escape sequences are stripped, and Rich does not read `[/x]` as markup or `:smile:` as an emoji. So are `afd validate --surface` findings and the shell's `help`. `--json` output from `tools`, `status` and `validate` is printed as JSON without Rich, as `call --json` already was, so it is exactly what the server sent. Before, such text could end `afd call`, `afd tools`, `validate` or the shell with a Rich markup error, or change what was shown or emitted.

### Security

- **`afd.testing` scenario commands and `McpTestingServer`** now enforce project-root confinement across all five scenario tools (`scenario-list`, `scenario-evaluate`, `scenario-coverage`, `scenario-create`, `scenario-suggest`) and use the resolved paths returned by `resolve_inside`, preventing path traversal and `cwd != os.getcwd()` sandbox escapes. Direct Python callers of `scenario_list`, `scenario_coverage_cmd`, and `scenario_suggest` can pass the new `root=` keyword argument when targeting directories outside the current working directory (#1709).

## [0.11.0] - 2026-11-18

Implements AFD contract `1.0-rc`.

### Breaking changes

- **The `requestState` of a confirmation** is now a sealed JSON object that carries the questions asked and the answers of earlier rounds (`afd.server.elicitation`), so a call that needs a confirmation and then an approval asks for each in turn, and an answer counts for 10 minutes after its question was asked. A state minted by an earlier version is not an answer, and the person is asked again; no code change is needed (#1312). A confirmation answered in band on a 2025 connection is kept for the call's later rounds.

The middleware types now live in `afd.core.commands`; `afd.server` and `afd.server.middleware` re-export the same objects. The root `CommandDefinition`, `CommandContext` and `CommandParameter` are still the `afd.direct` dataclasses; build definitions for `create_command_registry()` with `afd.core.CommandDefinition`.
- **`ErrorCode`:** a `str` alias for `CommandError.code`. It is open: custom string codes remain valid next to `ErrorCodes`.
- **`TimeoutController` and `create_timeout_controller(timeout_ms=None)`:** a deadline that starts at creation, with `remaining_ms`, `is_expired` and `await controller.run(awaitable)`, which bounds the await by the time left (not the full budget) and raises `TimeoutError`. Caller cancellation propagates as `CancelledError`. With no timeout it never expires.
- **`create_progress_chunk_with_steps(progress, current_step, total_steps, ...)`:** a convenience over `create_progress_chunk`, as in TypeScript.
- **Actor, clock and random on `CommandContext` ([#400](https://github.com/lushly-dev/afd/issues/400)):** `afd.core.CommandContext` and `afd.direct.CommandContext` gain `actor`, `clock` and `random`, as in TypeScript (#271, #274). New names at `afd` and `afd.core`: `Actor` (`kind`: `human`, `agent`, `service`, `script` or `test`; optional `id`, `label`, `on_behalf_of`), `ActorKind`, `ACTOR_KINDS`, `is_actor`, `is_actor_kind`, `ContextDefaults`, `with_context_defaults`, `Clock`, `ManualClock`, `ClockInstant`, `RandomSource`, `system_clock`, `system_random`, `fixed_clock` (epoch ms, ISO string or `datetime`; `set` and `advance`) and `seeded_random`, which gives the same sequence as TypeScript's `seededRandom` for the same seed (mulberry32 over the FNV-1a hash of the seed's UTF-8 bytes).
  - The server gives every handler a clock and a random source (`create_server(clock=..., random=...)`, real ones by default) and MCP calls the actor `Actor(kind="agent")` (`create_server(actor=...)`); `server.execute()` adds no actor. Results stamp `metadata.actorKind` (the kind only, never the id), now a typed `ResultMetadata.actor_kind`, and `executionTimeMs` is read from the context clock.
  - `DirectClient` calls are `human` unless `DirectClientOptions.actor` or `DirectCallContext.actor` says otherwise; both also take `clock` and `random`.
  - `create_test_context()`, the `command_context` fixture and in-process scenario steps use `Actor(kind="test")`; `create_test_context({"now": ...})` stops the clock at `now`, and `InProcessExecutorConfig.context` sets a step context for handlers that declare a `context` parameter.
  - The telemetry middleware records `actor_kind` and, with the timing middleware, reads time from the context clock.
  - The core registry (`create_command_registry()`) now always passes the handler a context, filled with the real clock and random source.
  - `actorKind` from a TypeScript server now parses into `ResultMetadata.actor_kind` instead of `metadata.model_extra["actorKind"]`.
- **Command journal and replay ([#425](https://github.com/lushly-dev/afd/issues/425)):** parity with TypeScript's journal (#273, `spec/journal.md`). New names at `afd` and `afd.core`: `JournalEntry`, `JournalRecord`, `JournalRange`, `JournalSink`, `JournalTape`, `JournalContextDigest`, `MemoryJournalSink`, `FileJournalSink` (JSON Lines; continues numbering and drops a torn last line), `create_context_digest`, `journal_actor`, `is_journal_entry`, `serialize_journal`, `serialize_journal_entry` and `parse_journal`. Entries are written as TypeScript writes them, so `spec/wire/journal.jsonl` parses and serializes back to the same bytes.
  - `afd.server.create_journal_middleware(sink, record_failures=, filter=, redact=, max_tape_reads=, on_error=)` records each call after validation, with a tape of the clock and random values the handler read. Commands named `auth-*` are skipped by default. An entry keeps only the actor, the interface and the trace ID from the context; other context values (sessions, tokens, headers) never reach it, not even hashed: the digest hashes their names only.
  - `afd.server.replay_journal(registry, entries, ...)` re-executes entries in `seq` order with the recorded clock and random values and reports each as `same`, `different` (with paths) or `error`, with notes for a tape the replay did not use up or ran past.
- **`SimpleRegistry` handlers can take a context ([#431](https://github.com/lushly-dev/afd/issues/431)):** a handler that declares a keyword-only `context` parameter (`async def roll(sides=6, *, context)`) gets the call's context, with `actor` (`human` from a `DirectClient`), `clock` and `random`. `SimpleRegistry(clock=..., random=...)` and `create_registry(clock=..., random=...)` set the defaults. Handlers without the parameter are called as before.
- **Command name warnings:** `define_command` (so `MCPServer.command` and `register`) and the core registry, for a definition `define_command` has not already checked, emit a `UserWarning` for a name that breaks the `domain-action` kebab-case rule, as TypeScript's `defineCommand` does. The command still registers.
- **`AFDLinter(rule_severity_overrides=...)`:** sets a rule's severity to `"error"` or `"warning"`, or turns it `"off"`, through the same path every finding is emitted on, so `passed`, `error_count` and `warning_count` follow the override. Findings of an `"off"` rule are counted as suppressed with reason `severity-off`. An unknown rule id or severity raises `ValueError` (#268).
- **Lint rules `afd-no-ambient-time` and `afd-no-ambient-random` ([#403](https://github.com/lushly-dev/afd/issues/403)):** `AFDLinter` warns on `Date.now()`, argument-less `new Date()` and `performance.now()`, and on `Math.random()` and `crypto.randomUUID()`, inside the inline `handler` of a TypeScript `defineCommand(...)` call, and suggests `context.clock` / `context.random`. Calls outside handlers, in strings or comments, and `new Date(value)` are not flagged; a handler passed by name is not followed. Test and story files are checked too. The scan is lexical: strings, comments and (heuristically) regex literals are skipped, and a regex the heuristic misses can hide or misplace a handler. Both rules take severity overrides, path excludes and `afd-lint-disable:` directives.
- **`afd-no-ambient-random` follows `crypto` imports ([#430](https://github.com/lushly-dev/afd/issues/430)):** in a TypeScript `defineCommand` handler the rule also warns on `randomUUID()`, `randomBytes()` and `randomInt()` imported from `crypto` or `node:crypto`, including aliases (`{ randomUUID as uuid }`) and namespace or default imports (`import * as c` then `c.randomUUID()`). Same-named functions from other modules, member calls such as `ids.randomUUID()`, type-only imports and calls outside handlers are not flagged.
- **Ambient lint rules for Python, Rust and C++ handlers ([#409](https://github.com/lushly-dev/afd/issues/409)):** `afd-no-ambient-time` and `afd-no-ambient-random` also warn inside Python, Rust and C++ command handlers, and suggest that language's context accessor (`context.clock.now()` / `context.random.next()`; Rust `context.clock().now()` / `context.random().next()`; C++ `context.clock->wall_ms()` / `context.random->next()`). `alfred/AGENTS.md` lists every flagged call and the handler scope per language. In short:
  - **Python** (parsed with `ast`): functions decorated with `@<x>.command(...)` taking a description or `@define_command(...)`, and a `CommandDefinition(handler=...)` lambda, same-file function (matched by name) or `self.<method>` of the enclosing class. Flags `time.time()`, `monotonic()`, `perf_counter()` (and `_ns`), `datetime.now()`, `utcnow()`, `today()`, `date.today()`, `random.*` (not a seeded `random.Random(seed)`), the `secrets` generators, `uuid.uuid1()`/`uuid4()` and `os.urandom()`, only when the module was imported and is not shadowed by a handler parameter.
  - **Rust:** `impl CommandHandler for` bodies, free functions and typed closures taking a `CommandContext`. Flags `SystemTime::now()`, `Instant::now()`, `Utc::now()`, `Local::now()`, `OffsetDateTime::now_utc()`, `rand::random`/`thread_rng`/`rng`, `Uuid::new_v4()`, `OsRng`. Methods of other `impl` blocks and untyped closures are not checked.
  - **C++:** lambdas, functions and functor `operator()` taking a `CommandContext`. Flags `std::chrono::*_clock::now()`, `std::time`/`time(nullptr)`, `clock_gettime`, `gettimeofday`, `std::rand()`, `std::random_device`.
  - Rust and C++ scans are lexical (strings, comments, raw strings and char literals skipped), and parameter lists naming a `Next` type are middleware and skipped.
  - `AFDLinter` now also scans C++ files (`.cpp`, `.cc`, `.cxx`, `.h`, `.hpp`, `.hh`, `.hxx`; `.h` is read as C++), which raises `files_checked` on trees that contain them. Only the ambient rules apply to C++.

### Fixed

- **`SseTransport` on mcp 2.x:** server info and capabilities use the wire names, a dropped event stream is detected again, network errors from the SDK's `httpx2` client count as connection loss, and a tool call that never gets a response is bounded by the transport timeout.

### Deprecated

- **`SseTransport` and `HttpTransport`** (an AFD server's 2024-11-05 `/sse` and `/message` lane) are deprecated in favour of `StreamableHttpTransport`.

## [0.9.0] - 2026-10-11

Implements AFD contract `1.0-rc`.

### Breaking changes

- **MCP discovery and errors:** `afd-discover` and `afd-detail` are available in every tool strategy. Unknown and unexposed tool calls return the structured `COMMAND_NOT_FOUND` result with callable suggestions over FastMCP (#325).

- **Input validation follows the advertised JSON Schema:** raw dict schemas are accepted by command decorators and enforced before middleware, including unknown-key stripping, defaults, nullability, strict JSON primitive types and shared issue codes. Pydantic commands validate the same advertised schema before converting valid UUID and date strings. Unsupported keywords, format names and incompatible regex syntax fail registration with a schema location (#310).
- **Parallel batch failures** stop new starts and let commands already running finish normally; batch deadlines and caller cancellation still cancel outstanding commands (#330).
- **Batch and pipeline timeouts** accept finite nonnegative fractional numbers, and pipeline references use the specified 1,024 UTF-16-unit bound (#329, #283).

- **Wire format:** results use the cross-language format checked by `spec/wire/*.json`: camelCase keys, unset fields omitted rather than `null`, and MCP `isError: true` on failures. Parsing still accepts snake_case. Error `details` keys are camelCase (`expectedFields`, `missingFields`, …). The built-in command payloads (`afd-schema`, `afd-help`, `afd-docs`, `afd-context-list`, `afd-detail`) use the wire format too (#250, #251).
- **Pipeline variables** follow `spec/pipeline-variables.md`, as in every language. `$input` is the request's own `input` field and never the host or caller context; `$`-prefixed literals such as `$9.99` pass through; `$$` escapes; paths follow only own JSON keys and in-bounds indices; unresolved references are omitted; `$eq`/`$ne` compare structurally; nesting deeper than 64 is rejected with `VALIDATION_ERROR`. DirectClient `$alias` references become `$steps.alias` (#250).
- **Security:** pipeline and DirectClient `$ref` paths follow only dict keys and list indices, never attributes or `_`-prefixed names. Previously any MCP client could read server process globals and environment through `afd-pipe` (#232).
- **Security:** `afd-help`, `afd-docs`, `afd-schema`, `afd-detail` and `afd-call` only see MCP-exposed commands. `afd-call` on a command that is not exposed returns `COMMAND_NOT_FOUND` (#232).
- **Security:** handler exceptions are logged to the `afd.server` logger and returned as "An internal error occurred" unless the new `create_server(dev_mode=True)` is set. Invalid input returns `VALIDATION_ERROR` with structured details (#232).
- **Dependencies:** the extras depend on `mcp>=1.19,<2` directly instead of the unused `fastmcp`, drop the unused `httpx-sse`, and require `websockets>=14`. `afd[cli]` includes the client transports (#232).
- **Unsupported options fail instead of being ignored:** a pipeline with `parallel: true`, or a step with `stream: true`, fails that step with `UNSUPPORTED_OPTION` and skips every other step before any command runs. `stream: false` is still accepted. `BatchOptions` and `PipelineOptions` reject unknown fields (#225, #253).
- **Batches and pipelines** coerce every item to a `CommandResult` (`INVALID_COMMAND_RESULT` for a plain dict), reject built-in tools as steps, and cap size and parallelism (`max_batch_size=500`, `max_batch_parallelism=16`) (#251).
- **Batch and pipeline envelopes are checked as TypeScript checks them** (`spec/vectors/batch-controls.json`). Before anything runs, `afd-batch` and `afd-pipe` reject:
  - a blank command name;
  - `null` in place of an omitted optional field, such as `id`, `as` or `options` (a Python caller building the models may still pass `None`);
  - a string or number where a boolean belongs, and a string or boolean where a number belongs.

  A rejected batch returns a failed `BatchResult` with "Invalid batch request envelope", and a rejected pipeline returns one step at index -1 with `INVALID_PIPELINE_REQUEST`. Some malformed envelopes used to return a plain `CommandResult` ("Invalid batch request format") instead (#317).
- **Handoff:** the client sends the token as an `Authorization: Bearer` header instead of a query parameter. `ReconnectingHandoffConnection` passes the session to its reconnect command as `sessionId`, the wire name TypeScript uses, instead of `session_id`; the `ReconnectionOptions.session_id` attribute is unchanged, but a reconnect command that read `session_id` must read `sessionId` (#251, #253).
- **Retry middleware:** `create_retry_middleware()` backs off exponentially with a cap and jitter, like TypeScript, instead of linearly: retry `n` waits `min(max_delay, retry_delay * 2 ** (n - 1))` ms, randomized to between half and all of that. Invalid options (a negative or non-integer `max_retries`, a negative `retry_delay` or `max_delay`, an infinite `max_delay`) raise `ValueError`, as in TypeScript (#253).
- **Dispatch order:** the MCP server checks a call in the TypeScript order before any middleware runs: lookup, exposure, active context, then input validation. Logging, retry, rate-limit and telemetry middleware no longer see unknown commands or invalid input, and a rejected call no longer spends a rate-limit slot. Middleware receives the validated input (the schema's model instance), and a handler exception passes out through the middleware before it becomes `COMMAND_EXECUTION_ERROR`. An unknown command gets the "Did you mean" suggestion on `server.execute`, batch and pipeline steps, and `afd-call`, naming only commands the caller could call. `input=None` validates as `{}`, so a missing required field returns `VALIDATION_ERROR` instead of crashing the handler (#304).
- **Unknown and unexposed commands** follow `spec/error-codes.md` (D4). `INVALID_INTERFACE` is gone: in the core registry and the server, an interface other than `palette`, `mcp`, `agent` or `cli` exposes nothing and returns `COMMAND_NOT_EXPOSED` (`retryable: false`), and an empty interface is treated as no interface, as in TypeScript.

### Migration

- Read serialized result and built-in payload fields as camelCase; Python model attributes remain snake_case, and parsing still accepts snake_case. Omitted optional fields are absent from wire output.
- Declare `expose=ExposeOptions(mcp=True)` for commands intended for MCP, update reconnect handlers to read `sessionId`, and send handoff tokens in the `Authorization: Bearer` header.
- Make inputs conform to their advertised JSON Schema before dispatch. Remove unknown batch/pipeline option fields, omit unused optional envelope fields instead of sending `null`, and remove unsupported parallel/stream options. Catch `ValueError` for invalid retry options and review exponential backoff timing.
- Use pipeline `$input` only for request input, replace attribute/private-name references with explicit JSON keys, and check `success` when a successful result can contain `None`.
- Expect redacted handler errors by default; use `dev_mode=True` only when development diagnostics are needed. Handle `SESSION_REQUIRED` for context mutation on stateless HTTP, and supply positive finite DirectClient deadlines in milliseconds.
- Treat unknown or hidden MCP tools as `COMMAND_NOT_FOUND`; update callers that handled `INVALID_INTERFACE` to handle `COMMAND_NOT_EXPOSED`. Discover commands through `afd-discover`/`afd-detail` in every strategy. Allow already running parallel batch commands to complete after `stopOnError`, and use fractional batch/pipeline timeout values only within the finite nonnegative range.
- Install `afd[client]`, `afd[server]` or `afd[cli]` for optional integrations; base `afd` supports local DirectClient use without HTTP/MCP dependencies. The planned 0.10.0 server-defaults milestone is separate from this release.

### Stabilization

- Bind MCP contexts to trusted SDK transport sessions, cap stacks at 16, preserve independent discovery/execution, and return `SESSION_REQUIRED` for context mutation on stateless HTTP (#353).
- Enforce positive finite DirectClient deadlines in milliseconds; reject booleans as numbers and require JSON-shaped object/array inputs. Cancellation requests do not guarantee mutation rollback (#354).
- Recognize `success(None)` by its success discriminant and cap decoded SSE frames at 1 MiB by default (#354).
- Reconnect MCP clients after HTTP/SSE connection loss or idle SSE EOF, refresh discovery, cancel obsolete attempts and never replay uncertain in-flight calls (#354).
- Add real subprocess/socket protocol tests for individual/grouped/lazy strategies over SSE and Streamable HTTP. See [`spec/protocol-conformance.md`](../spec/protocol-conformance.md) for the shared acceptance index and coverage limits (#361).
- Consume the shared 34-case / 130-test validation fixture; use 24 batch, 25 pipeline, 51 reference and 27 condition cases. Unsupported schema syntax rejects registration, and issue comparisons preserve duplicates while allowing sibling ordering differences.

### Added

- `max_delay` (default 5000) and `jitter` (default `True`) keyword arguments for `create_retry_middleware()` (#253).
- `DirectClient`'s `PipelineStep` has a `stream` field, so dict and typed steps are checked the same way (#253).
- `AFD_META_TOOL_NAMES`, `AFD_BOOTSTRAP_COMMAND_NAMES`, `AFD_CONTEXT_COMMAND_NAMES`, `AFD_BUILTIN_TOOL_NAMES` and `is_afd_builtin_name`, exported from `afd` (`afd.core.builtin_names`), with the same names as the other languages (#292).
- The similarity helpers in `afd.core.similarity` (#279).
- CI: `python.yml` runs pytest on Python 3.10–3.12, bug-class ruff rules, `uv lock --check`, and a clean-venv install smoke test for each extra (#234).
- `afd.CONTRACT_VERSION`, the AFD contract version from `spec/VERSION` (now `1.0-rc`). `afd-help` returns it as `contractVersion` (#313).
- `ErrorCodes` holds the 42-code shared catalog of `spec/error-codes.md`, adding the routing, context, batch, pipeline and stream codes the engines already emit, such as `COMMAND_NOT_EXPOSED`, `UNKNOWN_TOOL`, `BATCH_TIMEOUT` and `STREAM_TIMEOUT`. `tests/test_error_codes.py` checks it against `spec/vectors/error-codes.json`.

### Changed

- The MCP server's `afd-batch` honors `parallelism`, `timeout` and `stopOnError`, and preserves result order. Pipelines enforce `timeout_ms` with `PIPELINE_TIMEOUT`, and an exception in a step becomes `COMMAND_EXECUTION_ERROR` (#225).
- A missing or mistyped MCP argument returns a structured `VALIDATION_ERROR`. `McpClient` keeps TypeScript failure details and all result fields, and posts to `/message`. Server telemetry goes to stderr (#250).
- Fuzzy "did you mean" matching and echoed unknown names follow TypeScript's `similarity.ts`, counting UTF-16 code units (an emoji is two). A name over 128 units gets no suggestions instead of being matched on a truncated prefix. Echoed names are cut at 128 units plus `…` and never split a surrogate pair. `afd-detail` uses the same matcher and suggestion text as TypeScript (up to three close matches) instead of `difflib` (#232, #279).
- `exec_command()` defaults to a 5-minute timeout. `afd connect` accepts only http(s) URLs or `mock` (#251).

### Fixed

- A base `pip install afd` imports again: MCP client exports load lazily, and `afd --help` no longer needs pytest (#232).
- There is a single `CommandError` class, so `failure(not_found_error(...))`, DirectClient error paths, and `afd-batch` timeout/`stopOnError` return results instead of raising `ValidationError`. Serialized output is unchanged (#232).
- The `scenario-evaluate` command honors its documented `concurrency` and `timeout` options and reports each scenario's file path (#234).
- **Security:** `scenario-create` and `scenario-evaluate` stay inside the project root (symlinks included), sanitize scenario names, and only read `*.scenario.yaml`/`*.scenario.yml` files (#251).
- Batches cancel in-flight siblings when they stop, and malformed pipeline conditions are rejected up front (#251).
- The handoff client reads WebSocket and SSE connections in the background, and `ReconnectingHandoffConnection` cleans up its tasks on `close()` (#251).
- `exec_command()` and the testing `CliWrapper` kill and reap child processes when the caller is cancelled. The rate limiter evicts expired windows and tracks at most `max_keys` keys. Blind excepts now log, and a crashing `SimpleRegistry` handler is `COMMAND_EXECUTION_ERROR` (#251).
- `afd validate --surface` validates a server's commands, not its tools, when the server does not list `afd-help`/`afd-schema` (for example a TypeScript server). Grouped tools are expanded from `_meta.actions`, lazy servers are enumerated with `afd-discover` and `afd-detail`, and AFD's built-in tools are skipped. The HTTP transport keeps `_meta` in `tools/list` (#292).
- **Security:** `afd-batch` and `afd-pipe` answered a command that is not MCP-exposed with `COMMAND_NOT_EXPOSED`, revealing that it exists; they now answer `COMMAND_NOT_FOUND`, exactly as for an unknown name. A tools/call for such a command no longer returns `COMMAND_NOT_IN_CONTEXT` when a context is active.
- `DirectClient`'s `UNKNOWN_TOOL` error has a `suggestion` (the closest match, or `list_command_names()`) and `retryable: false`, as in TypeScript and C++.
- The core registry's `COMMAND_NOT_IN_CONTEXT` suggestion names the command's contexts instead of the `afd-context-*` tools, which the core registry does not provide.
- A `when` condition treats a first operand that is not a reference (`"$$prev"`, `"text"`) as absent, as TypeScript does, so `{"$exists": "$$prev"}` is false. `tests/test_pipeline_vectors.py` and `tests/test_batch_controls_vectors.py` now load the shared `spec/vectors` files (#317).
- **Security:** the core registry (`create_command_registry`), the core pipeline (`execute_pipeline`) and `SimpleRegistry` no longer return exception text. A raising handler returns `COMMAND_EXECUTION_ERROR` with "An internal error occurred" and is logged, unless the new `dev_mode=True` is set. The shared helper is `afd.core.execution_failure` (#304).
