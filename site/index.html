Commands are the product.

01

Fig. 01The opacity problem

Your app is a keyhole.

An LLM can read every line of your source and still can’t use your product.

The capabilities hide behind buttons. The state lives in components. Features only fire on mouse events. So you bolt on an API later. It copies the UI, badly, and now you maintain two systems that are never quite in sync.

02

Fig. 02The honesty check

“If it can’t be done via CLI, the architecture is wrong.”

One rule, applied to every feature. No UI-only code paths. No exceptions.

02

Fig. 02The inversion

  • No UI-only code paths. If a person can do it, an agent can do it.
  • Abstraction, enforced. Logic can’t hide in a click handler if the CLI has to reach it.
  • Portable by default. No UI dependency means the same commands run on a server, a phone or a kiosk.

01Define the command

Typed input, typed output, named errors. The schema is the contract every agent will read, so it’s written first.

commands/create.ts01 / 03
import { defineCommand, success } from '@lushly-dev/afd-server';
import { z } from 'zod';

const input = z.object({
  title: z.string().min(1, 'Title is required').max(200),
  priority: z.enum(['low', 'medium', 'high']).default('medium'),
});

export const createTodo = defineCommand({
  name: 'todo-create',
  description: 'Create a new todo item',
  expose: { mcp: true },
  mutation: true,
  input,
  errors: ['VALIDATION_ERROR'],

  async handler(input) {
    const todo = store.create(input);
    return success(todo, {
      reasoning: `Created todo "${todo.title}" with ${input.priority} priority`,
      confidence: 1.0,
    });
  },
});

03Surface it last

The UI is a thin wrapper over a command that already passes. Agents call the same command your components do. No translation layer, full parity.

AddTodo.tsx03 / 03
import { createClient } from '@lushly-dev/afd-client';

const client = createClient({ url: '/sse' });

export function AddTodo() {
  const [title, setTitle] = useState('');

  async function add() {
    const result = await client.call<Todo>('todo-create', { title });
    if (!result.success) {
      // The error already says how to recover.
      return toast.error(result.error.message, result.error.suggestion);
    }
    setTitle('');
  }

  return (
    <form onSubmit={(e) => { e.preventDefault(); add(); }}>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button>Add todo</button>
    </form>
  );
}
Rendered · live calls todo-create

Hate the layout? Rip the UI out and rebuild it. The commands underneath have been passing the whole time.

Fig. 04CommandResult

Agents get judgment.

Most tools hand agents raw data and wish them luck. A CommandResult carries the trust signals that make human UX work: how sure the system is, why it did what it did, and what to do next.

Pick a field

  : true,
  : { "id": 42, "name": "Jane Doe", "role": "admin" },
  : 0.85,
  : "Matched by email. 2 accounts share this domain.",
  : [{ "code": "ELEVATED_ROLE", "message": "Confirm before mutating" }],
  : ["Run user-permissions to review roles"],
  : [{ "type": "database", "title": "users" }]
}
{
  : false,
  "error": {
    : "NOT_FOUND",
    : "No user with email 'jdoe@example.com'",
    : "Try user-search with a partial match",
    : false
  }
}

confidence: 0.85

“This match isn’t certain. I should verify before I act on it.”

A score from 0 to 1 that the command sets: 1 for exact operations, lower for fuzzy matches and inferences. Agents can gate risky actions on it; UIs can show it as a trust badge.

What most APIs send instead

{ "status": 404, "message": "Not found" }

A blank wall. The agent stalls, retries blindly or makes something up.

Fig. 05Agent UX

Not just an MCP server.

AFD started with one question: what if we applied UX design to AI agents? Every good interface pattern has an agent equivalent. AFD ships them as command metadata that the server, CLI and tests all understand.

  • Progressive disclosure

    New todoSearchExportMore ▸

    Tool strategies

    toolStrategy: 'lazy'

    Grouped by default: one tool per domain. Switch to lazy and agents see five meta-tools and pull schemas on demand, so hundreds of commands don’t flood the context window.

    Tool strategies →

  • Confirmation dialogs

    Delete all todos?This can’t be undone.
    CancelDelete

    Destructive actions

    destructive: true,
    confirmPrompt: 'Delete all todos?'

    The frontend asks before an agent’s delete runs: the same dialog a click would get, instead of a silent bypass.

    Trust config →

  • Permissions

    PaletteIn-app agentExternal MCP

    Per-surface exposure

    expose: { mcp: true, cli: true }

    Each command opts in per surface. External MCP access is off until you turn it on; the command palette and in-app agent are on by default.

    Exposure & undo →

  • Undo

    Todo deletedUndo

    Reversible actions

    undoable: true

    Agents and UIs know which steps have a way back before they take them, so they can be bolder with those and careful with the rest.

    Exposure & undo →

  • Helpful error messages

    Title is required. Try “Buy milk”.

    Recovery paths

    suggestion: 'Try user-search with a partial match'

    Every error carries a stable code, a next step and whether a retry can help. The agent recovers instead of stalling.

    Command schema guide →

  • Wayfinding

    Prerequisites

    Agents learn the order of operations up front, from the tool list, instead of from an UNAUTHORIZED error halfway through.

Fig. 06Agent-buildable

Built for the agent writing your code.

The same structure that makes an app usable by agents makes it buildable by them.

A coding agent working against commands gets a tight loop: edit a handler, run afd call, read the structured error, fix. No browser, no screenshots, no guessing which click broke the data flow. When the UI needs rethinking, it rebuilds the screen against commands that never stopped passing.

Fig. 07Testing

Test the job.

Not the UI.

Most suites test buttons and endpoints. AFD tests the job someone hired your software to do. A YAML scenario walks through a real journey: each step calls a command, checks the result and hands data to the next step.

No browser, no Selenium, no flaky CSS selectors. Surface validation then audits the command set itself for naming collisions, schema drift and prompt injection.

scenarios/todo-lifecycle.scenario.yaml
name: Create and fetch a todo
description: As a user, I can create a todo and fetch it back
job: todo-lifecycle
tags: [smoke, step-refs]

steps:
  - command: todo-create
    description: Create a todo
    input: { title: Buy groceries }
    expect: { success: true }

  - command: todo-get
    description: Fetch it by the id step 0 returned
    input:
      id: ${{ steps[0].data.id }}
    expect:
      success: true
      data: { title: Buy groceries }

Fig. 08Toolkit

The toolkit.

Packages you install, not a platform you migrate to. TypeScript, Python and Rust share one agent-visible contract.

The contract

interface CommandResult<T> { success: boolean; data?: T; error?: CommandError; confidence?: number; reasoning?: string; warnings?: Warning[]; suggestions?: string[]; sources?: Source[]; plan?: PlanStep[]; alternatives?: T[]; } @lushly-dev/ afd-core CommandResult, CommandError, batching, streaming and pipelines. Everything else builds on these types.

Serve & call

afd-server Zod commands and an MCP server factory with middleware. afd-client MCP client, plus DirectClient for ~0.03 ms in-process calls.

Validate

afd-cli Connect, call, validate and explore commands from a shell. afd-testing JTBD scenario runner, surface validation and mock servers.

Build apps

afd-auth Provider-agnostic auth: middleware, session sync, React hooks. afd-view-state UI view state as commands, so agents can drive the screen too. afd-adapters Render any CommandResult as themed HTML.

Beyond TypeScript

afd Python Pydantic results, FastMCP server, middleware, testing and handoff. afd Rust CommandResult types and a CommandRegistry. WASM-compatible.
