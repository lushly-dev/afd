Umbel

The MCP server for an AFD repo.
Built from plugins.

Umbel gives a repository one MCP server for its agents. Turn on the plugins that ship with it, add your own commands as a plugin, and every tool arrives through one registry, with a command line beside it.

    Fig. 03The host

    What the host owns.
    And what it won't.

    The rule is short: if a feature could be a plugin, it is a plugin. That leaves the host with the parts every plugin needs and no opinion about what they are for.

    It owns

    • The ways in. MCP over stdio and HTTP, and a command line, from one registry.
    • Discovery. A few tools listed first, and the rest found on request.
    • Approvals. The prompts a person answers before something lasting happens.
    • The journal. Every change is a command, so every change is an event to read back.
    • The workspace. Configuration, spaces and which plugins are on.
    • The stores. A plugin reaches data only through a grant the deployer allowed.

    It won't

    • Have a feature of its own. With no plugin, it answers about itself and nothing else.
    • Call a model to answer you. The model calling it does the reasoning.
    • Let one plugin depend on another. Shared services come from the host.
    • Treat stored text as instructions. It is labelled, scanned and never promoted on an agent's say.
    • Mix spaces. Every read and write names its space.
    Fig. 04The plugin

    Four kinds of plugin.
    One contract.

    A plugin is a directory with one manifest. The manifest names its commands, the host services it needs and why, and anything it ships to be read. How it runs is one word in that file.

    compiled
    A Rust crate linked into a host binary.
    TrustedIt runs with the host's permissions. Its grants are a declaration.
    component
    The same source, built as a WebAssembly component.
    SandboxedNo network, files or environment. Only the services its grants allow, with fuel, time and memory limits on each call.
    mounted
    An MCP server you already have, started by the host, its tools renamed under a prefix.
    A separate processIts environment is cleared, and no caller's credential ever reaches it.
    pack
    Content alone: packs and skills.
    No codeThere is nothing to run.

      05
      Fig. 05The plugins

      Seven to start with.
      All optional.

      The stock umbel binary compiles in no plugin. A second binary, umbel-first-party, compiles in these seven, and a workspace turns on the ones it wants.

      sources
      Reads a space's Markdown and code files into the stores, by content hash.
      knowledge
      Search, a graph of how documents relate, and changes by proposal that a person approves.
      memory
      What an agent learned: private unless shared, never verified, and it expires.
      context
      One bundle for a session's start, sized to a budget, with what it left out.
      components
      Briefs on a component library, from the pack Specimen builds. The one in the run above.
      curator
      Drafts settled memory as knowledge proposals. It uses no model and runs only at a command line.
      ideas
      A person's ideas, kept for good, each marked by whether that person affirmed it.

      Build it from source.
      It isn't released yet.

      Build 
      cd endpoints/umbel && cargo build --locked -p umbel-first-party --features umbel/mounted
      A workspace 
      umbel init ~/umbel-ws
      Serve an agent 
      umbel serve --stdio
      A plugin of your own 
      umbel plugin new kind=component id=notes dir=notes

      Status

      In development. Nothing is released or published: there is no package, and it builds from source with Rust. The host, the plugin contract, knowledge, memory and context, and the curator are built and tested. Hosted sign-in and other storage backends are in progress. Until then, access filtering is exact only for a program that embeds Umbel.
