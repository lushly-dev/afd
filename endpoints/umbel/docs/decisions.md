# Umbel decision log

Dated decisions that shape the design. A phase specification cites the
entries it depends on. Amend by pull request; superseded entries stay and
point at their replacement. Open decisions are listed after the log and move
into it, dated, when they close.

| ID | Date | Decision | Consequence |
| --- | --- | --- | --- |
| D1 | 2026-10-30 | Host first. Umbel is an empty host for plugins; knowledge, memory and context are first-party plugins, not the host's identity | A deployment may run the host with any set of plugins, including none of the first-party ones |
| D2 | 2026-10-30 | Vocabulary follows existing AFD extension points: plugin, command, connector, backend, adapter, pack, skill, context. "Module" and "extension" are not used | Documentation and manifests use these words only. Clarified by D23 |
| D3 | 2026-10-30 | Plugins do not depend on other plugins. Shared services come from the host through declared capabilities; composition happens at the call site through batch and pipe, or through pipelines a plugin ships as data | Every plugin is independently testable; the host grants or refuses each capability |
| D4 | 2026-10-30 | Plugins carry plain semantic names for what they do, such as `knowledge` and `content-design`. Only the host carries a botanical name | No product names on plugins |
| D5 | 2026-10-30 | The host is named Umbel, "AFD Umbel" in full. Structure names such as Trellis were rejected after collision checks found an agent harness of that name; Cyme and Rosa were rejected for collisions in the Rust and agent ecosystems | Crate, binary and area are all `umbel` |
| D6 | 2026-10-30 | The `umbel/` area at the repository root is the family home for documents now and the Cargo workspace later; the feature index points here | `architecture.json` and the release inventory gain the root when manifests land. Superseded by D21 |
| D7 | 2026-10-30 | No model in the request path. A curator may use a configured model for background work and may run as a subcommand of the same binary in a separate process | The host has no language-model client; the curator's model is deployer configuration |
| D8 | 2026-10-30 | Content, schema, packs, plugin list and backend choice live in a deployer-owned workspace; the binary ships defaults for all of them | Nothing organization-specific in code |
| D9 | 2026-10-30 | The knowledge base changes only by proposal with evidence and provenance, approved per area by a policy or a person; memory is agent-writable, scoped, bitemporal and expiring | Two stores, two write paths |
| D10 | 2026-10-30 | Store interfaces are traits with an embedded reference backend and a conformance suite; alternative backends prove themselves against the suite | A deployment may host the knowledge base on a different stack |
| D11 | 2026-10-30 | The core is Rust; plugins may be WebAssembly components built from any language, or mounted external MCP servers. No dynamic-library plugins | Connectors are not forced into Rust |
| D12 | 2026-10-30 | Each phase has one owning agent that writes a detailed specification under its folder before implementation, citing the architecture's principles and these decisions; the architecture document is the through line and is amended only by pull request | Specifications are not written ahead of their phase. Refined by D24 |
| D13 | 2026-10-30 | Every knowledge and memory mutation is a journaled command, and the event log is a projection of those journal entries with record references, the provenance envelope and per-principal cursors; subscriptions, webhooks, harness channels and audit read it | One append-only record, AFD's journal, with one projection; the coming MCP events extension becomes a projection of the event log |
| D14 | 2026-10-30 | The principal is projected onto AFD's command context: the actor with `onBehalfOf`, and the `credentials` MCP Authorization proposes. Umbel's extension fields add at least the delegation chain, token binding, a human-presence flag and the policy decision. Commands that need a present human use AFD's confirmation prompt under `require-human`; enterprise-managed authorization is accepted on connections as an extension of MCP Authorization | Audit records both the agent and the person it acted for, in AFD's own fields |
| D15 | 2026-10-30 | Memory records carry episodic, semantic and procedural class labels, and nothing in memory is verified knowledge. The curator proposes stable semantic memory as knowledge entries and stable procedural memory as skills in a pack, always through proposals. Knowledge entries carry a verification lifecycle in the Open Knowledge Format's terms: `verified` events with an owner tier, `stale_after` as the verify-by date, `deprecated` for replaced entries; the curator re-verifies and raises inconsistency proposals instead of choosing silently | Promotion into durable knowledge has one path, the proposal |
| D16 | 2026-10-30 | The on-disk knowledge container is compatible with the Open Knowledge Format v0.2: one concept per file, path as identity, `type` required, `title`, `description`, `resource` and `tags` recommended, provenance in `sources` and `generated`, optional reserved `index.md` and `log.md` | Import and export with the converging markdown-with-frontmatter tools costs a naming convention |
| D17 | 2026-10-30 | A proposal is a domain record owned by the knowledge plugin and is recorded as a decision trace: policy applied and its version, evidence with content hashes, exception, approver, proposing agent and run, resulting state. AFD approval gates only the command that applies it | Umbel traces its own knowledge decisions and does not try to capture other systems' |
| D18 | 2026-10-30 | Mounting external MCP servers is a first-class capability, not an example: the federation path across vendor systems, with indexed-copy and live modes. Phases 0 and 1 are the core and come first; the knowledge plugin, phase 2, is the first plugin because every deployment needs it first and it exercises every host service; federation and other first-class plugins come after phase 2, unnumbered, each with its own specification. Only the mounted loader kind lands in phase 1 | One sequencing rule, quoted by the architecture, the proposal and the status |
| D19 | 2026-10-30 | Reserve seams, do not implement drafts: the result-contract wire shape, progressive-discovery mechanics, HTTP over stdio, DPoP and workload-identity enforcement, agent-to-agent endpoints and interceptors wait for final specifications, tracked in the [trajectory watch](trajectory.md) | Phase specifications cite the watchlist row, by its W number, for anything they depend on |
| D20 | 2026-10-30 | Progress lives in [STATUS.md](STATUS.md), not in the codebase. | D25 | 2026-10-30 | AFD first. | D26 | 2026-10-30 | A deployment holds one or more spaces, each an isolated knowledge base with its own content roots, stores, memory, event stream, packs, curator policy and permissions. Separate deployments remain the stronger boundary and can compose through federation | Isolation lives in the store traits and the event log from phase 0, not retrofitted; one owner can keep domains apart in one deployment |
| D27 | 2026-10-31 | The execution model is the hybrid strategy, the owner's choice that closes O2: a few first-class tools for the hot path, listed alongside lazy discovery and the meta-tools (`afd-discover`, `afd-detail`, `afd-call`, `afd-batch`, `afd-pipe`); a sandboxed code-mode plugin may follow later and stays optional. Rationale: the tool list stays fixed as plugins grow, commands change without the client reloading tools, the hot path is one call and combinations run in one call through batch and pipe; the lazy strategy alone costs a discovery round trip on every hot-path call.
