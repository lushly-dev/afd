# Loam decision log

Dated decisions that shape the design. A phase specification cites the
entries it depends on. Amend by pull request; superseded entries stay and
point at their replacement. Open decisions are listed after the log and move
into it, dated, when they close; O10 to O17 opened and closed on 2026-10-31
from the [landscape](landscape.md). D1 to D21, D23 and D24 were proposed in
the design session of 2026-10-30; the owner decided D22 on 2026-10-30 and
D25 to D49 on 2026-10-31. D50 to D53 were proposed by the phase 0
specification and decided when the owner approved it on 2026-11-01. The owner decided D54 to D58 on 2026-11-01, on the [shared plugin manifest proposal](../../../docs/features/active/plugin-manifest/plugin-manifest.proposal.md). Three independent reviews on 2026-10-31 corrected
facts and wording in some entries; each correction is marked "Corrected
2026-10-31" in its consequence, and none changes what was decided.

| ID | Date | Decision | Consequence |
| --- | --- | --- | --- |
| D1 | 2026-10-30 | Shell first. Loam is an empty shell for apps; projects, settings, experiments, account, notifications and the agent panel are shell sections because each aggregates across apps; everything with a domain is an app | A deployment may run the shell with any set of apps, including none of the first-party ones. The agent panel is the copilot since D24, and the documents section, runs and the builder joined the shell sections in D23, D42 and D47 |
| D2 | 2026-10-30 | Apps are plugins under a manifest, and surfaces are opt-in. The shell renders only what a manifest declares; nothing is inherited between apps; shared behavior arrives only through named compositions | Adding an app or a document type to one app never changes another |
| D3 | 2026-10-30 | Everything the shell knows is a command. Layout is the view-state commands, extended by layout presets; scope, overlays, settings, experiments, identity and navigation are commands; agents, tests and automation drive the shell as people do | The TypeScript view-state package is the contract; the kernel implements it in Rust. Revised by D25: the kernel is TypeScript and uses the package directly |
| D4 | 2026-10-30 | Scope is shell-level, with two levels, workspace and project. Every app declares the scopes it supports. The active project narrows, never grants, and a cross-project mutation is refused after the access decision. Scope is explicit per request: a command-context field in process, `_meta` over MCP, the path in the URL; never connection state | One `scope` on every command; `tools/list` never varies per connection |
| D5 | 2026-10-30 | The rail has two bands with a divider: the projects section and the project switcher head the top band, which lists apps that subscribe to the project scope; the bottom band lists apps that never take a project | The question "which apps care about my project" is visible; the rule for dual-scope apps is open decision O2, closed by D29 |
| D6 | 2026-10-30 | Overlays are shell resources with an owner and a lifetime, opened only through shell commands, following the policy table in the architecture when the active app changes; one modal at a time shell-wide; toasts render only in the shell's region | No app leaks a toast, dialog or modal into another; parked dialogs return with their app |
| D7 | 2026-10-30 | Layout is data: a parts model, constraints, presets and compositions, with persisted view-state per app and scope. Apps request; the shell decides. No app positions chrome | The shared UX engine stays opt-in and testable |
| D8 | 2026-10-30 | The kernel is Rust and the chrome is FAST-AF web components on Violet tokens. One crate compiles to WebAssembly for the browser and natively for the desktop and the hosted server; the DOM is driven by thin TypeScript bindings the SDK wraps. A chrome rendered by Rust is reserved, not chosen | App authors never touch Rust; the kernel has no DOM dependency. Superseded by D25 |
| D9 | 2026-10-30 | Three app kinds: a native ES module under a scoped registry, a sandboxed view on the MCP Apps profile, and a mounted AFD server rendered by the console. They mirror Umbel's loader kinds | Anything with commands can be in the shell on day one; any MCP server with Apps support appears with no Loam code |
| D10 | 2026-10-30 | The app manifest extends the plugin manifest Umbel and Plugin Discovery define, with UI contributions as an extension; the event shape and the grant vocabulary are shared; a shared crate is extracted when both hosts exist | A plugin with UI is one manifest; no second plugin contract in the repository. Corrected 2026-10-31: Umbel's manifest is still its open decision O3, so Loam will extend the manifest Umbel settles; the event fields both have keep Umbel's names, while Loam's cursors are per app and carry no provenance envelope where Umbel's are per principal with one; the UI contributions are an addition, not an extension in MCP's sense; after D25 the shared artifact is a schema package, not a crate |
| D11 | 2026-10-30 | Identity once, on `@lushly-dev/afd-auth`: Better Auth is the first production adapter, Mock for tests, Convex kept. Persona is a lens (presentation, defaults, emphasis), never a grant; authorization stays with the provider's roles and per-command scopes. The persona id travels in Loam's context fields, not in the actor | Apps receive the actor and the scope, never credentials; a persona can hide nothing that a role allows |
| D12 | 2026-10-30 | Experiments are flags with a lifecycle (hidden, visible, enabled, graduated, removed), off by default, opted into per person, enablable workspace-wide by an owner, with what may change and a graduation date shown; an app or a surface may require one | Nothing experimental reaches anyone who did not ask; every flag has an end |
| D13 | 2026-10-30 | Vocabulary: app, command, interface, surface, part, section, composition, scope, workspace, project, overlay, owner, experiment, persona, account, grant, kit, kernel, SDK. "Surface" means a shell region here and a transport in Umbel; the glossaries cross-reference each other. "Module" and "extension" are not used except in MCP's sense | Documents and manifests use these words only; a new term enters the glossary first. Extended 2026-10-31: "delegation" names the copilot handing a turn to another agent, so AFD's handoff pattern keeps its own word; the cross-reference from Umbel's glossary is a follow-up |
| D14 | 2026-10-30 | Loam lives in `endpoints/loam/`, following Botcore's layout: the kernel, hosted server, desktop app, chrome, SDK, kit and first-party apps are endpoint units beside these documents. A dependency-free layout engine or overlay manager, if one emerges, goes under `foundations/`. `loam` joins `architecture.json` and the release inventory when the first manifest lands; every unit starts quarantined | No new discovery root; the boundary rule that a foundation cannot depend on another family holds. Corrected 2026-10-31: `architecture.json` lists foundation families only, so Loam's units are classified as endpoints by path, as Botcore's and Health's are; `pnpm-workspace.yaml` gains a glob for `endpoints/loam/*` packages and the release inventory gains the units. Amended 2026-11-01 by the phase 0 specification: the glob is `endpoints/loam/packages/*`, because `endpoints/loam/*` would also match `docs/` |
| D15 | 2026-10-30 | AFD first. Where AFD has or proposes a mechanism, Loam uses or extends it: results, actor, context fields, exposure, confirmations, approvals, the journal, composition, discovery, view-state, the auth adapter, adapters, surface validation, scenarios, CLI exit codes and telemetry. Generic features Loam needs land in AFD first, specified for every language where they are cross-language | The architecture's Built on AFD and prerequisites tables are the map; any divergence is a new decision |
| D16 | 2026-10-30 | Progress lives in [STATUS.md](STATUS.md), not in the codebase. The status and every phase specification carry the status block: state, last verified with date and evidence, exactly what is done, exactly what is not, follow-ups not yet issues. A session that changes Loam updates it before ending | An agent reads the status first and never scans the code to learn what is current |
| D17 | 2026-10-30 | A phase specification lives at `endpoints/loam/docs/phases/<n>-<slug>/spec.md`, opens with the status block, cites the principles and decisions it serves, refreshes the trajectory rows it depends on, and is approved by the owner by pull request before implementation | Every phase starts from the same shape and the same approval |
| D18 | 2026-10-30 | Only the shell carries a botanical name. Apps carry plain semantic names for what they do, such as `projects`, `console`, `violet` and `health`, and their commands follow AFD's `domain-action` rule with the app id as the domain | No product names on apps; a mounted server's tools are renamed under the mount's prefix |
| D19 | 2026-10-30 | The first consumer is a Lushly support application: internal tooling for building Lushly, specified in Lushly's repository. Nothing Lushly-specific lives in Loam; a need the consumer surfaces is recorded in the status as a generic shell need before it is built | The shell stays usable by any deployment |
| D20 | 2026-10-30 | Loam imports no code from other shells. Prior designs inform the research through their public documentation only, cited in the source ledger; everything here is written against this architecture | Provenance is clean from the first commit; the research cites what it learned from |
| D21 | 2026-10-30 | Apps are web components written in TypeScript, HTML and CSS against the SDK. The SDK's client is the only way an app calls a command; transports (in-process, IPC, HTTP, MCP) and the kernel, Rust when this was decided and TypeScript since D25, never appear in an app, and nothing in an app changes between hosts. Confirmed by the owner | A consumer team ships an app with no Rust, REST or MCP knowledge |
| D22 | 2026-10-30 | The shell is named Loam, "AFD Loam" in full, decided by the owner. The crate is `afd-loam`, the packages `@lushly-dev/loam-*`, the area `endpoints/loam/`. The colliding projects, a file-based tree storage crate, the Loam SDK for Soroban smart contracts (upstream `loambuild/loam`: 3 stars, 7 forks, last pushed 2025-06-03, checked 2026-10-30) and a dormant npm GDAL wrapper, are none of them shells and none is widely used, and the scoped unit names avoid them. "AFD Shell" was rejected because the `afd` CLI already has a `shell` subcommand; Coldframe and Potager were clean but not chosen. Closes O1 | Crate, packages and area keep these names; the botanical register of D18 holds |
| D23 | 2026-10-30 | Documents are shell resources and document types are contributions. Any plugin may declare document types (schema, templates, editor, instance commands, optional surfaces); an instance has one model and any number of editors in the editor area, the main part when documents are open; New, tabs, splits, recents, search, trash and the references index are the shell's; documents reference each other through resource links and commands under `calls` grants, never through each other's code; the document's UI stays inside its editor frame and is built from the kit | A document is an application in miniature with the shell's frame around it; adding a type changes no other type |
| D24 | 2026-10-30 | The copilot is a shell section built on AFD: agents, delegations, sessions and turns are Loam's records on AFD's actor and journal; tools are the registry under `expose.agent`, through the DirectClient in the browser and the hosted registry on the server; confirmations and approvals are AFD's, mapped to the runtime's interrupts; the model SDK sits behind a runtime adapter that owns nothing durable; the runtime is TypeScript, a worker in the browser, a service beside the hosted server, a sidecar on the desktop; the stream to the panel is AG-UI events; providers swap by configuration; no vendor copilot SDK | The SDK can change without changing an app. Renamed 2026-10-31: handoff became delegation (D13). Runtime placement revised by D25: in-process on the hosted Node server, a worker in the browser and the desktop webview |
| D25 | 2026-10-31 | TypeScript first, Rust where it pays. The kernel, stores, identity, copilot runtime, hosted server and chrome are TypeScript on AFD's TypeScript packages; the desktop is Tauri 2 with the kernel in the webview and Rust only in Tauri's host and native plugins; Rust enters otherwise only as WebAssembly modules behind TypeScript interfaces when a measurement on a real workspace shows a need, and in Umbel, which is mounted. Rust is not chosen for its own sake. Supersedes D8; closes O4 | No prerequisite waits on Rust parity; every AFD TypeScript package and Lushly's code are reused directly; a single static binary, a Rust server's memory floor and a shared crate family with Umbel are given up; `afd-loam` from D22 is reserved for any Rust unit that lands |
| D26 | 2026-10-31 | Design foundation before UI. Violet is the token engine; Loam's semantic token layer as a Violet theme in light, dark and high contrast, the bridge onto the FAST-AF components' theme registries, the design document in the shape of the afd.dev design record, its authoring skill and the component checklist are phase 0 deliverables, before the chrome grows past a skeleton. Components are built and styled as they are needed, under the checklist, and reference semantic tokens only, verified by a lint | No catalog built ahead of use; no component without the system behind it. Revised by D28: the components consume Violet themes in place of their local registries rather than through a bridge |
| D27 | 2026-10-31 | The copilot runtime is TanStack AI 1.0 behind the runtime adapter of D24. Closes O9. The adapter keeps the choice reversible; a spike of the headless client inside a web-component panel is the first task of the phase 5 specification; Lushly's copilot code is inventoried for shared libraries under D19 | Provider adapters, isomorphic tools, subagents with typed input and limits, `decide()`, approval interrupts and the AG-UI stream come from the SDK's stable core; agents, delegations, runs, sessions and approvals stay Loam's records. Corrected 2026-10-31: durable sessions and budgeted parallel agents are in TanStack AI's experimental harness, not its 1.0 core; Loam does not need them, because sessions and runs are its own records (D24) |
| D28 | 2026-10-31 | One component set, many Violet design systems. The FAST-AF components in `foundations/fast-af` are the shared set for Loam, Lushly and any consumer; they consume Violet themes through the Violet runtime, as CSS custom properties with baked-in defaults, in place of their local theme registries, which exist only because Violet was not ready when they were built. Loam's theme and Lushly's theme are two Violet design systems feeding the same components; a consumer swaps the theme, never the components. Lushly's move to Violet throughout starts with the shared components and is specified in Lushly's repository; edits to the imported components follow the FAST-AF provenance rules | Nothing is forked; the design foundation's first deliverable is the components' token mapping, in phase 0. Revised by D50: the components take Violet's output as data and custom properties, not through the runtime, since `foundations/fast-af` may not depend on Violet |
| D29 | 2026-10-31 | An app that supports both scopes appears once in the rail: in the top band under the project when one is active, otherwise in workspace scope, with its workspace resources and project resources kept apart in its sidebar. Closes O2 | One entry per app; the band says whether the app cares about the project |
| D30 | 2026-10-31 | App-to-app calls need both the callee's `apps` exposure flag, new in AFD beside palette, agent, MCP and CLI and off by default, and the caller's `calls` grant; the flag is specified for every language as an AFD feature. Closes O3 | The callee declares, the caller is permitted, the kernel checks both; one small AFD proposal before phase 5 |
| D31 | 2026-10-31 | Scope is a field Loam adds to AFD's command context first, as Lushly extends it for tier and surface; it is proposed AFD-wide when a second consumer needs it, unified with Umbel's space rather than added beside it. Closes O5 | No AFD-wide context field for phase 2. Corrected 2026-10-31: over MCP the scope needs AFD's MCP server to forward a declared `_meta` key into the command context, and the journal needs to keep declared context fields; both are AFD prerequisites, with scope as command input as the fallback |
| D32 | 2026-10-31 | A hosted deployment is single-tenant; workspaces bind to the identity provider's organizations; a reserved tenant field stays for later. Closes O6 | No multi-tenant isolation work without a consumer |
| D33 | 2026-10-31 | Mobile is responsive chrome in the browser first: the rail becomes a bottom tab bar and the sidebar a drawer; Tauri mobile stays reserved until the desktop lane is stable. Closes O7 | Responsive rules are a phase 0 deliverable |
| D34 | 2026-10-31 | Scoped custom element registries are polyfilled in Firefox through the dependency fast-element already carries, and the polyfill is retired when watchlist row W3 says Firefox shipped. Closes O8 | No browser excluded, no new dependency. Corrected 2026-10-31: Firefox 159 shipped scoped registries on 2026-10-27, so the polyfill serves only older Firefox and is retired when the support floor reaches 159 |
| D35 | 2026-10-31 | Documents get their own specification beside scope and projects inside phase 2, because the editor area and the reference index are each as large as the project store | Two specifications, one phase, one owner |
| D36 | 2026-10-31 | The hosted server runs on Hono: one Node process serving the SPA, MCP through the SDK's Hono package, REST, Better Auth and the copilot's TanStack AI routes, all on web-standard Request and Response; the owner's other applications already use it | Revisited only if libraries extracted from Lushly assume another host. Corrected 2026-10-31: AFD's `createMcpHandler` is a Node `(req, res)` handler, so MCP goes through it mounted by Hono's Node adapter; the SDK's own Hono package would bypass AFD's Host and Origin checks, contexts, confirmations and approval relay; a fetch-style AFD handler is an optional prerequisite |
| D37 | 2026-10-31 | A Rust WebAssembly accelerator is admitted only by a written rule: a named operation on a reference workspace of documented size measured above a budget in CI, with the TypeScript implementation kept as the fallback; the operations and budgets are set in the phase 0 specification | D25 is applied by evidence, not taste |
| D38 | 2026-10-31 | The shared components take Violet themes as Violet's exported CSS custom properties, with defaults baked in from the Loam theme, so a component renders without the runtime present and a consumer mid-transition to Violet can still use it | The mapping from component tokens to Violet names is the design foundation's first artifact |
| D39 | 2026-10-31 | The registry projects into agent hosts. Commands exposed to MCP register as WebMCP tools in the browser from phase 5, behind feature detection; an MCP bundle for the Windows registry, AppFunctions and App Intents are reserved until those previews settle and Tauri mobile lands. Closes O10 | No new commands; projections of `expose` only |
| D40 | 2026-10-31 | Agent members. An agent identity has a human sponsor, is installed by a workspace owner, is scoped to projects, is not a seat, is visible on delegated work with the person still accountable, cannot sign in or administer, and reads workspace and project guidance; AFD's actor with `onBehalfOf` is the wire form. Identities in phase 3, delegation and guidance in phase 5. Closes O11 | Agents are members of the workspace, not callers outside it |
| D41 | 2026-10-31 | Autonomy policy and approval health. Suggest, ask or act per workspace, project, app and command, inherited downward; approval of a plan or a capability within limits; the resolved action always shown; approval volume, override and auto-approve rates reported as a control-health signal; tool results and mounted content labeled untrusted in the copilot. Settings in phase 4, enforcement in phase 5. Closes O12 | OWASP's ASI09 is answered in the interface, not the model |
| D42 | 2026-10-31 | Runs are shell resources: a copilot session with scope, isolation (sandbox, or a worktree for code), plan, artifacts and status; a runs list; scheduled automations; pause, redirect and stop by anyone with access; shareable in a project. Records in phase 5; the section when the first consumer needs it. Closes O13 | The unit of agent work is the run, not the chat |
| D43 | 2026-10-31 | A2UI is the second agent-UI path after the MCP Apps view, with the kit as its component catalog and the Lit renderer as the start, themed by the design foundation; phase 5 or later. Closes O14 | Agent-declared UI renders native components, not iframes |
| D44 | 2026-10-31 | Agent packs. The copilot's agent surface loads Agent Skills directories first and plugin-shaped directories second: skills, `.mcp.json` connectors as mounted servers, commands as palette entries, sub-agents as specialists; an app may be only a pack. Phase 5. Closes O15 | Existing open role plugins work without Loam code |
| D45 | 2026-10-31 | On-device models are watched, not built: a provider joins the runtime adapter when the platform reports a model and the Prompt API is on by default on pages, for suggestions, summaries and classification only. Closes O16 | No consequential action on an on-device model. Corrected 2026-10-31: Chrome 148 shipped the Prompt API on pages on 2026-05-05, so Chrome meets the condition; Mozilla objects and WebKit opposes; the provider still waits for the runtime adapter to be stable |
| D46 | 2026-10-31 | Multiplayer is a shell service, not a document type's feature. Collaboration has four parts, sync, presence, sharing and threads, bound by a contract every document type declares from phase 2, and every run when run records land in phase 5 (D42), so no type is built for itself. The command journal is the system of record; fine-grained concurrent content merges through a CRDT whose updates travel as commands; structured fields default to per-property last-writer-wins with the server ordering; presence is ephemeral and expressed in the type's selection model; sharing is membership plus links with generations, and live sessions revalidate authorization when membership changes and rebind when still authorized; agents are collaborators with presence and attribution; threads anchor to the type's locators. Its own specification after phases 2 and 6. Closes O17 | The earlier one-type multiplayer is not repeated; every document and run shares one service |
| D47 | 2026-10-31 | Loam is the development environment for its own apps. From New, "App" creates a draft app in the workspace and opens the builder: the console as the draft's first stage and the copilot with the builder agent, a specialist carrying the SDK skill, the design skill and the `app-*` commands. The agent has no terminal and no file system; it builds through journaled commands against the store, under the autonomy policy. Drafts run as sandboxed views by default with the kit delivered inside and tokens as custom properties; promotion to the native kind is a review step. Publish is a lifecycle, draft, checked, published to self, published to the team, each publish a version with a changelog, team publication approved by a workspace owner; a published app is a versioned, revocable artifact in the workspace store. A repository is optional: `app-export` writes a package the repository workflow accepts, and a repository app can be edited in the builder through the same commands | Loam is the operating system and the development environment; capability is bounded by the registry, every action is journaled, code runs sandboxed until promoted, nothing leaves the workspace without a publish |
| D48 | 2026-10-31 | The console is every app's first UI. A new app's main surface is the console, command list, forms from input schemas, results through the adapters and the journal of calls, until views replace parts of it; a usage view reports which commands run through the palette, the copilot, MCP, other apps or a view, so UI is built where it is used | "No UI yet" is a shippable state, measured |
| D49 | 2026-10-31 | Builders get, by declaration: a document type kit with a text editor and a form or table editor so a collaborative document needs no editor code; triggers from their events and actions from their commands, composed by the automations surface; affordance tests in the test kit that grade whether a model selects their commands from their descriptions, contexts and skills; packaging as workspace artifacts or npm packages validated by `app-check` on install, with no app store | Each is a builder promise in the proposal and a phase deliverable |
| D50 | 2026-11-01 | Revises D28. The shared components take Violet themes as data and custom properties, never as a package dependency, because the boundary rule forbids a foundation from requiring another family: `violet-elements` generates its presets from a committed export of Loam's resolved themes (`tokens/violet-theme.export.json`), its literal fallbacks are checked against the light theme, and its local registries are retired; Loam's theme package writes and checks the export; `VioletRuntime` gains a preloaded source so consumers may apply a Violet theme at runtime with no token server. Decided with the [phase 0 specification](phases/0-kernel-chrome/spec.md) | D28's one component set and many design systems hold without coupling two foundation families; a consumer applies its own Violet output at its root and changes nothing in the components |
| D51 | 2026-11-01 | `appearance` (theme and density) and `palette` join the shell domains in phase 0; phase 4's settings take over appearance's storage without changing its commands. Decided with the phase 0 specification | Theme and density are commands from the first build, so light, dark and high contrast are driven and replayed like layout |
| D52 | 2026-11-01 | The desktop's store backend is IndexedDB in the webview, as in the browser; SQLite through a Tauri plugin is admitted in phase 6 only on a measurement. Decided with the phase 0 specification | One store backend for two hosts in phase 0; nothing waits on Tauri |
| D53 | 2026-11-01 | Specimen gains a `high-contrast` theme context, emulated as Playwright's light scheme with `prefers-contrast: more`, so the chrome's captures cover the three themes; forced colors and axe stay in Loam's Chromium suite. Decided with the phase 0 specification | The exit criterion's captures and checks cover high contrast without a second capture harness |
| D54 | 2026-11-01 | Native apps are trusted code, not sandboxed, as Umbel's compiled plugins are. Isolation is enforced for sandboxed views and mounted apps | A module in the shell's own page cannot truly be isolated, so the shell does not claim it. `app check` says "trusted, not sandboxed"; untrusted apps ship as views. The architecture's isolation text is amended |
| D55 | 2026-11-01 | Until Umbel's phase 5, a Loam instance may mount a team Umbel instance only where every member of its projects may read all of it. Access is decided in Loam by project membership; team instances use HTTP | Umbel sees one principal until then and cannot separate Loam's members. `app check` and the console say so |
| D56 | 2026-11-01 | A stdio instance is trusted code. Only the person who owns the workspace on the desktop, or the deployer's configuration on the hosted server, can add or change its `command`; no command, app or agent may write it, and the autonomy policy cannot grant it | The child runs as the host's OS user, and the command line is held in workspace data. The builder (D47) cannot reach it |
| D57 | 2026-11-01 | Phase 1 proves the mounted-server app kind end to end against a real Umbel instance, shown in the console. The first-party Umbel app stays after Umbel's phase 2 and Loam's phase 5 | Umbel-specific gaps show up early; `loam.yml` gains a Rust build |
| D58 | 2026-11-01 | The [shared plugin manifest](../../../docs/features/active/plugin-manifest/plugin-manifest.proposal.md) is a host-neutral core in `spec/` with one closed profile per host; Loam's phase 1 writes Loam's profile. One or more Umbel instances join a Loam instance as headless mounted apps, with instance identity apart from app identity, a command prefix per instance, and `error` on conflicts. Umbel stays headless in Loam for now, and signing waits for W9 | Refines D10: Loam's schema does not reference Umbel's `$defs`, which are closed and host-specific.
