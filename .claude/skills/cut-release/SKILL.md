# Cut Release

AFD's four implementations each follow semver on their own API, with their own version, changelog, tag and release path; before 1.0 a minor release may break the API. They are four of the admitted units in `scripts/release/inventory.json`; `botcore` publishes `lushly-botcore` alone, and Specimen's four units, `fast-element`, `violet-elements` and `violet-npm` publish an npm prerelease under `preview`. Every other unit there, the other five Botcore distributions included, is quarantined and has no release path: stop and ask. The three `*-changes` units are the private stubs that hold a track's version for Changesets (below); nothing publishes them.

**Publishing is irreversible and is the maintainer's job.** An agent prepares the release PR: version, changelog and docs. It does not push tags, create GitHub Releases, merge or enqueue the npm version PR (merging it publishes), run a publish workflow, or change repository or registry settings. The one exception is when the session's user, in the current turn, names that irreversible step ("push the `rust-v0.2.2` tag", "merge the version PR"); a request to cut, ship or prepare a release is not that. Then run only the named step, on the reviewed merge commit.

## Tracks

| Track | Version lives in | Changelog | Tag | Published by |
|---|---|---|---|---|
| npm: the nine `afd-npm` packages | each `package.json`, set by Changesets | `packages/*/CHANGELOG.md`, by Changesets | `@lushly-dev/<package>@X.Y.Z`, by the release finalizer | `release.yml` to npm |
| npm preview: Specimen's eight packages, `fast-element`, `violet-elements` and Violet's five | each `package.json`, set by Changesets as `X.Y.Z-preview.N` | each package's `CHANGELOG.md`, by Changesets | `@lushly-dev/<package>@X.Y.Z-preview.N`, by the release finalizer | `release.yml` to npm under `preview`, with GitHub prereleases |
| Python `afd` | `python/package.json` (the private stub `afd-python`), set by Changesets; `pnpm version-track python` copies it to `python/pyproject.toml` and `__version__` in `python/src/afd/__init__.py` | `python/CHANGELOG.md`, by `pnpm version-track python` | `python-vX.Y.Z` | `publish-python.yml` to PyPI |
| Rust `afd` crate | `packages/rust/Cargo.toml` | `packages/rust/CHANGELOG.md` | `rust-vX.Y.Z` | `publish-rust.yml` to crates.io |
| C++ `afd-cpp` | `project(afd VERSION …)` in `packages/cpp/CMakeLists.txt` | `packages/cpp/CHANGELOG.md` | `cpp-vX.Y.Z` | Nothing: consumers fetch the tag with CMake |
| Botcore `lushly-botcore` | `endpoints/botcore/package.json` (the private stub `lushly-botcore`), set by Changesets; `pnpm version-track botcore` copies it to `endpoints/botcore/pyproject.toml` and `__version__` in `endpoints/botcore/src/botcore/__init__.py` | `endpoints/botcore/CHANGELOG.md`, by `pnpm version-track botcore` | `botcore-vX.Y.Z` | `publish-botcore.yml` to PyPI |

Read current versions from those manifests, and published ones from the registries and `git tag -l`. The private root `package.json` version is not a release; never set one there.

- The root `CHANGELOG.md` is an index; never add release notes to it.
- No no-op changeset for Rust, C++ or docs-only work, and no no-op fragment for Python or Botcore. A docs or package-description fix waits for the next release; never claim a published artifact changed.
- A hotfix has no separate path: branch from `main` (there are no `release/*` branches), add a `patch` changeset (for Python or Botcore, a `patch` fragment that names its stub) or the Rust or C++ changelog entry, and follow the track's steps.
- Until the new version or tag is verified, install snippets stay on the last published one. Then update package READMEs, skills, `site/index.html`, `site/js/runtime.js` and `site/llms.txt` together.

## Contract version

`spec/VERSION` (now `1.0-rc`) versions the shared contract: `spec/wire`, `spec/pipeline-variables.md`, `spec/vectors` and the conformance suite. Each implementation exports the version it implements (`AFD_CONTRACT_VERSION`, `afd.CONTRACT_VERSION`, Rust `afd::CONTRACT_VERSION`, C++ `afd::contract_version`). It stays `1.0-rc` until all four languages load every vector file, and changes only through the shared specification process, never in a release. Name it in the changelog section (`pnpm version-track python` writes that line) and the tag message; `node scripts/check-versions.mjs` fails when a constant or the Contract row of `docs/language-parity.md` disagrees.

The version in `spec/package.json` (the private stub `afd-spec`) is not the contract version. Changesets needs a semver number to consume a fragment, so that one only counts folds of `spec/CHANGELOG.md`: `pnpm version-track spec` moves the pending contract entries into the changelog under the heading of the version in `spec/VERSION`, and never writes `spec/VERSION` or a constant. It is not a release, so run it whenever fragments that name `afd-spec` are pending and a release PR is being prepared, or when asked.

## Every release

- The track's CI and `conformance.yml` are green on the exact candidate, and again on the merge commit.
- Each Rust, C++, Python and Botcore changelog gets a dated section, breaking changes first with migration notes, under an empty `Unreleased` section (an npm package's changelog has none: Changesets writes its sections from the changesets). For Rust and C++ write it by hand from the entries under `Unreleased`. For Python and Botcore `pnpm version-track <track>` writes it from the fragments in `.changeset/` that name the track's stub, and takes the version from their bumps; read the result, then add an introduction or migration notes to the dated section by hand where the fragments lack them. Never set those two versions, write a section or add under their `Unreleased` by hand: `pnpm check:tracks` (in `pnpm check` and the pre-push hook) fails when the stub, `pyproject.toml`, `__version__` and the newest section disagree, and on anything under `Unreleased`.
- `pnpm version-track` runs Changesets on the stub alone, in a disposable worktree, and writes to the checkout only what the track owns. It needs `uv` for the locks and the provenance records; `--skip-tools` skips them and prints each command still owed, and `--date YYYY-MM-DD` sets the section's date (default today, UTC). If a lock fails part-way, the version is already written and its fragments are gone, so do not run the step again: the error lists every command still to run, in order.
- `node scripts/check-versions.mjs --write` sets the Version row of `docs/language-parity.md`; check its Distribution row by hand.
- Verify what the registry or tag actually serves. Never retry a successful publication because a response looked stale.

## npm (Changesets)

1. On every push to `main`, `release.yml` opens or refreshes the route-specific version PR (`chore: release packages` on `changeset-release/npm-main` for stable releases, and `chore: release prerelease packages` on `changeset-release/npm-prerelease` for preview releases), through `scripts/release-version-pr.mjs` and `scripts/release-control.mjs version --route <route>`, which also updates the parity docs and commits `.release/npm-intent.json`. `pnpm release:select` shows the selection locally. It never selects the three track stubs (their units have no route) and leaves their fragments in `.changeset/` for the track's own step, although `pnpm changeset status` lists `afd-python`, `lushly-botcore` and `afd-spec` among the packages to bump.
2. **Release failures on `main` are silent.** Nothing alerts on a red `release.yml`; read `gh run list --workflow Release --branch main` before assuming a version PR or a publish happened. A run that is red only at "Update npm-main release PR" or "Update npm-prerelease release PR" has already published whatever it was going to: both run after the publish and the claim, and concern only the version PRs, so it needs no recovery.
3. Review the version PR: the intent, all nine manifests, internal peer ranges, `peerDependenciesMeta` and `pnpm changeset status --verbose`. Exercise optional peers absent and present, especially auth commands and view-state with and without local-db.
4. **The version PR's checks.** `release.yml` opens and refreshes it with the release App's token, so every refresh starts its CI. If a run warns "No release App token" and the PR's head changed, `GITHUB_TOKEN` pushed it and its checks need starting by hand: close and reopen it. Every check must pass before merge.
5. **Maintainer** enqueues the reviewed head once `ci-ok` passes on it, with `enqueuePullRequest` and that head as `expectedHeadOid` (`prepare-pr` step 9), never auto-merge, which lands whatever later refresh is there, reviewed or not. Each merge to `main` while a release is selected refreshes the version PR, and each refresh the App pushes starts its checks on the new head, so `main` keeps moving and nobody holds it still: re-read the intent if it changed, and enqueue the new head when it is green. Once it is queued its branch is locked (`prepare-pr` step 9), so a refresh cannot replace the reviewed head. The merge queue merges it (`release.yml` makes the commit of a version PR it opened as that pull request's author, `github-actions[bot]` today and the release App's bot once the App opens one, because the queue lands that commit as it is, so its author is who `main` credits; it never commits as a person, so a version PR someone opened by hand fails its route update step's author check: close it and let the next push open one. A version PR the App opened has not been through the queue yet, #1624); `release.yml` then runs `pnpm check:all`, publishes the approved plan with provenance and pushes the tags. [Platform release controls](../../../docs/operations/platform-releases.md) explains intent, claims and holds.
6. Verify all nine versions at `https://registry.npmjs.org/<name>` rather than a cached `npm view` (listing all nine can take minutes), each tag's target, and a fresh consumer install.

**The preview route** (`npm-prerelease`) maintains its own version PR (`changeset-release/npm-prerelease`) independently from `npm-main` (`changeset-release/npm-main`), so queued preview fragments never block or overwrite a stable version PR. Its fragments version from the seed, so `2.2.0-preview` becomes `2.2.0-preview.0`, then `.1`; npm sets up a trusted publisher only for a package that exists, so a new name starts with a `0.0.0-bootstrap.0` placeholder the maintainer publishes, which holds `latest` for as long as the unit is a preview. `pnpm version-packages` records Changesets' edits to imported Specimen and FAST-AF files in their provenance before writing the intent; never re-record them on the version PR afterwards, which stales the intent and holds publication. A preview never becomes `latest`: `pnpm release:plan` refuses a prerelease while any of its names lacks `latest` or has it on a prerelease other than a `0.0.0-*` placeholder or on a version that is not valid semver, and the fix is the maintainer's `npm dist-tag add`, never an agent's ([the one-time retag](../../../docs/operations/platform-releases.md#npm-workflow)). For other provenance edits, run `node scripts/release/provenance.mjs <family> "<reason>"`. [Platform release controls](../../../docs/operations/platform-releases.md#npm-workflow) explains the seed and the route.

Keep `workspace:^` on internal peer dependencies and `onlyUpdatePeerDependentsWhenOutOfRange` in `.changeset/config.json`: without both, every bump rewrites the internal peer ranges. Changesets 3 bumps a dependent that leaves its peer range by patch and narrows the range (Changesets 2 made it major), so `pnpm version-packages` refuses a changed peer range without a major of that package; add a `major` fragment for it or widen the range.

**When an npm publish fails,** read the exact failed run and error before changing anything. Trusted publishing is the only upload path: npm 11.5.1 or later, Node 22.14.0 or later, a GitHub-hosted runner, `id-token: write`, and npm's publisher entry as [recorded](../../../docs/operations/stabilization-release.md#npm-publication-outcome). Never add an npm token as a fallback. A failed or uncertain upload stays held until the reviewed recovery under "Holds and recovery" in platform release controls.

A native tag publishes only a commit on `main`, and a release tag cannot be moved or deleted once pushed: a tag on the wrong commit uses up its version, so release the next one. Each publish job, a GitHub Release's rerun included, waits for the maintainer to approve its environment's deployment; approve it only after `git fetch origin main` and `git merge-base --is-ancestor <sha> origin/main` succeed for the commit SHA the waiting run shows, since the guard runs from the tagged commit ([platform release controls](../../../docs/operations/platform-releases.md#native-routes)).

## Python (PyPI)

1. On a branch from `main`, run `pnpm version-track python`. The fragments that name `afd-python` give the bump (`minor` for a capability or, before 1.0, a breaking change; `patch` for a fix); with none it refuses, because there is nothing to release. In one step it sets the version in `python/package.json`, `pyproject.toml` and `__version__`, writes the dated section with its contract line, moves the compare links at the bottom of `python/CHANGELOG.md`, deletes the fragments it consumed, runs `uv lock` in `python/` and in each project that locks it as an editable source (alfred, Botcore and its Factory plugin, Health and the todo backend today; their workflows fail on a stale lock), records the Botcore lockfile it rewrote in Botcore's provenance (only files that provenance already lists), and updates `docs/language-parity.md`.
2. Read the new section in `python/CHANGELOG.md` and edit it where the release needs more than its entries: migration notes under the breaking changes, entries that say the same thing merged.
3. Commit `chore(python): release afd X.Y.Z`; merge after `python.yml` passes. Run the gate as CI does (`uv sync --frozen --all-extras`): a stale local `.venv` on another interpreter fails test collection with misleading import errors.
4. **Maintainer** tags the merge commit and pushes the tag: `git tag -a python-vX.Y.Z <merge-sha> -m "afd Python X.Y.Z; AFD contract <spec/VERSION>"`. `publish-python.yml` checks the tag against admission and `pyproject.toml`, runs `python.yml` and uploads once the maintainer approves the `pypi` deployment. A GitHub Release on the tag (`--latest=false`) reruns it, skipping existing files.
5. Verify: download the published wheel, match its SHA-256 to PyPI's, and install base, client, server and CLI in fresh environments on Python 3.11 to 3.14.

## Rust (crates.io)

1. Set the version in `packages/rust/Cargo.toml`.
2. In `packages/rust`, run `cargo publish --dry-run --locked` and the `rust.yml` steps. docs.rs builds each version once, so a failure there costs a patch release, as 0.2.0's did; `rust.yml`'s `docs-rs` job mirrors it in CI, and `pnpm verify` skips it. Reproduce it with `RUSTDOCFLAGS='--cfg docsrs' cargo +nightly doc --all-features --no-deps`: the cfg goes to rustdoc only, since as `RUSTFLAGS` it reaches dependencies whose docsrs paths don't build.
3. Commit `chore(rust): release afd X.Y.Z`; merge after `rust.yml` passes.
4. **Maintainer** tags the merge commit `rust-vX.Y.Z` (annotated, as above) and pushes it. `publish-rust.yml` checks the tag against admission and `Cargo.toml`, runs `rust.yml` with its `docs-rs` job, skips a version crates.io already has, and publishes with a short-lived trusted-publishing token once the maintainer approves the `crates-io` deployment. Create no long-lived token.
5. Verify <https://crates.io/crates/afd>, `"doc_status":true` at `https://docs.rs/crate/afd/<version>/status.json` (failed builds are listed at `/crate/afd/<version>/builds`), the downloaded crate's checksum, and fresh consumers with default and no default features.

A new crate's first version is a one-time manual upload, because crates.io offers trusted publishing only for existing crates; [native-first-releases.md](../../../docs/operations/native-first-releases.md) records 0.1.0's bootstrap.

## C++ (tag only)

1. Set `project(afd VERSION X.Y.Z)`; it generates `afd/version.hpp`. The package uses `SameMinorVersion` compatibility, so a minor bump also updates `find_package(afd X.Y CONFIG REQUIRED)` in `packages/cpp/tests/consumer/CMakeLists.txt`. Only the daily or dispatched `cpp.yml` runs the package jobs that catch a miss, as #454 found.
2. Merge after `cpp.yml` and `conformance.yml` pass. Tag only after a daily or `workflow_dispatch` run of the full `cpp.yml` matrix (sanitizer, macOS, MSVC, Emscripten, package and fuzz legs) passes at the merge commit, or at a later `main` with the same C++ inputs.
3. **Maintainer** tags the merge commit `cpp-vX.Y.Z` (annotated), pushes it, and creates the GitHub Release from the changelog section with `gh release create cpp-vX.Y.Z --verify-tag --latest=false`, so the npm release keeps "Latest".
4. Verify fresh consumers built from the public tag through `FetchContent` (`GIT_TAG cpp-vX.Y.Z`) and an installed `find_package`, checking the header, library and contract versions.

## Botcore (PyPI)

The first AFD release, 0.6.0, waits for the owner steps in the [handoff record](../../../docs/features/complete/platform-monorepo/botcore-handoff.md): `lushly-dev/botcore` loses its PyPI publisher before AFD's is added, so two repositories never publish at once.

1. On a branch from `main`, run `pnpm version-track botcore`. The fragments that name `lushly-botcore` give the bump, as for Python. It sets the version in `endpoints/botcore/package.json`, `pyproject.toml` and `__version__`, writes the dated section in `endpoints/botcore/CHANGELOG.md`, deletes the fragments it consumed, runs `uv lock` in `endpoints/botcore` and in each project that locks it as an editable source (alfred, Health and the Factory plugin today), and then records every imported file it rewrote that Botcore's provenance already lists (the changelog, the stub, `pyproject.toml`, `__init__.py`, `uv.lock`) in both provenance copies with `scripts/record_provenance.py --refresh`.
2. Read the new section and give it its introduction where the fragments carry none: one paragraph on what the release is for. The provenance test and `package_smoke.py` fail on an imported file changed after step 1, so record that edit: `uv run --directory endpoints/botcore --no-project python scripts/record_provenance.py --refresh --reason "<what changed>" CHANGELOG.md`.
3. Commit `chore(botcore): release lushly-botcore X.Y.Z`; merge after `botcore.yml` passes.
4. **Maintainer** tags the merge commit `botcore-vX.Y.Z` (annotated) and pushes it. `publish-botcore.yml` checks the tag against admission and `pyproject.toml`, runs `botcore.yml`, builds, inspects the `lushly_botcore-X.Y.Z` wheel and sdist into a receipt, and uploads after re-verifying it, once the maintainer approves the `pypi-botcore` deployment. A GitHub Release on the tag (`--latest=false`) reruns it, skipping existing files.
5. Verify <https://pypi.org/pypi/lushly-botcore/json>: the version, the uploaded files' SHA-256 against the receipt, and a fresh install on Python 3.11 and 3.12 that imports `botcore` and reports the version.
