# Gates

What each gate covers, the traps between them, and the rules for changing them.

The sources of truth are `lefthook.yml` (the hooks and `pnpm check`), `.github/workflows/` (each workflow's `paths` and jobs) and `scripts/affected/` (the scope and the local suites). `pnpm verify --list` prints the plan for a change, so this page lists no workflow's steps; it holds what those files do not say on their face.

## What runs where

- **Pre-commit** fixes the staged files with Biome and typechecks the packages that own them, with their dependents. **Commit-msg** runs commitlint; `commitlint.config.js` has the types and scopes.
- **Pre-push** runs the full lint, the affected packages' tests and typecheck, and the repository-wide checks. It neither installs nor builds, and packages import each other's `dist`, so it fails on stale output: run `pnpm install` after pulling `main`, and `pnpm build` (or `pnpm check`) after changing a package another one imports. A push that only updates the factory lane's refs (`refs/factory/queue/*`, `refs/factory/hosts/*`) runs nothing: a queue ref hands a branch to the lane, which validates it.
- **`pnpm check`** is pre-push plus the affected build and coverage, and is exactly what `ci.yml` runs: if it passes locally, that workflow passes remotely. On pull requests `ci.yml` runs only the `.nvmrc` Node.
- **`pnpm check` is TypeScript only.** It does not touch Python, Rust, C++, Alfred, Botcore, Health or Umbel. For Specimen, FAST-AF, Violet, Loam and the Health dashboard it builds the packages and runs only their browser-free, store-free units.
- **`pnpm verify`** runs `pnpm check`, then, for each workflow whose `pull_request.paths` match the change, the steps `scripts/affected/suites.generated.mjs` (generated from `.github/workflows/*.yml` by `pnpm ci:sync`) lists for it. A suite's `remote` line names what only the workflow covers: other operating systems, Node and Python versions, Firefox and WebKit, sanitizers.
- **The release-tooling suites** run inside the tooling tests only when one of `RELEASE_INPUTS` changes (`scripts/run-tooling-tests.mjs`: `scripts/`, the workflows, `.changeset/`, `.release/`, `.nvmrc`, the root manifest, the lockfile).

## Scope

`scripts/affected.mjs` diffs against the merge base with `origin/main` (`AFD_BASE` in CI) and selects the packages that own changed files, their dependents and, for `pnpm-lock.yaml`, the importers whose resolved dependencies changed. A build adds the scope's dependencies. `pnpm affected` prints the selection and the reason for each package. Lint and the repository-wide checks always run whole.

- A package's own test file selects that package without its dependents. A family's provenance records select no package.
- The files in `GLOBAL_FILES` (`scripts/affected/scope.mjs`: the root manifests and configs, `ci.yml` and the scope scripts) select the whole workspace. `suites.mjs` does not.
- The workflows' path filters do not exempt documentation: a README under `packages/rust/` triggers Rust, Conformance, Alfred, Umbel, Loam and Loam's plugins. Read `pnpm verify --list --files <paths>` before choosing what to touch.

## Daily-only legs

The slowest legs run only on the daily schedule and on manual runs: C++ under TSan, on macOS and Windows, with packaging, benchmarks, fuzzing and Emscripten; Umbel on macOS, on its MSRV and in its Windows store and clippy job; fast-element on Firefox and WebKit; `ci.yml` over the whole workspace on the older supported Node versions.

A pull request cannot show a break in them, so read the daily results (`gh run list --event schedule`). GitHub can start a scheduled run hours late, so a run missing that morning has not necessarily been skipped.

## Unit notes

Only what a failing gate will not explain.

- **Imported families** (FAST-AF, Violet, Specimen, Botcore, Health) are changed here, never in their source repositories first. An edit to an imported file fails the tooling tests until the family's provenance records it; that includes a file a build rewrites, such as FAST-AF's API reports.
  - Specimen and FAST-AF: `node scripts/release/provenance.mjs <family> "<reason>"`. Specimen's record also covers its feature documents under `docs/features/`, so an edit to its `STATUS.md` needs recording too.
  - Violet: `foundations/violet/provenance/adaptations.json`.
  - Botcore: `endpoints/botcore/scripts/record_provenance.py`. On Windows, normalize edited Botcore files to LF before running `--refresh`: `verify_provenance.py` hashes raw bytes on disk while `.gitattributes` checks out LF, so CRLF digests pass locally and fail Linux CI (#2390).
  - Health: `endpoints/health/provenance/provenance.json` and its pinned digest; any added file needs a row.
  - Botcore, FAST-AF, Specimen and Violet do not commit the sha256 of `adaptations.json` in `provenance.json` (#1610), and their provenance tests refuse a committed one, so two branches that edit different files of one conflict only where their rows neighbour each other. Botcore's build stamps it into the wheel and sdist (`hatch_build.py`); the npm packages of the other three ship no provenance records, so nothing is stamped for them. A merge made by an older `pnpm base:sync` puts the digest back; the recorder removes it: `python scripts/record_provenance.py --refresh` from `endpoints/botcore`, or `node scripts/release/provenance.mjs <fast-af|specimen> "<reason>"` — pass the real reason for the branch's changes, because `provenance.mjs` is the full recorder and on a branch with unrecorded edits in that family it also records them under that reason. Violet has no recorder: delete the line by hand. Health has no `adaptations.json`: its test pins the digest of its whole `provenance.json`, and the merge below leaves its records alone. `pnpm base:sync` merges records-only conflicts three ways with `scripts/provenance-merge.mjs`, as the factory lane does, and refuses a value both sides changed differently: record that file again by hand. Then run the unit's provenance test.
  - A `package.json` change to dependency ranges alone, as Dependabot makes, is not an adaptation in the three npm families (Specimen, FAST-AF, Violet): their records also hold the manifest's digest with its ranges blanked.
- **FAST-AF:** do not run the upstream `check:v3` scopes or sync from lushly-dev/fast-af, which is frozen. Microsoft FAST releases of `fast-element` come in as a three-way merge from the last release taken, never as copied files: the [FAST-AF README](../../../../foundations/fast-af/README.md#microsoft-fast) has the steps. `@lushly-dev/violet-elements` is its own integration unit (`#1783`), outside per-file FAST-AF provenance and covered by `scripts/check-file-size.mjs` and the bloat sweep; only `fast-element`, FAST-AF root files and `tests/consumers/fast-af/` require FAST-AF provenance records.
- **Violet** lints with its own Biome configuration (`foundations/violet/biome.json`). The root Biome config skips its directories, so `pnpm lint` says nothing about them.
- **Health:** its source repository is private. Never import private Health inventories, reports, history or configuration.
- **Health dashboard:** its committed fixtures must equal the Health CLI's output, so a schema or CLI change in `endpoints/health/` that breaks one fails `fixtures:check` and the browser suite.
- **Umbel:** `Cargo.lock` is committed (the `.gitignore` negates it), so update it with the dependencies. Umbel depends on `packages/rust` by path, so a change there can break it. No `.wasm` file is committed; the suites build the components. Integration tests live in one `tests/it/main.rs` per crate (plus `tests/it_logs/main.rs` in `umbel`) and plugin binaries live outside the plugin library crates (`first-party/`, `bins/todo/`) to keep target directories bounded (#1774).
- **Loam:**
  - A change to the kernel's `SESSION_50` needs `pnpm -F @lushly-dev/loam-chrome session:record`, which regenerates the chrome's committed journal fixture.
  - An added, removed or retyped theme id needs `pnpm -F @lushly-dev/loam-theme theme:check --write`, which regenerates `contract/tokens.json`.
  - `test:mounted` builds a stock `umbel`; `LOAM_UMBEL_TARGET_DIR` gives that build a target directory of its own.
- **Hosted fixtures:** `pnpm test:hosted:local` needs no credentials and is not evidence about a hosted provider. [Hosted verification](../../../../docs/operations/hosted-verification.md) covers that.

## Changing CI, the scope scripts or a test's inputs

- **Watch it fail.** A new or edited check, hook or gate script is not done until it has been seen red: plant the exact violation it exists to catch in a real file, run it and confirm the output names that violation, remove the plant (restore from a copy, not `git restore`), and see it green. Say in the pull request what you planted and what it printed. A gate also ships with a test that feeds it a violating fixture. The `maintain-gates` skill has the rest: properties over shapes, exemptions that expire, tolerances that reach what they exempt.
- **Skipped and unrun tests are registered.** `.only` fails `pnpm check`; an unconditional `.skip`, `.todo` or Playwright `.fixme` in a JavaScript or TypeScript test needs an entry (owner, reason, issue) in `scripts/policy/test-quarantine.json`, and fails once its test recovers. A skip that depends on the environment is written as `skipIf`, `runIf` or Playwright's `test.skip(condition, reason)` instead. Every tracked JS/TS, Python, C++ and Rust test file must be claimed by an active test runner (or registered in `scripts/policy/test-discovery.json` with owner, reason and issue, failing once it is deleted or wired in), and every active runner must claim at least one test file (`check-test-discovery.mjs`).
- A new pull-request workflow needs an entry in `scripts/ci/workflow-graph.mjs` and `scripts/sync-ci.mjs` (`pnpm ci:sync` updates workflow `paths:` blocks and regenerates `scripts/affected/suites.generated.mjs`), or `pnpm check:ci` and the tooling tests fail. `ci.yml` and `ci-ok.yml` are the exceptions.
- Reusable CI blocks: Node + pnpm setup uses `.github/actions/setup-node-pnpm`; path-filtered workflows call `.github/workflows/queue.yml` as their `queue` job. Every non-reusable job declares `timeout-minutes`, and `scheduled-failure-issue.yml` tracks failures and recoveries for every workflow with a `schedule:` trigger.
- `ci-ok` (`ci-ok.yml`, `scripts/ci-verdict.mjs`, `scripts/commit-credit.mjs`) is one verdict per pull request: it waits for every workflow the head commit started and passes when each passed or was skipped. It finishes last. Re-running a failed workflow does not re-run it, so re-run `ci-ok` afterwards. `main` requires it, from GitHub Actions only. On a pull request it also reads how `main`'s queue merges (`queueMergeMethod`); once that is a rebase, which lands each of the branch's own commits on `main` as it is and drops its merges, it checks those commits as `main`'s are checked and refuses more than one (`pnpm branch:squash`, the skill's step 6; #1809). Its two scripts run from the commit the change is built on, never from the change under test, so an edit to either takes effect once it lands. The change's own run drives the base's scripts with its own `ci-ok.yml`: land a new argument or variable in the scripts first, as optional, and use it in a later change; make the scripts stop needing one before `ci-ok.yml` stops passing it; never move or rename them in one step. A pull request opened with `GITHUB_TOKEN` starts no workflows, so it gets no `ci-ok`: the Release workflow opens Changesets' release pull request with the release App's token for that reason, and warns when it cannot (then close and reopen the pull request to start its checks).
- **On a merge group** (`merge_group`, the commit the merge queue builds for each queued pull request; `main` requires the queue, and step 9 enqueues) `ci-ok` is asked for again, and it has to mean the same thing there.
  - No `paths` filter applies to a merge group, so every workflow that runs on pull requests has the trigger and starts for every queued pull request. A path-filtered one opens with the `queue` job (`Merge queue paths`), which runs `node scripts/affected.mjs trigger <its file>`: the files the group adds to its base (`merge_group.base_sha`) against the workflow's own `pull_request.paths`. Every other job needs it, so a group outside the paths costs that one short job. On every other event the job passes straight through; it is never skipped, because a skipped job skips whatever needs it.
  - `ci-ok` checks credit on the commits the group holds that `main` does not (`commit-credit.mjs --merge-group`): its own commit and those queued ahead of it, as they will land. The queue rebases, so each is a pull request's own commit as the branch made it, and any `Co-authored-by` line fails the group, except one naming the commit's own author by the same address, which credits nobody else. A failure's fix is chosen by how the queue merges (`queueMergeMethod`), so it stays right if the method changes again. It then waits for a `merge_group` run of every workflow that has the trigger and fails if one has not started within 15 minutes: a pull request has no such list, since its path filters decide what runs.
  - `scripts/merge-group-contract.test.mjs` holds the rules. A new pull-request workflow needs `merge_group:` and, with `paths`, the `queue` job copied from another workflow with its own file name. A job that needs `queue` opens its `if` with `needs.queue.outputs.run == 'true'`; a job behind such a job uses no status function (`always()`, `!cancelled()`), which would run it for every group. Past the gate nothing names the `merge_group` event, a job that can run only for a pull request is listed in `PULL_REQUEST_ONLY` with its reason, and `paths` keep to `*`, `**` and a leading `!`, the syntax the `queue` job reads. Every `Swatinem/rust-cache` step carries `save-if: ${{ github.ref == 'refs/heads/main' }}` under its `with:`, the one ref read the contract allows (`SAVE_IF`): pull requests and merge groups restore `main`'s Rust caches and save none of their own, which only they could restore and which push `main`'s past the 10 GB cache limit (#1683). `node scripts/merge-group-contract.mjs` names what is wrong.
- A package test that reads a file outside its package, another package's test files included, must be declared in `EXTRA_INPUTS` (`scripts/affected/scope.mjs`). Without it, a change to that file skips the test.
- The FAST-AF, Violet, Specimen, Health dashboard, Loam, Umbel and Conformance workflows open, after `queue`, with an `Affected units` job (`node scripts/affected.mjs gate`), so a lockfile or shared-input change runs their jobs only when it reaches them. A gate must name every package whose suites its jobs run.
- Pin an action to a full commit SHA with a `# vX.Y.Z` comment. Dependabot updates them.
- Give a pull-request workflow the concurrency group the others use, so a newer push cancels the run it supersedes.
- AGENTS.md lists no workflows or per-unit suites, so a new one needs no line there. Add a unit note here only for something a failing gate will not explain.

## Dependencies and the lockfile

- Dependabot's version updates (`.github/dependabot.yml`) cover the root npm workspace, the GitHub Actions pins and AFD's own Python and Rust roots, one entry per root; a new lockfile in AFD's own code gets its own entry. They leave out Botcore's, Health's and Specimen's lockfiles, which change here only with a provenance record of why; those stay in the dependency graph, so Dependabot's security alerts cover the dependencies it reads from them. Loam desktop's exact pins (Tauri, `reqwest`, `windows-sys`) move only by hand.
- `pnpm-workspace.yaml` sets a three-day `minimumReleaseAge`, matching Dependabot's, because a lockfile holding a younger version fails every Dependabot npm update. A newly published dependency waits until it is three days old unless `minimumReleaseAgeExclude` lists it.
- pnpm 12 fails `pnpm install` with `ERR_PNPM_IGNORED_BUILDS` when a dependency's install script is undecided, so a new or updated dependency that ships one, a Dependabot update included, needs an `allowBuilds` entry in `pnpm-workspace.yaml`; deny it unless something needs its script. Overrides live there too: pnpm 12 does not read the `pnpm` field of `package.json`. With `minimumReleaseAge` set, `pnpm add` of a younger version stops at a prompt, and fails without a terminal, rather than adding it to `minimumReleaseAgeExclude`.
- Dependencies can ship agent skills, which `pnpm approve` would link into `.claude/skills`. Leave them unapproved; the repository's skills are written here.
- Pull requests that change `pnpm-lock.yaml` go through the merge queue like any other. Two lockfile changes that each pass alone can merge without a conflict and still leave a lockfile `pnpm install --frozen-lockfile` refuses (#937). The queue builds each on top of those ahead of it and `ci.yml` runs that install there, so the second should fail in the queue instead of on `main`; no session has seen that happen yet. Then wait until the one ahead has landed, merge `main` (`pnpm base:sync`), run `pnpm install` to settle the lockfile, confirm `pnpm install --frozen-lockfile` passes, commit and push it, and take the new head through step 8 before enqueueing again. On a Dependabot pull request ask for `@dependabot rebase` and verify its new head the same way.

## Rust builds and disk

Every worktree adds its own copy of the workspace crates and test binaries to a shared `CARGO_TARGET_DIR`, and Cargo never removes one: a shared directory reached 162 GB in a week. The repository's `.cargo/config.toml` therefore turns off incremental compilation and dependency debug info, and builds on a shared machine run with `CARGO_BUILD_JOBS=4`.

`pnpm rust:sweep` evicts builds that nothing has read for three days and wipes a target directory still over 60 GB (`--dry-run`, `--days`, `--max-gb`). `pnpm verify` runs it before its Rust suites. Never run it while cargo is running.
