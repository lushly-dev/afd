# Platform release controls

The [platform migration](../features/active/platform-monorepo/) separates source admission from publishing. `scripts/release/inventory.json` records exact units, distribution identities, source paths, protocols, authority, routes, states, and required gates. The current nine AFD npm packages remain one coordinated unit. Registry scope alone does not make a package part of that unit.

## Importing source safely

An imported or split distribution starts quarantined. An unknown public manifest discovered in current or future roots is also quarantined. Declare its family, installation contract, export coverage, protocol, original publisher, and cutover requirements before release selection. A source move does not enable a publisher or grant registry rights. Preserve the old source authority until its recorded transfer.

Foundation dependencies must remain inside their family or third-party dependencies; separately installed integrations and endpoints compose families. Boundary checks inspect declared installation graphs and supported static source/configuration references. Clean artifact consumers remain required to establish actual runtime/type independence. A graph check alone is not complete consumer evidence.

## npm workflow

1. Add npm semver release intent using `pnpm changeset`. Botcore category fragments must never share npm fragment storage. Malformed/foreign formats fail before the approved wrapper runs.
2. `pnpm release:select` inspects complete eligible units and prerequisite evidence. A held family retains its fragments. Explicit multi-unit fragments must be selected as a whole or revised through review.
3. The main-branch workflow uses `pnpm version-packages` to run Changesets 2.31.1 in a disposable Git worktree with only selected workspace units and fragments. It validates the write set before copying selected manifests/changelogs and consumed-fragment deletions back. It updates parity documentation and `.release/npm-intent.json`.
4. Review the version PR and its committed intent. That record binds selected units, resulting versions/manifests, and package source content. A changed pending candidate holds publication. Missing intent never authorizes a version merely because it is absent from npm.
5. After the reviewed version PR merges and required gates pass, `intent-status` distinguishes missing, fulfilled, and pending intent. Fulfilled intent is an inert record, even if later development changed source. Pending intent must remain current.
6. `pnpm release:plan --plan <temporary-path>` packs only the approved selection and validates actual portable manifests, dependency ranges, identities, and hashes. This step performs no upload. Build first with the required gate.
7. Authorized automation calls `pnpm publish:npm --plan <temporary-path> --receipt <temporary-receipt>`. It revalidates the plan and each upload, publishes explicit tarballs in dependency order, and records outcomes. The receipt finalizer compares npm integrity with each approved archive, verifies candidate tags, then pushes explicit tags and creates GitHub Releases.

Specimen's unit carries four prebuilt native hosts, one npm package per platform, released at the core's version. When the approved intent selects `specimen`, `release.yml` builds each host on its own platform (Linux on glibc 2.35), with no build cache and read-only permissions, before the publishing job runs. That job stages each one into its package after the quality gate and before step 6, through `foundations/specimen/host/stage.mjs`, which reads the binary's header and refuses one built for another system or architecture. Each package's `prepack` checks it again, so a plan cannot pack a platform package without its host, and a failed host build stops the publishing job.

A unit on the `npm-prerelease` route names its npm tag in the inventory (`distTag`, never `latest`), and only such a unit names one. Specimen's four units and `fast-element` use it with `preview`. Its manifests start at a seed, `x.y.z-<tag>`: `pnpm version-packages` runs Changesets' prerelease mode for that run only, so the seed becomes `x.y.z-<tag>.0` and each later release counts on from the version itself (`.1`, `.2`), with no `pre.json` kept between runs; it then deletes the fragments it applied, which prerelease mode moves to `.changeset/pre`. Committed prerelease state of any kind (`pre.json`, `.changeset/pre`) is refused. Start a preview from a seed, with the dependents' peer ranges on it (`^x.y.z-<tag>`): from a stable `2.2.0`, a `minor` would give `2.3.0-preview.0`, which leaves a dependent's `^2.2.0`. Changesets 3 then bumps the dependent by patch and narrows its peer range, a breaking change for its consumers, so `pnpm version-packages` refuses any run that changes a selected package's peer range without a major of that package: add a `major` fragment for the dependent or widen its peer range. Planning takes the route and tag from the intent's units, publishes only `x.y.z-<tag>.N` versions under that tag, and refuses `latest` or a seed; the main route refuses any prerelease version. One release is in flight at a time, so units on different routes or tags never share one: the workflow tries `npm-prerelease` first, then `npm-main`, and the other waits: a preview takes over an open main-route release PR, which returns once the preview publishes, so a stream of preview fragments would hold the main route back. Because Changesets edits imported Specimen and FAST-AF files, `pnpm version-packages` records them in each family's provenance (`scripts/release/provenance.mjs`) before writing the intent, which binds those records too. Leaving the preview means moving the unit to `npm-main` with no `distTag`, after which a `patch` releases `x.y.z`.

The npm workflow checks pending version intent independently from held fragments. Before any upload it creates a durable GitHub commit-status claim for the exact intent digest. A pending or failed claim holds later runs, including runs where every version reached npm but tag/release finalization did not finish. Success is recorded only after artifact integrity and finalization verification. Restoring identical intent bytes must preserve their existing claim. Runner receipts, plans and tarballs are retained as additional evidence; they are not the durable claim store.

GitHub refuses a `GITHUB_TOKEN` push of a tag whose commit has different workflow files from main, which a workflow change merged during the release causes. So the tag push uses a GitHub App token when one is configured: the repository variable `RELEASE_TAG_APP_CLIENT_ID` and the secret `RELEASE_TAG_APP_PRIVATE_KEY`, for an App installed only on this repository with `Contents` and `Workflows` write. The token is created after the upload (after the quality gate in recovery), and reaches only that step's git. It is not an npm credential; uploads stay on trusted publishing. Without the App, or if its token cannot be created, the push falls back to `GITHUB_TOKEN`, and a refused push holds the release for recovery with the tags pushed by hand first.

Changesets' own version/publish branch decision is not a publication-admission mechanism. Never use raw `changeset publish` on the complete workspace. Direct arbitrary shell execution remains trusted operator execution; these tools do not claim to sandbox an operator.

## Native routes

Existing Python and Rust tag routes remain distinct. Each checks exact admitted unit/route, triggering tag and checked-out source, manifest identity/version, and packaged metadata before authentication/upload. Python validates its complete wheel/sdist set and hashes; Rust validates its packaged Cargo identity and VCS/source data, then rechecks before `cargo publish`. Cargo repackages source during upload, so the local archive receipt is trace evidence rather than proof of the registry's exact bytes.

Botcore's `lushly-botcore` has its own PyPI route, `pypi-botcore`: a `botcore-vX.Y.Z` tag runs `publish-botcore.yml`, which applies the same guard as the Python route (`scripts/release-native.py --unit botcore`), runs `botcore.yml`, and publishes from the `pypi-botcore` environment. Its wheel and sdist file names and the sdist root use the normalized stem `lushly_botcore`; the metadata keeps `Name: lushly-botcore`. The route is a publisher handoff from `lushly-dev/botcore`, recorded in [botcore-handoff.md](../features/active/platform-monorepo/botcore-handoff.md); the other five Botcore distributions stay quarantined with no route.

C++ remains a source distribution. Immutable tags, `packages/cpp`, `afd::afd`, FetchContent, installed find_package, and vendoring contracts remain intact. Any relocation needs the migration's explicit compatibility decision and external consumer evidence.

## Holds and recovery

A failed or uncertain publication requires receipt and registry reconciliation before retry. Never overwrite versions, infer absence from a stale cached response, automatically fall back to a second publisher, or label a partial family as fully released. Tag/release finalization failures also hold their receipts; repair the missing step only after matching registry bytes and source identity.

An accepted npm upload can precede registry metadata visibility. Upload and finalization readback verify canonical registry tarball bytes against the approved SHA-256 and size, independently of delayed version metadata. Missing blobs retry within a ten-minute deadline; each request has a ten-second timeout. A mismatch or network failure holds the release; uploads are never retried automatically.

For a held upload whose acceptance can be verified, review and commit `.release/npm-recovery.json` with the original run/attempt, source revision, plan binding, intent digest and exact failed status ID. After that change passes review and CI, dispatch `release.yml` on `main` with the SHA-256 of those approval bytes as `recovery_approval`. The recovery job runs the quality gate, downloads the retained original evidence, restores the sealed artifact paths, and checks the frozen source in a separate worktree. It verifies the uncertain upload before appending an owned recovery claim linked to the original failed status. Original failure history is preserved.

Recovery adopts verified existing versions even if a later registry listing regresses, uploads only the remaining artifacts once, and requires the complete planned package/tag/release set before success. The original plan is neither repacked nor resealed. If a recovery itself is held, the next reviewed approval also pins `failure.runId`, `failure.attempt`, `failure.sourceRevision` and the new failed status ID. Both the original artifact bundle and latest failed recovery bundle are checked and retained; the latest held receipt supplies the uncertain upload to reconcile. Missing retention evidence, an absent uncertain upload, changed source/intent, conflicting tags/releases or unknown registry state require further reconciliation. A failed recovery remains held; the previous approval cannot acquire or replace an active/successful claim. A completed upload receipt with held finalization can authorize finalization-only recovery after its exact package/tag/notes set and every registry blob are verified. This mode adopts existing artifacts with uploads disabled. Tag pushes use the already validated and built checkout sharing the frozen source's Git common directory and publisher origins. All missing explicit tag refs are pushed together with hooks enabled, then every remote target is read back before GitHub Releases are created. Receipts separately record the hook checkout HEAD and frozen tag target.

Planning also refuses a tarball that lacks a `files` entry or a file its manifest points to (`main`, `types`, `bin`, `exports`), since packing copies built output git ignores: a release whose build did not run would pack only a manifest and a readme. `release.yml` sets `LEFTHOOK=0` so Changesets' push skips the git hooks; the quality gate drops it from its own environment, because `lefthook run check` under `LEFTHOOK=0` runs nothing and exits 0.

Trusted publishing uploads only to a package npm already has, with its publisher linked, so `pnpm release:plan` refuses a planned package npm does not have, and the run stops before it claims the intent. Set up a new name's publisher first, through a deprecated placeholder. An upload npm refused outright, with no version of the release on the registry, is not an uncertain upload, and recovery cannot adopt it; after reconciling the registry, a new reviewed intent over the same versions replaces the held one, and the held claim stays as the failure record.

Before any publisher transfer, record old/new authority, queued/in-flight release handling, frozen candidate/artifact identity, registry settings, and restoration steps. Simulated authentication failure tests the decision process only. Actual credentials, first upload, registry readback, and isolated installations remain separate Phase 5 evidence.

## Scoped development

Use existing language-native commands and pnpm filters for the selected area. For example, `pnpm -F @lushly-dev/afd-core test` works without browser/native environments; `uv` commands in `python/` or `alfred/` use their own locked environments. Full `pnpm check` and path-specific native/conformance workflows remain mandatory where applicable. Shared skills remain authored in the current canonical source until Botcore source/asset ownership is reconciled in Phase 2.
