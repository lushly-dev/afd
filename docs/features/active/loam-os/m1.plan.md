Epic: [#2595](https://github.com/lushly-dev/afd/issues/2595). Progress is in [STATUS.md](STATUS.md).

inputs, results and refusals are the proposal's [Commands (draft)](loam-os.proposal.md#commands-draft),

this plan says why.

## What M1 must show (the proposal's exit)

1. Every `m1` scenario (01 to 11, 14 to 18) passes against the fake runtime, and 01, 03, 04, 08 and
   16 against a real one.
2. Tests cover crash recovery at the pre-effect journal boundary (no machine or run starts without a
   persisted intent) and the lane's external verify-record check, including rejection when the
   host's observed `state`, `head`, `tree` or `base` disagrees with the output or the slot.
3. In one fleet run every validation ran in a machine. A planted branch whose tests try to read the
   lane's token, the `gh` sign-in and a file outside the workspace, and to reach a host outside every
   policy, gets none of them, and its own pre-push hook does not run on the lane host.
4. A cell given a planted branch that fails in the image and passes on the lane host's own system
   repeats the failed run in a machine of its own and destroys it.
5. After the run the host's disk use is back where it started and `host-status` shows nothing
   unlisted. The report gives validation time against the slot's, the journal's growth and how often
   an operator used the runtime's own tools.

## What M0 measured that changes the plan

From the M0 measurements in [STATUS](STATUS.md), on Hero and `random`:

- **Run time.** A cold `pnpm verify --all` on `random` took 7,790 to 12,716 s in Colima's 6-processor
  VM, up to twice Hero's. Every step's `timeoutSeconds`, the host's `steps.maxTimeoutSeconds` and
  the lane's translated `timeout` must allow that, so the configuration's maximum is 6 hours, not
  the fixture's 7,200 s. The lane's poll beat and its hold timeout for `HOST_FULL` and
  `*_UNAVAILABLE` are about holds, not run length, and stay as they are.
- **Egress.** The install step reached three GitHub hosts that the example `registries` policy omits
  (`github.com`, `raw.githubusercontent.com`, `release-assets.githubusercontent.com`). CMake's
  `FetchContent` reaches them, not the clone, which in M1 comes from the host's mirror. Allowing
  `github.com` would let a planted branch send data out within policy, which weakens exit item 3.
  So the image carries those dependencies, and `registries` stays the package registries (step 6).
- **Offline validate.** Verify passed with no network after an online build, with `UV_OFFLINE=1`. A
  cold install followed at once by a validate step under `none` is not measured yet; step 6
  measures it, and validate falls back to `registries` if it fails, as the proposal's
  [Network](loam-os.proposal.md#network) says. The host sets `UV_OFFLINE=1` on every step whose
  policy is `none`, and records it on the run as environment the host added.
- **Disk limits.** The runtime ignored a per-container disk limit, and a container's writable layer
  wrote 1.5 GB under a 1 GB `--storage-opt`. So the host enforces `size.diskGb` itself, counting the
  machine's volumes and its writable layer (step 5). Freed space reaches the host's own disk only
  after `fstrim` in Colima's VM, so the host measures inside the VM, with no trim needed before
  measuring, and `machine-destroy` and `host-prune` trim after they remove. Trimming needs root in
  the VM; the `Runtime` trait gains a disk-usage method with a Colima implementation and a plain
  Docker one.
- **The verify record.** Run 7 passed and wrote no record. A crash-point test in
  `umbel-store-embedded` aborts a child, and with core dumps on in the image that left a `core` file
  in the checkout ([#2898](https://github.com/lushly-dev/afd/issues/2898), open, with a fix under way
  outside these steps). Step 4
  also runs every machine with a core-dump limit of zero, so no branch's crashing test can block
  its own record.
- **Capacity on `random`.** Colima's VM has 16 GB, and a full run peaked at 12.2 GB. The host needs
  `lane.slots` + 1 machines, two for one lane slot, so two full-size machines do not fit at once
  ([For the owner](#for-the-owner), question 3).
- **Checkpoints.** Committing a whole container is far too slow (8 GB in 21 minutes). That is M2's.

## The scenario harness

The scenario runner (`packages/testing/src/runner/`, behind `afd scenario run`) cannot drive the host over MCP as it is. It applies a fixture
through an adapter and has none for these fixtures. One server keeps its state across scenarios.
Every MCP caller is `agent:loopback`, so scenario 11's `test` actor is unreachable. And the
fixtures fake more than a runtime: the clock (`now`), the source's branches and heads, records,
the journal's health and restart state.

So step 2 builds an in-process Rust harness in the unit's tests. It reads the YAML, as Umbel's
ideas plugin does (`endpoints/umbel/plugins/ideas/tests/it/scenarios.rs`), and gives each scenario
a fresh host with fakes for the runtime, the git source, the clock and the records, seeded from the
scenario's fixture merged over its `base` (`host.json`). Umbel's journal is real: only the storage
under step 1's middleware is faked, so it can fail writes on demand and scenario 14 tests the real
`JOURNAL_UNAVAILABLE` path. The test actor is set per call. The fakes live in the unit's test
tree, which means moving M0's public `FakeRuntime` out of `src/`, so the shipped binary has no
fake runtime and one configuration schema. The harness keeps a
table of how far each scenario file runs before it reaches a command or behaviour not yet built. A
step that builds one moves that file's row forward, and the table must end with every `m1` file
complete. It covers the seven fixtures the `m1` scenarios use (`host`, `full`, `restart`,
`journal-down`, `leftovers`, `runtime-down` and `ejected`); `warm` and `warm-red` are M2's.

## What stays as drafted

The command table, the refusal codes and the lane's table of answers in the proposal's
[How the lane uses it](loam-os.proposal.md#how-the-lane-uses-it). The scenarios are the acceptance
tests. A step that has to change one says so in its pull request and updates the scenario with it.
The scenarios' build order is the one the owner approved on 2026-11-25. This plan builds the
commands in a different order, and the harness's table, not the build order, says which scenario
each step completes.

## Decided here

- **A cell's calls.** The proposal leaves it to M1's specification whether a cell reaches the host
  through the factory's own command host (`factory-cell`) or the host's command line
  ([How the lane uses it](loam-os.proposal.md#how-the-lane-uses-it)). In M1 a cell uses the host's
  command line, with its limits in the cell brief (step 12). `factory-cell` can wrap it later.
  Neither route enforces anything until M3's sign-in, so wrapping it now adds a layer and no safety.

## For the owner

1. **The runtime without the `http` grant (steps 3 to 11).** The proposal leaves a plugin that talks
   to the container runtime without Umbel's reserved `http` grant as the owner's call for M1. M0's
   `host-status` already does this through `CliRuntime`, read-only. From step 3, callers' values
   reach the runtime too: `steps[].args`, `env` and output paths, as arguments with no shell. The
   operator's configuration owns everything else: the image, the size, the policy, the mounts and
   the user. Recommended: allow it, recorded as an Umbel decision. Compiled plugins are trusted code
   (D42, D205), the commands declare D42's `external` effect so the doctor shows it, and an `http`
   grant would describe a network call that is not what happens.
2. **Timing failures in a machine (step 11).** STATUS's follow-ups leave to M1 how much of the host a
   lane machine gets, and whether a step that fails on a time limit is run once more before the
   branch is ejected. A repeat changes the factory's flake rule, which is the owner's. Recommended:
   no automatic repeat. A failure that does not happen in the machine either is already a flake by
   the factory's rule, and repeating would hide the load problem the M0 runs found.
3. **Capacity on `random` (step 13).** A lane slot and a cell's own run need two machines, and two
   full-size machines (12.2 GB each at peak) do not fit in the VM's 16 GB. Options: give the VM
   20 GB of the Mac's 24 GB, which squeezes the other lanes; keep `lane.slots = 1`, so a cell's
   machine waits while the lane validates; or a smaller cell size that runs one suite, not
   `verify --all`. Recommended: the third. A cell repeats one failed step, not the whole run.
