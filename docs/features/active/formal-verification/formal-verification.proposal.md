# Formal verification and stateful property checking in AFD

**Pilot.** When branches post competing live claims, agents need to know which branch holds the issue. The owner approved reporting the earliest still-standing live claimant. The factory scenario and the issue-claim CLI now exercise the same histories, and the commands that release a claim keep to the rule. Spend more on generated histories or formal models only when a specific remaining failure justifies them.

**Status.** Active for the fixed-fixture pilot, 2026-11-23, revised 2026-11-24 after an independent review. The baseline observations below are from `38f5c2bba`. The initial process review used pstack as a reference for choosing invariants, demonstrating failures and explaining exclusions. [STATUS.md](STATUS.md) tracks implementation and adoption decisions.

## Baseline observations

A session consulting the issue-claim CLI and a foreman registering a cell both need to avoid duplicating work. The existing factory job already requires a refused registration to name the holder and suggest where to find another issue. The Node tool reads the same GitHub comment format to decide who may claim or release work. [Factory job](../../active/software-factory/scenarios/14-triage-the-backlog.scenario.yaml) · [CLI evaluation and read-back](../../../../scripts/issue-claim.mjs) · [Factory registration refusal](../../../../endpoints/botcore/plugins/botcore-factory/src/botcore_factory/cells.py)

**Observed in an isolated fixture.** We used open issue 205 from the factory backlog fixture, labelled `status:in-progress`, a third branch as the observer, no relevant PR, and a clock fixed at 2030-01-03 00:00 UTC. Both leases end on January 4. The factory host executed `cell-register` against its fixture world. The CLI's real `run` entry point executed `check 205 --json` against the same ordered comment bodies through its fake GitHub interface. Each row starts with a fresh fixture. A is `fix/alpha`, B is `fix/bravo`.

| Posted history | Factory refusal names | CLI reports held by |
| --- | --- | --- |
| Claim A | A | A |
| Claim A, claim B | **B** | **A** |
| Claim A, claim B, release B | A | A |

All three factory calls returned `ALREADY_CLAIMED`, suggested `issue-check` and left the fixture world, state and log unchanged. All three CLI checks returned its documented held exit code (3). The middle row demonstrates conflicting recovery information for an agent who needs to contact the holder. It supplies no evidence that two cells ran or that this happened on live GitHub. At the baseline revision Python selected the latest standing comment. Node selected the first live standing claim. Both sets of tests passed during this review. [Python claim tests](../../../../endpoints/botcore/plugins/botcore-factory/tests/test_claims.py) · [Node claim tests](../../../../scripts/issue-claim.test.mjs)

**Observed in the commands that write, 2026-11-24.** The review ran the real commands on the middle row, at the same revision. Each result contradicted the rule the readers were about to share.

| Command on "claim A, claim B" | Observed at the baseline | The rule asks for |
| --- | --- | --- |
| A releases with the CLI | The label came off. The observer's `check` printed "free" while B's live claim stood | B holds |
| B releases with the CLI | Refused as "held by A". With `--force` it ended both claims and took the label off | A holds |
| The foreman drops B's cell | The label came off. `issue-check` listed the issue as dispatchable and a third cell registered | A holds |
| A renews with the CLI | A released its own claim with "B claimed it first" | A holds |

The label is one value on the issue, and each release took it off without asking whether another claim stood. Both readers ignore claim comments on an issue without the label, so a release hid the other branch's claim from them. A fixture of comment bodies with the label held constant cannot show this. `issue-check` also listed an issue as stale, for the foreman to release, when a live claim was followed by a later one that had lapsed.

**Approved contract.** For a complete, ordered history on an open, labelled issue with distinct, unexpired branch claims and no associated PR, both readers name the earliest still-standing live claimant. Releasing either branch leaves the other visible. The refusal directs the caller to `issue-check`, which lists work they can register. [Acceptance scenario](../software-factory/scenarios/14b-identify-the-standing-claimant.scenario.yaml) · [Shared fixture](../software-factory/scenarios/fixtures/claim-histories.json)

**What keeps the contract through the commands.** These follow from the approved rule and were made with the readers.

- The label belongs to the holder. A release posts its comment first, ending its branch's claims, then takes the label off only when no other live claim stands. A claim whose lease ran out but whose branch has an open PR counts here for both, since the CLI reads it as holding. This holds for the CLI's `release`, for the undo of a failed `claim`, for `lane-drop` and for the undo of a failed `cell-register`.
- A branch whose claim does not hold the issue takes back its own claim without `--force`. Ending the holder's claim still needs it.
- The CLI's `claim` reads back as its `check` reads: it backs off when another branch's claim is the earliest live one, an open PR counting as `check` counts it. A holder that renews beside a later rival keeps the issue, and a branch that released and claims again goes behind the rival that stayed.
- The fixture's two release rows are the histories the CLI's `release` leaves, which its test checks by running the command.

**How both readers read a renewal.** A branch holds its place from its first live claim. Its latest live claim gives the lease and machine reported, so a renewal shows the current expiry. Once that first lease lapses the branch's place is its next live claim, so a rival that claimed in between then holds. Both readers already agreed on who holds. They now agree on the lease reported too. The last sentence is shared behaviour, pinned by a fixture row, and is the pilot's one open decision ([Pilot decision](#pilot-decision)).

**A third reader, with its own rule.** The factory gateway reads the same markers in the same plugin. It counts only comments its App wrote, takes the latest claim or release as the record, and names a holder by branch and machine. That is coherent for the comments' only writer. Its reader names B for the middle row above when its App wrote the comments, and reads nothing when another account did, apart from its cutover rule. The pilot's contract therefore covers the two readers that work from the owner's account, and it ends when their writers move behind the gateway: `cell-register` and the session claim are both planned to claim through the gateway's `issue-claim` in its G1 milestone, after which two live claims cannot be written. Until then the cutover is the one period in which all three read the same issue, and the gateway's reader takes a claim the owner's account released as still held until its lease ends. That belongs to the gateway's plan. [Gateway claim reader](../../../../endpoints/botcore/plugins/botcore-factory/src/botcore_factory/gateway/claims.py) · [Gateway claims design](../factory-gateway/factory-gateway.proposal.md#claims-github-is-the-record-the-gateway-its-only-writer) · [Gateway status](../factory-gateway/STATUS.md)

**Known differences, pinned.** These have distinct rules today and stay as they are. The first three have fixture rows that say what each reader observes, so a change to either is deliberate; the fourth has a test on each side.

- An expired claim whose branch has an open PR stays live for the CLI only.
- The CLI reads branch and machine names made of letters, digits and `. : @ / + - _`. `cell-register` accepts other branch names, which the CLI then reads as a label with no claim.
- A release whose branch is `null` ends every claim for the factory and none for the CLI. Neither writes one.
- `status:in-progress` with no claim comment, set by hand, is stale at once for the factory, which names an unknown holder and lists it in `staleClaims`. The CLI calls it held until the issue has been quiet for the lease length.

Two things have no row. A lease written without a time zone is UTC for the factory and local time for the CLI, and the two accept different non-ISO lease spellings; neither writes either. Closed and reopened issues keep their existing tests. [CLI claim protocol](../../../../scripts/issue-claim.mjs) · [Factory intake](../../../../endpoints/botcore/plugins/botcore-factory/src/botcore_factory/intake.py)

**What the contract does not promise.** A GitHub label update, posting a comment and reading it back are separate operations. Agreement over a completed history is achievable even if two writers initially observe a free issue. The decision above covers reporting. The factory does not read back after it claims, so a cell that raced a session keeps running after both readers name the session. A guarantee of exclusive execution during competing writes would require a separate protocol decision and evidence at that boundary; the gateway's single writer is that decision. Both readers also trust every comment's author and any lease length: on this public repository an outside account can post a claim marker before the real claim and win. The gateway counts only its App's comments.

## What changes with the industry evidence

| Production experience or method | What it buys AFD | Where its cost stops paying |
| --- | --- | --- |
| S3's ShardStore team compared operations on production code with an executable reference model. For S3 Express One Zone, the team combined models, generated tests and scheduling under injected faults, then maintained the checks as features evolved. [ShardStore](https://www.amazon.science/publications/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3) · [S3 Express, SOSP 2026](https://www.amazon.science/publications/validating-a-high-performance-cloud-object-store-with-lightweight-formal-methods) | Write down who should observe what before comparing implementations. Two readers can agree on the same wrong answer. Put the expected observation in the fixture from the agreed contract. | A small, stable decision table is cheaper than a second implementation of claim handling. Introduce a model only when combinations repeatedly escape the table. |
| FoundationDB uses a deterministic runtime to reproduce failures under simulation. Its team also tests outside that runtime. [FoundationDB, SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf) | Reuse the factory's fixture clock, GitHub responses and on-disk state. Keep the operations, ordering and clock needed to replay a failed test on a clean checkout. | A sequence of public calls explores call order. It cannot model a race *inside* a call unless the harness can pause at that boundary. A scheduler for the entire factory would duplicate substantial infrastructure. |
| AWS used TLA+ to find protocol design errors. Microsoft's CCF team connected its TLA+ model to implementation traces in CI. MongoDB's replication experiment could not match its traces to its model and reported the cost of observing consistent snapshots. [AWS design experience](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf) · [CCF, NSDI 2025](https://www.usenix.org/conference/nsdi25/presentation/howard) · [MongoDB engineering report](https://www.mongodb.com/company/blog/engineering/conformance-checking-at-mongodb-testing-our-code-matches-our-tla-specs) | Use a finite model when a protocol decision depends on which writes, crashes or retries can occur between observations. Replay a distinguishing trace against real handlers when the fixture exposes those steps. | A file list and reviewed SHA establish that someone looked. They cannot show that a model describes a changed implementation. If even one meaningful transition cannot be mapped, label the result design-only and keep it out of a code-conformance gate. |
| Hypothesis generates and shrinks sequences against a state machine. Its replay blobs depend on the library version. Kani checks Rust harnesses symbolically and reports insufficient loop bounds. [Stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html) · [Replay](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html) · [Kani unwinding](https://model-checking.github.io/kani/tutorial-loop-unwinding.html) | Keep a small named regression after discovering an unexpected sequence. Use a bounded proof for a Rust property only when the input domain and assumptions can be reviewed. | Sampled histories give examples. A passing proof applies to the harness and its stated bounds. An unreachable success path, an unresolved unwind assertion or a timeout leaves the question open. |

The opportunity for AFD is the connection between existing assets. The factory already has a fixture-backed command host and real multi-process lock tests, and the gateway has a test that runs eight claims on one issue at once. Core has specification-authored behavior vectors. The C++ workflow runs fuzzing and sanitizers, and the Rust crate has five cargo-fuzz targets that its workflow runs weekly. Treat those as the baseline when evaluating any new checker. [Factory fixture host](../../../../endpoints/botcore/plugins/botcore-factory/tests/conftest.py) · [Process contention tests](../../../../endpoints/botcore/plugins/botcore-factory/tests/test_lock_processes.py) · [Gateway route tests](../../../../endpoints/botcore/plugins/botcore-factory/tests/test_gateway_routes.py) · [Vector authorship rules](../../../../spec/vectors/README.md) · [C++ workflow](../../../../.github/workflows/cpp.yml) · [Rust fuzz targets](../../../../packages/rust/fuzz/fuzz_targets) · [Rust workflow](../../../../.github/workflows/rust.yml)

**Agent-authored models.** In its November 2026 Raft experiment, Antithesis used agents to construct proofs and checked recorded executions against the models. The team also changed the specification, logs and implementation deliberately to check that each layer could detect a violation. Their prototype covered safety with explicit storage and timing exclusions. For AFD, an agent can propose a property and shrink a failing history. The intended outcome should come from the caller's job and the approved rule. An agent inferring both model and expected holder from one reader could faithfully reproduce the very disagreement the pilot needs to expose. ## Where to invest after the pilot

These are independent decisions. Completing the claims pilot does not authorize another toolchain. Each row names what is covered today, so that what remains can be told from what exists.

| Candidate and who benefits | Covered today | Untested transition, and the trigger for more |
| --- | --- | --- |
| **Foreman takeover and event delivery.** A successor needs to see open work after a former holder resumes. | The session is checked again inside the transaction that marks delivery. A wait left open by a superseded session leaves the event to its successor, a refused old session changes nothing, and real processes contend for the lock. [Foreman tests](../../../../endpoints/botcore/plugins/botcore-factory/tests/test_foreman.py) · [Event tests](../../../../endpoints/botcore/plugins/botcore-factory/tests/test_events.py) | Delivery is recorded under the consumer's name, not the session. Start with two sessions, one event and one crash boundary. Name the persistent state, fairness assumptions and exclusions. | **Lane merge and gateway recovery.** An owner needs evidence that the head admitted to the merge queue received the required validation. | A head that moved is refused by the queue and ejected, a queued head the lane did not validate is not adopted, a merge at another head is recorded as such, and the enqueue is bound to the head. | **Rust output budgets and approval decisions.** A caller needs an actionable over-budget read failure and should see the result of a completed mutation with its warning. | All four ports load the output-budget vectors, which hold both outcomes at command dispatch. Three protocols with state are not in the table, because nobody has yet read their code against a failure: a held call's approval from issue to single use, the states of an MCP task, and the gateway's cutover. Each would enter by the same route as a row above, with what is covered and one named transition.

**Process costs.** Keep the invariant, exclusions and concrete failing history with the unit's test or design note. A diagram earns its place when it helps the owner choose between protocol behaviors. Defer a model manifest, compulsory statecharts, generated skills, an always-on verifier and broad theorem proving. Reconsider a process rule only after another subsystem independently needs it and there is a recurring omission the rule would catch. A retained model needs a unit maintainer, pinned runnable tools, a finite configuration and a documented way to observe divergence. Retire it if the owning protocol disappears or the promised check can be covered by a simpler regression.

## Pilot decision

The owner approved the fixed-fixture pilot on 2026-11-23, with the holder rule for the common two-branch case: the earliest still-standing live claimant. The fixture's first five histories cover one claimant, two claimants, release by either branch and a free issue. Ten more rows hold lapsed leases, a renewal and the known differences. Broader adoption depends on evidence of a failure the fixed cases miss; the review found one in the CLI's renewal, which three operations reach.

**Open for the owner.** Two branches hold live claims on one issue, and the first one renews in time. When its original lease time passes, the issue passes to the second branch, although the first never stopped renewing. Both readers do this today and the fixture pins it. Recommended: keep it. It can only happen while two live claims stand, which the gateway's single writer ends, and a rule that keeps a renewed holder's place would have to judge from comment times whether each renewal came before the lease it extends.
