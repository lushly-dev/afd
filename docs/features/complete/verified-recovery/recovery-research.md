# Compilers test their fixes; agent errors don't

*Research of 2026-11-24, the basis of the [verified recovery proposal](verified-recovery.proposal.md). Its findings about AFD describe `main` on that date; [STATUS.md](STATUS.md) records what has changed since. Corrected after review on the same day: shared vectors also pin the text of some engine suggestions (`validation.json`, `app-calls.json`), Python's testing package warns `MISSING_SUGGESTION` too, and the todo conformance suite has 50 cases, not 34.*

Ten researchers searching on 24 November 2026 found no tool, paper, linter or protocol test suite that takes the recovery suggestion carried by an agent tool's error, carries it out, and checks that the caller got closer to success. For structured command errors read by AI agents, the idea is new. Its parts are not. Compiler test harnesses (rustc's `run-rustfix`, Roslyn's code-fix verifier, Clang's FixIt tests) have long applied their own fix suggestions and recompiled the result. Proof assistants (Isabelle's Sledgehammer, Lean's `exact?`) replay a suggestion inside the trusted checker before showing it. Formal methods name the target property, "from every state a caller can reach, success is still reachable", and give cheap ways to check it on small worlds. The case for checking is now measured. In a 15,120-trial study, telling an agent with expired credentials to run a terminal command left 45% of tasks recovered, against 84% when the error named a login tool. In another study the list of recovery tools, not the diagnostic detail, carried the whole gain. Fix validation at scale gives the main warning: "the refusal went away" proves only that a fix is plausible. Automated program repair and Google's LLM patching both passed "fixes" that deleted the check. The gap is concrete in AFD. The server tells every agent to "follow error.suggestion to recover", yet `suggestion` is free text that nothing verifies. Of 379 measured suggestion sites, only 18% can be followed by a program exactly as written, and 42% cannot be followed by a program at all. One factory test asserts a suggestion naming `lane-handoff`, a command no surface registers, and the Python port silently ignores suggestion assertions. The prior art points to a staged build: first a static check that every named command exists, then a structured recovery field in the shared specification, then a follow-and-assert step in scenarios with an independent progress oracle, and only after that exhaustive exploration of small worlds.

## Agent research measures how wording affects recovery but never tests the advice itself

The plain idea in this field is simple. An AI agent calls a tool, gets an error back as text, and decides what to do next from that text. Researchers ask which kinds of error text help the agent recover. They answer statistically, by running many agents over many tasks, and nobody asks whether one particular suggestion is true. MCP, the Model Context Protocol most agent tools use, splits errors into protocol errors and tool execution errors. It says the latter "contain actionable feedback that language models can use to self-correct and retry with adjusted parameters", but it defines no structured suggestion field: its own example is plain prose ("Invalid departure date: must be in the future. Current date is 08/08/2025.") ([MCP spec, Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)) [full text]. The protocol's one machine-readable recovery path is `URLElicitationRequiredError` (-32042), which "MUST include a list of elicitations that are required to complete before the original can be retried" ([MCP spec, Elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)) [full text]. Vendor guidance only recommends good error text. Anthropic tells tool authors to "prompt-engineer your error responses to clearly communicate specific and actionable improvements" ([Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)) and to say "what Claude should try next" ([Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)). Gemini's guide says only "Implement robust error handling" ([Gemini docs](https://ai.google.dev/gemini-api/docs/function-calling)). Google ADK's `ReflectAndRetryToolPlugin` retries a failed call up to three times regardless of what the error said ([ADK](https://adk.dev/integrations/reflect-and-retry/)) [docs via summariser].

The strongest measurement is Xu and Wu's study of MCP error messages ([arXiv 2609.35381](https://arxiv.org/html/2609.35381v2)) [full text, v2]. They surveyed **3,001 error messages from the 150 most-starred MCP servers**. **949 tell the caller what to do next, and 477 of those depend on something the server cannot see**, such as the caller's login, permissions or tools. Of 67 credential-error steps, 62 ask for a configuration change, a web page or a terminal command. Of 30 rate-limit steps, 20 say to wait and retry without naming the call to repeat. In 15,120 trials across five OpenAI models on BFCL tasks, **expired credentials with a terminal-command step left 45% of tasks recovered, against 82% with the cause alone and 84% when the error named a login tool**. On a rate limit, "Wait before retrying." recovered 6% and naming the exact call to repeat recovered **88%**. The second-pass reading corrects one headline claim. The "up to 69 points" loss belongs to a single model (GPT-6 Astra), and the "more capable, more harmed" trend fails for GPT-6 Luna, which lost 26 points. The limits matter for AFD. Codex agents labelled the survey with no reported human agreement. The experiment used synthetic error texts, not the servers' own. The authors state that "the survey did not execute or test the suggested steps against real services."

Two further studies isolate what makes advice work. Panthi and Abdelfattah's outcome monitors attach a "receipt" naming the violated property and the tools that could recover ([arXiv 2608.19303](https://arxiv.org/html/2608.19303v1)) [full text, first ~100k of 109k characters]. Completion rose from **10.9% to 28.1%** on hard ToolMaze workflows. Stripping the recovery-tool list left completion at baseline (+0.9 points), and restoring it added **+11.4 points**. Diagnostic detail showed no detectable effect, though the authors note the test could only detect effects of about 18 points or more. The monitor "never executes a repair", and the listed tools are not shown to have been checked. Woo, Conde and Reviriego studied how an error is delivered, not what it says ([arXiv 2611.11581](https://arxiv.org/html/2611.11581v1)) [full text, first ~100k of 153k characters]. The second pass corrects the first: they used **four fault kinds (transient, fixable, unrecoverable and ambiguous)** as experimental conditions, not a proposed taxonomy. A kind-specific sentence delivered as a runtime note raised explicit-error success by **+14.2 points (7–8B models) and +10.5 (32–70B)**. An oracle that knew the true fault kind beat their rules by 16.8 and 18.5 points. Their frozen rules gave correct guidance to 29.8% of errors, wrong guidance to 3.9% and none to 66.3%. The authors warn that retry guidance with "no idempotency gate" could duplicate writes, and that the intervention "does not run tools or change their results."

Fault-injection benchmarks show how often agents fail to recover, read here at abstract level. RetryRealistic reports correct recovery in **19–68%** of faulted runs and confident fabrication in 6–26% ([arXiv 2611.28341](https://arxiv.org/abs/2611.28341)) [abstract only]. Bench2Robust degraded 69 of 70 model-subset pairs ([arXiv 2608.11977](https://arxiv.org/abs/2608.11977)) [abstract only]. Apple's ToolSandbox scores "milestones" on world state, a formal definition of progress short of success ([arXiv 2408.04682](https://arxiv.org/abs/2408.04682)) [abstract only]. SWE-agent gives older ablation evidence ([arXiv 2405.15793](https://arxiv.org/html/2405.15793v3)) [full text]. An edit command that rejects broken edits with linter feedback raised resolution from **15.0% to 18.0%**. After one failed edit, the chance that an edit eventually succeeds fell **from 90.5% to 57.2%**. A small-model study found that putting the failed call back into context raised the chance of repeating it from **0.06 to 0.54**, and that "do not repeat" instructions did not help ([arXiv 2608.23651](https://arxiv.org/abs/2608.23651)) [abstract only]. The safety side is just as clear. VATS reports that instructions hidden in error text roughly triple the success of indirect prompt injection, because agents treat error text as authoritative ([arXiv 2606.07992](https://arxiv.org/abs/2606.07992)) [abstract only]. Agents obey error advice, so wrong advice is costly and planted advice is dangerous.

The tooling that exists checks the form of error text, never its truth. `7shep/mcp-linter` sends each read-only tool four bad inputs and flags stack traces, opaque text and errors returned as successes ([source](https://github.com/7shep/mcp-linter/blob/main/src/mcp_lint/rules/probe.py)) [full text]. The second pass corrects the first here too: its "no guidance" rule passes a message that *either* names the bad input *or* contains a guidance word such as "try" or "expected". `robert19001-cmyk/mcp-lint recover` checks with regular expressions that credential errors name a same-server tool and that no step points to a terminal, config file or web page ([score.ts](https://github.com/robert19001-cmyk/mcp-lint/blob/main/src/recover/score.ts)) [full text]. Its "names the retry" rule accepts any listed tool, not necessarily the failing call. Its live probe calls each tool once with empty arguments. Neither linter calls the tool a suggestion names, and both are one-star projects a few weeks or months old. The official MCP conformance suite's tool-error scenario passes if `isError` is true and the text is non-empty ([tools.ts](https://github.com/modelcontextprotocol/conformance/blob/main/src/scenarios/server/tools.ts)) [full text]. Its authorization scenarios contain the field's only real follow-the-advice test. A mock server returns 403 with a step-up scope, and the suite asserts the client re-authorizes for that scope, with at most three attempts ([scope-handling.ts](https://github.com/modelcontextprotocol/conformance/blob/main/src/scenarios/client/auth/scope-handling.ts)) [full text]. That checks that a client obeys a fixed protocol challenge, not that a real server's advice is true. AgentCheck is closest in shape: it replays a recorded fault, applies a mitigation and reruns ([arXiv 2607.11098](https://arxiv.org/abs/2607.11098)) [abstract only]. But the mitigation is the developer's change to the agent, not the server's suggestion. The live MCP proposal SEP-3313 would add `retryable`, `retryNotBefore` and a free-text `agentGuidance`, with the rule that a client "MUST NOT auto-retry a non-idempotent tool even when `retryable` is true". It defines no test that the guidance is true ([SEP-3313 text](https://github.com/johnyzaguirre-glean/modelcontextprotocol/blob/draft/tool-failure-classification/seps/3313-tool-failure-classification.md)) [full text; open draft].

Web standards help explain why nobody built this check. HTTP and RPC error formats deliberately keep recovery advice away from programs. RFC 9457 says the human `detail` field "should help the client fix the problem" but that consumers should not parse it ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)) [full text]. Google's AIP-193 puts "the full resolution" in a message for end users and keeps machine data in `ErrorInfo` ([AIP-193](https://google.aip.dev/193)) [full text]. Machine-followable recovery exists only for a few generic cases: `Retry-After` timing, authentication challenges, allowed methods, re-reading on conflict, and pointers to the bad field. Kubernetes spells out a per-reason recovery table, for example "Do not retry. Fix the request." for 422 ([API conventions](https://raw.githubusercontent.com/kubernetes/community/master/contributors/devel/sig-architecture/api-conventions.md)) [full text]. Where clients act on error metadata automatically, getting the classification wrong is the documented failure. AWS's SDK guide describes legacy retrying that "continues to retry at full rate during service disruptions", and the cross-SDK retry table and token bucket built in response ([AWS retry behavior](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html)) [full text]. Testing tools stop one step short. Schemathesis checks that a 405 response carries an `Allow` header but does not retry with an allowed method, and it follows links only after a successful call ([checks](https://schemathesis.readthedocs.io/en/stable/reference/checks/); [stateful guide](https://schemathesis.readthedocs.io/en/stable/guides/stateful-testing/)) [full text]. Arazzo 1.1.0 lets a workflow say "run this remediation step, then retry the failed one" ([Arazzo](https://spec.openapis.org/arazzo/latest.html)) [full text], but the test author writes the recovery into the test, not the server into its response. There is one more lesson from the web. Hypermedia ("the response tells you what you can do next") failed partly because real clients never followed server-supplied links ([htmx essay](https://htmx.org/essays/hypermedia-clients/)). Agents do follow them, so whether the offered next step is true has become a live question for the first time.

## Compilers and proof assistants already carry out their own suggestions

Compiler diagnostics are the closest analogue. A compiler error with "help: write `&x` here" is a suggestion of the same kind, and mature compilers test such suggestions at three increasing strengths. The weakest compares text: the test applies the edit and checks the resulting file against a stored "expected" file. The middle strength applies and rechecks: after applying the edit, the test runs the parser or compiler again on the result. The strongest also checks the exact set of remaining errors and that repeated fixing stops.

Rust's compiler is the best documented. A UI test marked `run-rustfix` checks that the expected diagnostic is emitted, applies the suggestion, compares the result with a stored `.fixed` file, and then compiles the fixed source; this compilation "is required to succeed" ([rustc dev guide](https://rustc-dev-guide.rust-lang.org/tests/ui.html)) [full text]. Each suggestion carries an **applicability level**: `MachineApplicable` ("Can be applied mechanically"), `HasPlaceholders`, `MaybeIncorrect` or `Unspecified`. The level says whether a tool may apply the suggestion without a person checking it, and authors are told to "be conservative" ([rustc dev guide, diagnostics](https://rustc-dev-guide.rust-lang.org/diagnostics.html)) [full text]. A repository lint ("tidy") requires every error code's documentation to contain an example that fails with *that* code. Its exemption list errors out when an exempt code gains a proper example, so the list cannot go stale ([error_codes.rs](https://github.com/rust-lang/rust/blob/main/src/tools/tidy/src/error_codes.rs)) [full text]. The gap is that "the fixed code compiles" is enforced, but "the original warning is gone" is not asserted separately. At run time `cargo fix` recompiles after applying fixes. Its test suite injects a failing second compile and asserts the error "errors present after applying fixes", and that without `--broken-code` the source is left unchanged ([cargo fix.rs](https://github.com/rust-lang/cargo/blob/master/tests/testsuite/fix.rs)) [full text].

Roslyn, the .NET compiler platform, does the most. After a fix, its test library recomputes all analyzer and compiler diagnostics on the fixed code and requires them to equal an expected set, which is empty unless the author says otherwise. It applies fixes repeatedly under an asserted upper bound, by default one round per fixable diagnostic, and stops when a fix produces no change ([CodeFixTest\`1.cs](https://github.com/dotnet/roslyn-sdk/blob/main/src/RoslynSdk/Microsoft.CodeAnalysis.Testing/Microsoft.CodeAnalysis.CodeFix.Testing/CodeFixTest%601.cs)) [full text]. So **Roslyn checks all three properties AFD would want: the original problem is gone, no new one appeared, and repeated fixing converges**. ESLint's RuleTester re-parses every fix and suggestion and rejects one whose output equals its input, a cheap guard against no-op advice. At run time the linter re-lints for up to 10 passes and stops with "Circular fixes detected" when a fix undoes the one before it ([rule-tester.js](https://github.com/eslint/eslint/blob/main/lib/rule-tester/rule-tester.js); [linter.js](https://github.com/eslint/eslint/blob/main/lib/linter/linter.js)) [full text]. Error Prone compiles the expected output unless a test opts out with `allowBreakingChanges()` ([BugCheckerRefactoringTestHelper](https://github.com/google/error-prone/blob/master/test_helpers/src/main/java/com/google/errorprone/BugCheckerRefactoringTestHelper.java)) [full text]. Clang's design rule ties a fix to everything that follows: "Clang must recover from errors as if the fix-it had been applied", so every later diagnostic indirectly tests the fix ([Clang Internals](https://clang.llvm.org/docs/InternalsManual.html)) [full text]. Its `fixit.c` test applies all fix-its and recompiles with `-Werror -pedantic` ([fixit.c](https://github.com/llvm/llvm-project/blob/main/clang/test/FixIt/fixit.c)) [full text]. TypeScript's code-fix tests, Go's analyzer tests and clang-tidy only compare text ([fourslash.go](https://github.com/microsoft/typescript-go/blob/main/internal/fourslash/fourslash.go); [analysistest.go](https://github.com/golang/tools/blob/master/go/analysis/analysistest/analysistest.go); [check_clang_tidy.py](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/test/clang-tidy/check_clang_tidy.py)) [full text]. Command-line hints are weaker still. Git's tests compare `hint:` lines byte for byte and test the hinted commands (`cherry-pick --continue`, `--skip`, `--abort`) in separate tests, never chaining "receive the hint, run it, reach success" ([t3507](https://github.com/git/git/blob/master/t/t3507-cherry-pick-conflict.sh)) [full text, sampled files only].

Proof assistants check a suggestion before showing it. Their plain idea is a split between search and replay. An untrusted, fast search finds a candidate, and the trusted checker replays it under a time limit before the user sees it. Sledgehammer's external provers find a proof, and Isabelle "preplays" the suggested one-line proof with a default **1-second** limit. Each suggestion is displayed with its replay time, or marked "timed out" or "failed" ([Sledgehammer manual, 24 Oct 2026](https://isabelle.in.tum.de/dist/doc/sledgehammer.pdf)) [full text]. Textual reconstruction succeeded in **7,838 of 7,893 cases (99.3%)**, and the authors' lesson is that "preplaying insulates users from failures" ([Blanchette et al.](https://smolka.st/papers/isar_jar.pdf)) [full text; publication year from memory]. Its regression option `expect=some_preplayed`, as opposed to plain `some`, is a ready-made vocabulary for "a suggestion exists" versus "a suggestion was verified". Lean adds a finding that applies directly to AFD. `mkValidatedTactic` re-runs the *printed* tactic text in the saved starting state, because "we cannot determine if a tactic requires `expose_names` merely by inspecting its syntax ... nor the underlying `Expr`". When replay fails, Lean replaces the suggestion with "found a proof, but the corresponding tactic failed" ([TryThis.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Meta/Tactic/TryThis.lean)) [full text]. **A correct internal object can print as text that does not work**, so the rendered form must be checked. Mathlib's `says` keeps recorded suggestions from going stale. In CI it regenerates the suggestion and fails on mismatch with a message saying how to reproduce the failure locally ([Says.lean](https://raw.githubusercontent.com/leanprover-community/mathlib4/master/Mathlib/Tactic/Says.lean)) [full text]. GHC type-checks each "valid hole fit" before listing it, and it rolls back the type checker's side effects so that checking one candidate cannot disturb the next, a dry run in miniature. The author argues the cost is acceptable because it is paid "only ... when the program would in any case fail due to an error" ([Gissurarson 2018](https://users.cs.northwestern.edu/~robby/icfp2018/icfpws18haskell/icfpws18haskellmain-id14-p.pdf)) [full text].

Databases and infrastructure add two more patterns. PostgreSQL computes some hints from the matcher's own failed search, "This call would be correct if the variadic array were labeled VARIADIC", while its style guide allows hints that "might not always be applicable" ([parse_func.c](https://github.com/postgres/postgres/blob/master/src/backend/parser/parse_func.c); [style guide](https://www.postgresql.org/docs/current/error-style-guide.html)) [full text]. Preflight interfaces show a range of strength. AWS EC2's `DryRun` checks permissions only and returns its verdict as an error code. Kubernetes' server-side dry run runs the whole request pipeline except storage, and fails a request "rather than risk an unwanted side effect" when a webhook cannot promise none ([Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/); [EC2 RunInstances](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_RunInstances.html)) [full text]. None of them closes the gap between check and use: state can change after the check and before the call.

## A vanished refusal proves only plausibility, not progress

Automated program repair asks the question AFD's check must answer, and the answer is cautionary. A repair tool generates a patch and accepts it if the test suite then passes. Researchers call a patch that passes the tests "plausible" and one that actually fixes the bug "correct". Qi, Long, Achour and Rinard re-examined the patches reported by three published repair systems and found that most were not even plausible. The overwhelming majority were equivalent to deleting functionality, and Kali, a tool that only deletes code, did as well as the published systems ([ISSTA 2015](https://www.cs.toronto.edu/~fanl/papers/kali-issta2015.pdf)) [full text link; the per-system counts were relayed from garbled slides and are left out here]. Industry found the same thing with LLM fixes. Google's sanitizer-bug pipeline runs tests and sanitizers before a human sees a fix, yet the first human review still rejected **10–20% of commits that had passed the automated checks**. The rejected fixes included one that removed the failing test and one that "fixed" a data race by making the code run sequentially ([Google technical report, Jan 2024](https://storage.googleapis.com/gweb-research2023-media/pubtools/7563.pdf)) [full text]. GitHub's Copilot Autofix harness asks four questions of each fix over 2,300 real alerts: was the alert fixed, did new alerts appear, were syntax errors introduced, and did test output change. Fixes that fail "are not displayed to users" ([GitHub Docs](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/responsible-use-autofix-code-scanning)) [full text]. Every industrial system gates on the same checker that raised the problem (Infer, CodeQL, the sanitizer), and that gate is exactly the one a fix that silences the check passes. All of them add a second oracle, a different check the fix cannot game, and a human. For AFD, "following the suggestion made the refusal disappear" is the analogue of "the tests pass". A suggestion such as "pass `--force`" would pass it.

Outcome measures help but are proxies. Google's ML review-comment edits were tuned to 50% precision. 40–50% of previewed edits were applied, and fewer, more precise suggestions earned higher acceptance; the team calls acceptance a proxy for usefulness ([Google Research blog](https://research.google/blog/resolving-code-review-comments-with-ml/)) [full text]. Renovate's Merge Confidence estimates whether an update works from other repositories' CI results, weighted toward projects "with high test reliability" ([Renovate docs](https://docs.renovatebot.com/merge-confidence/)) [full text]. That is the population-level version of the same lesson: a repository with no tests passes every update.

Outside software tooling, many fields attach a prescribed response to an alarm or error, and most require only that the response *exist*. Few show that it *works*. Google's SRE book says "Every page should be actionable" and that a page with "rote, algorithmic responses" should be automated instead ([SRE book](https://sre.google/sre-book/monitoring-distributed-systems/)) [full text]. Read across to AFD, a suggestion deterministic enough to verify is deterministic enough to execute. Its "3x MTTR" claim for playbooks has no published method ([SRE book](https://sre.google/sre-book/introduction/)). Google's DiRT exercises test recovery while "explicitly preventing critical personnel, area experts, and leaders from participating", so the documentation has to carry the recovery, which is the human version of a literal-minded follower ([ACM Queue](https://queue.acm.org/detail.cfm?id=2371516)) [search excerpts; full text returned 403]. IBM's z/OS message catalogs split responses by audience ("Operator Response", "User Response") and flag "action required" in the message ID ([IBM TSO/E messages](https://www.ibm.com/docs/SSLTBW_2.1.0/pdf/ikj2m200.pdf)) [search summaries of the PDFs]. No public account shows these responses being tested. WCAG 2.2's success criterion 3.3.3 requires error suggestions on web forms, but its guidance lists "no failure techniques and no test procedures" ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)) [full text]. Aviation shows the same gap. NASA's Burian found that checklist developers rely on "precedent ... and their own preferences and judgment" for lack of validation guidance, and that crews choose the wrong checklist for a cue ([NASA](https://hsi.arc.nasa.gov/flightcognition/Publications/EA_Checklist_Design.pdf)) [full text]. A suggestion can be right in itself and still attached to the wrong error, so a test must trigger the refusal from real state. Medicine has the strongest outcome-based validation. In a randomized simulation trial, surgical crisis checklists cut failures to perform critical steps **from 23% to 6%** ([Arriaga et al., NEJM 2013](https://psnet.ahrq.gov/issue/simulation-based-trial-surgical-crisis-checklists)) [secondary summaries]. The procedure was validated by having teams follow it in a faithful reproduction of the failure and measuring the outcome.

Software failure studies explain why recovery paths rot. Yuan et al. found that **92% of catastrophic failures** in five distributed systems came from mishandled non-fatal errors, and that **58%** could have been caught by simple tests of the error-handling code. They recommend starting "from existing error handling logic" and working backward to a test that triggers it ([OSDI 2014](https://files.usenix.org/s3fs-public/cdn/osdi14-paper-yuan.pdf)) [full text]. Their trivial-handler category (empty, log-only or "TODO" handlers) has an AFD counterpart in suggestions such as "contact support". Wasabi found retry bugs by reusing existing unit tests and injecting the retry-triggering exception, catching bugs the original suites missed ([SOSP 2024](https://knowledge.uchicago.edu/record/14028/files/If-At-First-You-Dont-Succeed-Try-Try-Again-Insights-and-LLM-informed-Tooling.pdf)) [full text]. That is a cheap way to build an AFD checker: reuse the scenarios that already reach each refusal.

## Formal methods name the property: no dead ends, not just no deadlocks

Formal methods do not test suggestions, but they give precise names for what "the suggestion is true" means. They also show that the obvious check is the wrong one. Start with type soundness. Programming-language theory proves "progress": a well-typed program is either finished or can take another step, so it never gets stuck ([Pierce, TAPL](https://www.cis.upenn.edu/~bcpierce/tapl/); [Wright and Felleisen 1994](https://doi.org/10.1006/inco.1994.1093)) [standard references, not re-read]. When exceptions are added, an uncaught error counts as finished. AFD's present rule, that every failure has the right shape, is the same weak theorem. The researcher's proposed strengthening, a "non-stuck refusal", is the researcher's own construction, not a published result. It requires that every failure's suggestion name a command that is enabled in the resulting state, meaning that calling it is not refused immediately for the same reason. A stronger form requires that following the suggestion either succeeds or strictly reduces a measure of distance to success. That is the standard technique for proving that a loop terminates, applied to recovery.

The key distinction is between a **deadlock** and a **dead end**. A deadlock is a state with no next step at all. A dead end is a state from which success can no longer be reached, even though steps remain possible. A refusal that leaves state unchanged is a step back to the same state, a self-loop, so deadlock checks pass trivially while the caller is stuck forever. The property that matters, "from every reachable state, success is still reachable", is written **AG EF success** in CTL, a branching-time temporal logic. It is a *possibility* property: some path exists. The stronger *guarantee* property, "a caller who always follows the suggestion will get there", is a leads-to (liveness) property and needs a fairness assumption ([Owicki and Lamport 1982](https://doi.org/10.1145/357172.357177)) [standard reference, not re-read]. Popular tools handle these unevenly. TLA+'s checker cannot state AG EF directly, and practitioners on its list assert the negation and read the counterexample as a witness, or add fairness and check liveness instead ([TLA+ group](https://groups.google.com/g/tlaplus/c/A58EEr7YWGg)) [confirmed]. Lamport's paper on possibility properties is the theory behind the second workaround ([MSR PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/Proving-Possibility-Properties.pdf)) [venue and year from memory; PDF not text-extracted]. A violation of the guarantee property appears as a "lasso": a cycle of suggestion-following that never succeeds, such as two errors that suggest each other.

AI planning has a matching vocabulary. An *explicit* dead end has no applicable action. An *implicit* dead end has applicable actions, none of which reaches the goal ([SixthSense, AAAI 2010](https://ojs.aaai.org/index.php/AAAI/article/view/7752)) [confirmed]. These map exactly onto two failures: a refusal whose suggestion names nothing that can be called, and a refusal whose suggested command runs but leads nowhere. Planners also offer checkers that need no trust in the planner: VAL independently validates that a given plan runs and reaches the goal ([VAL](https://github.com/KCL-Planning/VAL)) [standard reference, not re-read]. Process modelling contributes workflow-net "soundness" (van der Aalst): from every reachable state the end is reachable, finishing leaves nothing half-done, and every task can occur in some run ([van der Aalst](https://www.vdaalst.rwth-aachen.de/publications/p98.pdf)) [partially confirmed]. The third condition catches suggestions that name commands which are never applicable anywhere.

Games state the distinction most memorably. A level is "completable" if a winning path exists from the start, but "the player may still get stuck if they stray from the solution path", which game designers call a softlock ([PCG Workshop 2025](https://pcgworkshop.com/archive/cooper2025softlocks.pdf)) [search snippet only]. Item randomizers check only completability. Research systems check softlock freedom, for example by CTL model checking of Super Metroid level abstractions ([Mawhorter and Smith](https://api.crossref.org/works/10.1145%2F3582437.3582447)) [abstract only; venue unverified]. AFD's existing happy-path scenarios are completability checks. The missing check is softlock freedom. Interactive fiction's "Zarfian cruelty scale" grades games from Merciful (cannot get stuck) and Polite (stuck, but it is immediately obvious) through Nasty and Cruel (an action silently makes the game unwinnable) ([IFWiki](https://ifwiki.org/Cruelty_scale)) [confirmed]. A refusal that honestly says "not recoverable, tell the user" is Polite and legitimate. The dangerous cases are successes that silently make a goal unreachable, and only state-space search finds those. Plotkin's 2019 revisit warns that a big enough undo makes every game feel merciful ([Zarf 2019](https://blog.zarfhome.com/2019/09/the-zarfian-cruelty-scale-revisited)) [confirmed]. A suggestion check should therefore not let a universal "start over" count as a good suggestion everywhere.

Fault-tolerance theory supplies the strongest notion of recovery and a testing pattern. A self-stabilizing system reaches a legitimate state from *any* starting state (convergence) and then stays there (closure) ([Dijkstra 1974](https://doi.org/10.1145/361179.361202); [Arora and Gouda 1993](https://doi.org/10.1109/32.256850)) [standard references, not re-read]. The pattern to borrow is to start tests from arbitrary or corrupted states, not only from states normal use reaches. Crash-only software makes recovery the normal start path so it is exercised constantly ([Candea and Fox 2003](https://www.usenix.org/conference/hotos-ix/crash-only-software)) [standard reference, not re-read]. A suggestion that is only displayed is never tested. Interface automata define two components as compatible if *some* environment can steer clear of error states ([de Alfaro and Henzinger 2001](https://doi.org/10.1145/503209.503226)) [standard reference, not re-read]. In those terms, a true suggestion is the first move of such an environment's strategy, and checking a given strategy is far cheaper than finding one.

All of these are graph-reachability questions, and they are cheap on small worlds. Jackson's "small scope hypothesis" holds that most bugs have small counterexamples, so exhaustively checking all cases up to a small bound finds a high share of them. A re-evaluation found that small scopes "can indeed find a high proportion of errors, but results depend on the observed benchmark and appropriate test oracles are required" ([TU Graz](https://tugraz.elsevierpure.com/en/publications/reevaluating-the-small-scope-testing-hypothesis-of-answer-set-pro/)) [confirmed]. The recipe the formal-methods researcher derived is their own inference, assembled from the techniques above, not a published method. Build every state reachable in a world of two or three entities. Compute, backward from success states, the set that can still reach success. For each refusal, check that the suggested command is enabled and that it lands inside that set. The cost grows linearly with the explored graph. None of these fields was found applying the idea to API error hints.

## The idea is new for agent command errors, though every part has been done before

The verdict follows directly. As of 24 November 2026, no published or open-source work found takes a command or tool error's own suggestion, performs it, and asserts that the caller made progress. The search was limited to what web and GitHub search could reach, so closed-source vendor tools could exist unseen. The combination is what is new: a suggestion addressed to an AI agent, treated as a testable claim, executed against fixtures, and judged by a progress oracle. Each ingredient has precedent, as the ladder below shows, from weakest to strongest verification.

| Instance | Field | What it verifies about the offered recovery | Strength | Evidence |
|---|---|---|---|---|
| MCP tool-error conformance, Inspector exit codes, promptfoo `is_error` | Agents | An error is flagged and its text is non-empty | Exists | full text / docs via summariser |
| WCAG 3.3.3, Nielsen #9, IBM message catalogs, SRE "actionable" pages | HCI, operations | A suggestion is required to exist; reviewed by people | Exists | full text / search summaries |
| `mcp-linter`, `mcp-lint recover`, APIs.io `next` label test | Agents | The text has a guidance word or names a same-server tool, and avoids terminal, config and web steps | Form | full text |
| Git hints, TypeScript and Go code fixes, clang-tidy, pg_regress | Compilers, CLIs, databases | The suggestion's text or edit matches a stored copy | Text | full text |
| ESLint RuleTester, Error Prone, rustc `run-rustfix`, Clang `fixit.c`, `cargo fix` | Compilers | The fix is applied and the result parses or compiles | Apply and recheck | full text |
| Sledgehammer preplay, Lean `mkValidatedTactic`, GHC hole fits, Mathlib `says` | Proof assistants | The rendered suggestion is replayed in the trusted checker before display, or regenerated in CI | Replay before offer | full text |
| Roslyn code-fix tests | Compilers | The original diagnostic is gone, none are new, and repeated fixing converges within a bound | Full recheck | full text |
| MCP conformance step-up authorization scenarios | Protocols | A client follows a fixed 403 challenge and re-authorizes with the right scope | Follows one fixed path | full text |
| 2609.35381, 2608.19303, 2611.11581 | Agents | Aggregate agent recovery under alternative advice texts | Statistical, not per suggestion | full text |
| AgentCheck | Agents | A developer's mitigation removes a replayed fault | Follows the developer's fix, not the server's | abstract only |
| Copilot Autofix harness, Google LLM patching | Fix validation | The alert is gone, no new alerts appear, tests still pass, then a human reviews | Recheck plus second oracle | full text |
| Super Metroid CTL, workflow-net soundness | Games, formal | No reachable state is a dead end | Exhaustive, on a model | abstract only / partially confirmed |

Three lessons recur across the table. First, verifying anything requires a machine-readable action: Rust's applicability levels, MCP's -32042 list, Roslyn's edits. Prose advice gets at most a form check. Second, the checker that raised the problem is a poor judge of the fix, so strong systems add an independent oracle. Third, every system that keeps recorded suggestions also re-derives them in CI (`says`, `expect`, tidy) or they go stale.

## AFD tells agents to follow its suggestions but checks only substrings

The shared specification makes a promise it does not check. The schema defines `suggestion` as an optional string with no pattern or structure, described as "Actionable recovery guidance for the caller" that commands "should always set" (`spec/schema/error.json:7-22`). The default `server/discover` instructions, in the specification and in code, tell every agent: "follow error.suggestion to recover" (`spec/tool-strategies.md:143-144`; `packages/server/src/mcp-modern.ts:214`). Besides the text that shared vectors pin for a few engine errors (the `VALIDATION_ERROR` layout, `CALL_NOT_GRANTED`), the only rules about what a suggestion may say concern meta-tools. A suggestion may name `afd-discover`, `afd-detail`, `afd-help` or `afd-context-*` only where the caller can call them, and an unknown-command suggestion offers at most three close matches from names the caller may call (`spec/error-codes.md:83-117`). That one path is true by construction, because `notFoundSuggestion` computes its matches from the live registry (`packages/server/src/command-routing.ts:65-94`), the same pattern as PostgreSQL's matcher-derived hints. Tool-strategy conformance states outright that "Suggestions are not compared" (`spec/tool-strategies.md:334`). The schema README claims surface linters enforce suggestions (`spec/schema/README.md:57-62`), but no surface rule reads suggestions at all. The 13 rules cover names, descriptions, schemas, categories, contexts and the `requires` graph (`packages/testing/src/surface/*`). The only generic check is a `MISSING_SUGGESTION` *warning* when a suggestion is absent (`packages/testing/src/validators.ts:209-216`, and Python's `python/src/afd/testing/validators.py`). All four ports model the field identically as optional free text: TypeScript `suggestion?: string`, Python `str | None`, Rust `Option<String>` and C++ `std::optional<std::string>` (`packages/core/src/errors.ts:25-81`; `python/src/afd/core/errors.py:23-53`; `packages/rust/src/errors.rs:44`; `packages/cpp/include/afd/errors.hpp:16-31`). The shared factory texts ("Check the input and try again", "Please try again. If this persists, contact support.") name no command. The only structured "command plus arguments" anywhere in a result is `undoCommand`/`undoArgs` on a *success* (`spec/schema/result.json:60-68`), and the error side has nothing like it.

A measured corpus shows what the free text contains. One researcher extracted **379 suggestion sites (339 distinct strings)** from five surfaces: the factory plugin (89), its gateway (60), the todo example's four backends (27), the TypeScript server's built-in errors (57) and the Umbel host (146). They classified each by hand where the heuristic was unsure (216 overrides; boundaries could move roughly ±10 rows).

| Class | Meaning | Share |
|---|---|---|
| A | Names a command on the same surface | 28% |
| B | Change the arguments and call again (half state the valid values) | 25% |
| C | Wait or retry unchanged | 8% |
| D | An action outside the command surface: shell, config, GitHub, ask a person, or Umbel's CLI | 31% |
| E | Generic ("Check the input and try again") | 3% |
| F | Other: nothing to do, check the effect, or a transport action | 5% |

What a program could do with them matters more. **Only 18% (68 sites) can be followed by a deterministic test exactly as written**, meaning they name an existing command and leave no argument missing. Another 16% need arguments the suggestion does not give. 24% can be acted on mechanically without naming a command: changed arguments with the valid values stated, a wait, or a transport step. **42% cannot be followed by a program at all.** The factory does best (57% class A, 28% followable as written). Umbel does worst (49% class D, mostly instructions for an operator). Of the class A suggestions, 62% name a mutation and 38% only a read. A read suggestion makes progress only as information, but many make a checkable claim about the read's output, such as "lane-status lists held branches and their holdReason" (`cells.py:502`). 16% of all suggestions, and 28% of class A, depend on state, for example "Wait for the lane to land it (lane-resume if paused)". In some of these the code picks the branch from known state; in others the caller must read state first and then decide.

The corpus already contains the bugs this check would catch. The factory's `NOT_LANE_HOST` error says "Hand the branch over with **lane-handoff**", but no surface registers that command. `tests/test_queue.py:13` asserts `"lane-handoff" in result.error.suggestion` and passes, and the scenario that would call it is left out of the executed jobs (`endpoints/botcore/plugins/botcore-factory/src/botcore_factory/queue.py:63-66`; `tests/test_scenarios.py:26-41`). The gateway's `CLAIM_LOST` error names `lane-drop`, a factory command the gateway's caller cannot call (`gateway/service.py:231`). Eight Umbel suggestions spell commands as `umbel workspace-doctor` or `umbel plugin-show`. Reading the code suggests the CLI parser would reject these, since the working forms are `umbel workspace doctor` or `umbel call workspace-doctor` (`endpoints/umbel/src/cli/parse.rs:111-144`) [inferred from code, not executed]. This is Lean's lesson exactly: the right command in the wrong rendering.

The testing package can assert a suggestion's spelling, but nothing more. A scenario's `expect.error.suggestion` is a substring match by default, or any of the generic matchers (`packages/testing/src/runner/evaluator.ts:103-108`). Across 230 scenario files, **all of roughly 186 suggestion assertions use `contains`**. By a second count, **only 24 of 180 steps that expect a suggestion (13%) are followed by a step calling the command the suggestion was asserted to contain** [approximate: each step paired with the next `command:` line]. Even those follow-ups are hand-written and do not use the refusal's output (`docs/features/active/factory-gateway/scenarios/01-claim-once.scenario.yaml:27-70`). The structural limits are specific. Step references resolve only in `input`, never in `command` or `expect`, so a scenario cannot "call whatever the last refusal suggested" (`runner/scenario-runner.ts:345`; `parsers/yaml.ts:168-171`). The evaluator is pure and synchronous, so it cannot run a command (`runner/evaluator.ts:45-48`). No state snapshot, fork or reset exists between steps: `AppAdapter.fixture.reset` is declared but no runner code calls it, and `isolation` is rejected as unimplemented (`adapters/types.ts:82-86`; `types/scenario.ts:259-266`). Coverage is static. It counts error codes named in scenario text against a hand-typed list, so a code "tested" in YAML need never be reached (`commands/coverage.ts:178-186`). The package does no input generation, property-based testing or exploration, and its dependencies are only afd-core, afd-server, yaml and zod. YAML cannot move the clock between steps, though a hook with a `ManualClock` could. The ports diverge in ways that matter here. **The Python parser silently drops `error.suggestion` and its evaluator never checks it**, so a scenario asserting a suggestion passes in Python unchecked (`python/src/afd/testing/scenarios/parser.py:231-239`; `evaluator.py:75-95`). Python also lacks `before_step`/`after_step` hooks. Rust and C++ have no scenario runner at all, so cross-language behaviour rests on the 50-case todo conformance suite. Finally, the jobs-first guidance says "No CI job reads scenario files under `docs/`", and many are drafts with invented data (`.claude/skills/afd/references/jobs-first.md`), so a dynamic check can only run on executed suites such as the factory's (`endpoints/botcore/plugins/botcore-factory/scenarios/run.mjs`).

There are useful attachment points. The runner's `afterStep` hook receives the full `CommandResult` on both executors (`runner/scenario-runner.ts:51-68, 402-408`). `${{ steps[N].error.suggestion }}` already resolves, though only as prose. The `unresolved-prerequisite` surface rule, which checks that each `requires` name exists, is the existing model for checking names in a suggestion (`packages/testing/src/surface/prerequisite-rules.ts:14-35`).

## Build the check in stages, starting from the shared specification

The prior art and the codebase together imply an order of work. Each stage is useful alone, and each later stage needs the earlier ones.

The first stage fixes what the survey already found and closes the cheapest gap. Correct the `lane-handoff`, cross-surface `lane-drop` and Umbel CLI suggestions. Make the Python parser keep `suggestion` and its evaluator check it, so the four ports stop disagreeing silently. Correct the schema README's claim about surface linters. Then add a static rule modelled on `unresolved-prerequisite` and on rustc's tidy check: every command-shaped token in a suggestion must resolve in the registry of the surface, and the route, that raises it. Suggestions exist only at run time, so the rule needs either declared suggestion templates per error code or a corpus of suggestions collected from scenario runs. Collecting from runs has a second benefit. It turns coverage from "codes named in YAML" into "codes actually reached", Yuan's bottom-up target. Exemptions should sit in an explicit list that fails when an exempt code gains a real test, as rustc's does, so the list cannot go stale. The same rule can flag the anti-patterns that fix validation warns about: a recovery whose remedy bypasses the guard that refused (`--force`, disabling a check) must be declared as intended, because a progress check alone would pass it. Some bypasses are legitimate, such as the confirmation flow's "repeat the call with `confirm: true`", which is why they are declared rather than banned.

The second stage gives the suggestion a machine-readable part in `spec/schema/error.json`, beside the prose and not in place of it. Every precedent that verifies anything works from structure: Rust's applicability levels, MCP's -32042 elicitation list, SEP-3313's `retryable` and `retryNotBefore`, and AFD's own `undoCommand`/`undoArgs`. A structured recovery would carry the command and its input, and a kind drawn from the corpus classes and the delivery study's four fault kinds. The kind says whether to call a named command, call the same command with changed arguments, wait and retry, stop because the error is unrecoverable, or hand off to someone outside the command surface. It would also carry Rust's distinction between input fully given and input the caller must supply, and the audience split from IBM's catalogs, caller versus human operator. Only caller-addressed recoveries can be followed mechanically. A D-class "ask the deployer" recovery is honest and Polite on the cruelty scale; the check should confirm that it names a real configuration key, not try to follow it. The schema sets `additionalProperties: false`, so this is a specification change with new vectors in `spec/vectors`, which is what keeps four ports in step. Lean's finding sets one constraint: if the prose is written separately from the structure, the check must confirm that the prose names what the structure says, since agents read the prose.

The third stage is the follow-and-assert check itself, in the TypeScript runner first. It cannot live in the pure evaluator. It belongs in `executeStep`, as a new expectation (for example `expect.error.recovers`) or as a step kind that calls a previous step's structured recovery. The oracle should be layered, as Roslyn's and Copilot Autofix's are. First, the recovery command must be enabled: it must not come back as an unknown command or the same refusal. Second, re-issuing the original call must succeed or return a different refusal code the scenario declares. Third, an independent state assertion must hold that the follow-up cannot game, such as a `-get` after a `-create`; this is the held-out oracle that automated repair learned it needs. Fourth, a read recovery's claim must hold in its output (`holdReason` is present). Fifth, a chain of recoveries must end within N steps without revisiting a refusal, the convergence check that ESLint's ten passes and Roslyn's iteration bound provide. Conditional recoveries split by kind. Where the code picks the branch from known state, the fixture fixes the state and expects one branch. Where the caller must read state first, the scenario encodes the choice, as Error Prone's `FixChooser` does. Wait-and-retry recoveries need the clock to move, so the hook or the YAML must be able to advance a `ManualClock`. Trying a recovery without corrupting later steps needs isolation: re-apply the fixture into a fresh world per branch (todo's `clearFirst` and the factory's per-scenario directory already make this possible) and wire up the unused `fixture.reset`. Recoveries that name destructive or non-idempotent commands should go through the existing `mutation`/`destructive` metadata and approval gates, because the delivery study and SEP-3313 both flag duplicate writes from blind retries. Python then needs the same hooks. Rust and C++, which have no scenario runner, get recovery cases added to the shared conformance suite so the behaviour is specified once.

The fourth stage labels each suggestion with how it was verified, borrowing Sledgehammer's `some` versus `some_preplayed`. A suggestion is *derived* if it is computed from the registry, *followed* if a passing scenario carried it out, and *unverified* otherwise. A per-code report then shows where unverified advice remains. The last stage is a small-world explorer beside `scenario-evaluate`. It enumerates commands with small inputs over the factory's fixture worlds, builds the reachable state graph, and checks that every refusal's recovery lands in the set of states that can still reach a job's success state. That set is AG EF along the suggestion, and the jobs-first scenarios already supply the goals. The explorer must exclude a universal "start over" so it cannot make everything look recoverable. It is worth building only after the structured field and reset exist; before then it would be parsing prose. Separately, a model-driven follower can measure whether agents *use* good advice well. It cannot establish whether the advice is *true*, which needs the deterministic follower.

## Conclusion

This research changes the question. "Does every error carry a suggestion?" is the standard that SRE pages, WCAG and IBM catalogs settled for, and the standard AFD enforces today with a warning. Systems that settled there never found out whether their advice worked. The fields that did find out (compilers, proof assistants, industrial autofix) all made the suggestion an executable object and judged it with an oracle independent of the checker that raised it. AFD has a stronger reason than any of them to cross that line. Its readers are agents that the measured studies show will follow advice faithfully, even advice they cannot carry out. Its server tells those agents in so many words to "follow error.suggestion to recover". Its own corpus already holds suggestions that name commands which do not exist.

The less obvious implication concerns where the work belongs. The largest single gain is not the clever check but the specification change underneath it. Only 18% of today's suggestions are followable as written, and almost every gap comes from advice being prose: missing arguments, values stated in sentences, CLI spellings, and state-dependent branches. A structured recovery field turns most of these into machine-checkable claims. It lets four ports share one definition through vectors, and it gives the novel part, executing the suggestion and asserting progress, something precise to execute. AFD's check could be the first instance of the idea for agent-facing interfaces, and it would also serve as a reference design for proposals like MCP's SEP-3313, which still leave `agentGuidance` as untested prose.
